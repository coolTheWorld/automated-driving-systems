# 运动规划：Frenet 采样（`ads_planning`）

> **改这个模块前先读本文。** 里面有八条「做错了不会报错，只会给出一条看起来能开的轨迹」的结论，
> 每一条都会指出守着它的测试用例。
>
> 相关：[control.md](control.md)（下游）、[map_and_routing.md](map_and_routing.md)（上游）、
> `tasks/plan.md` 第四部分（切片与检查点）。

---

## 0. 这个模块要回答什么

上游 `ads_map` 给出一条全局路径（`/route/path`，车道中心线采样点，步长 0.5 m）。
下游 `ads_control` 要一条**能跟的轨迹**。中间缺的那一步是：

> **前面有东西挡着，这一段该怎么走、走多快。**

拆成两个动作，对应本模块的两个交付能力：

| 能力 | 触发条件 | 输出 |
|---|---|---|
| **绕行** | 侧向留得下车 + 安全间距（§6 的不等式） | 一条偏离中心线的轨迹 + 相应的速度剖面 |
| **减速停车** | 留不下（几何上无解） | 沿中心线、在障碍物前停住的剖面 + diagnostics 报「不可行」 |

**两个都要。** SPEC §2 第 3 条原文是「遇到前方静止/慢速障碍物时安全减速**或**绕行」——
只做绕行的话，遇到绕不过去的情况会去挤那条不存在的缝。

## 1. 约定与符号

**全部沿用仓库既有约定，一个都不新发明。** 符号不一致是这类模块最贵的 bug 源：
它不会崩，只会让车往反方向绕。

| 符号 | 含义 | 单位 | 约定来源 |
|---|---|---|---|
| `s` | 沿参考线的累计弧长 | m | `ads_common::PathPoint::s_m` |
| `d` | 横向偏移，**左为正** | m | `PathProjection::lateral_error_m`（同一个量） |
| `θ(s)` | 参考线切向 | rad | `PathPoint::heading_rad` |
| `κ(s)` | 参考线曲率，**正 = 左转** | 1/m | `PathPoint::curvature_inv_m` |
| `T(s)` | 单位切向量 `(cos θ, sin θ)` | — | — |
| `N(s)` | 单位**左**法向量 `(−sin θ, cos θ)` | — | 因为 `d` 左正，法向必须也左正 |
| `d′`, `d″` | `dd/ds`、`d²d/ds²` | 无量纲、1/m | **对 s 求导，不是对 t**（见 §4.3） |

**`d` 左正是从哪来的**：`ads_map` 的车道横向偏移 `t` 左正、ROS 的 y 轴向左、
转角 δ 左正、`lateral_error_m` 左正。全仓库统一，代价是 Stanley 的控制律里多一个减号
（见 control.md §0）。**不要为了「教科书是右正」在这里翻过来。**

二维 Frenet–Serret（本文全部推导的出发点）：

```
dT/ds =  κ N
dN/ds = −κ T
```

## 2. 为什么用 Frenet 而不是直接在笛卡尔系规划

笛卡尔系下「沿路往前走多远」和「偏离车道多少」是**耦合**的：要往前 20 m 又偏左 0.8 m，
得同时定 x 和 y，搜索空间是二维的，而且「不出车道」这个约束在 x-y 里是一条弯曲的带子。

Frenet 系下这两件事**正交**：

- `s` 管纵向 —— 走多远、走多快
- `d` 管横向 —— 偏多少

于是可以**分别**采样再组合，二维搜索降成两个一维问题；「不出车道」也变成一个
简单的区间约束 `|d| ≤ 车道半宽 − 半车宽`。这就是 Apollo EM Planner 和绝大多数
量产规划器的基础思想（SPEC §3.2）。

**代价有两个，都要知道**：

1. **变换本身有奇异点**（§3.4）。`d·κ ≥ 1` 时偏移曲线出现尖点，Frenet 坐标失效。
2. **参考线的质量决定一切**。参考线抖，规划出来的轨迹就抖，而且症状出现在下游。

## 3. 坐标变换

### 3.1 笛卡尔 → Frenet：**已经有了，不要重写**

`ads_common::ReferenceLine::project()` 返回的 `PathProjection` 就是这个变换：

| Frenet 量 | 取自 |
|---|---|
| `s` | `projection.s_m` |
| `d` | `projection.lateral_error_m` |
| 参考线在该处的 `θ`、`κ` | `projection.heading_rad`、`projection.curvature_inv_m` |

它有 16 个 L1 用例对着解析解验过（`build/ads_common/test_reference_line`），
其中包含 P2 踩过的三个坑：弧长按实际点距而非序号累加、角度差必须过 `angle_diff`、
最近点用局部搜索。**规划侧直接用，不要因为「这是控制包写的」而另起炉灶。**

> ⚠️ **`project()` 的 `hint` 不是性能优化。** 环线上自车前后必然有几何距离相近的
> 两段路径，全局最近点会在两者间跳。规划周期 100 ms、车速 8.3 m/s 时一拍走 0.83 m
> ≈ 1.5 个采样点，默认 30 点的窗口有两个数量级余量。

### 3.2 Frenet → 笛卡尔：等距偏移曲线

这是 S2 要新写的部分。位置是直接的：

```
p(s, d) = r(s) + d · N(s)
```

切向对 s 求导（`d` 随 s 变化，用乘积法则 + Frenet–Serret）：

```
dp/ds = T + d′·N + d·(dN/ds)
      = T + d′·N + d·(−κ T)
      = (1 − d·κ)·T + d′·N
```

记 **`σ ≜ 1 − d·κ`**（下文反复出现），则：

| 量 | 表达式 | 直觉 |
|---|---|---|
| **弧长因子** | `\|dp/ds\| = √(σ² + d′²)`；`d` 为常数时退化成 `σ` | 左转弯（κ>0）内侧（d>0）走的路更短，所以 σ<1 |
| **朝向偏差** | `Δψ = arctan(d′ / σ)` | 轨迹相对参考线的夹角 |
| **朝向** | `θ_p = θ + Δψ` | — |

**`σ = 1 − d·κ` 这个因子不是新东西** —— `ads_map` 算车道中心线长度用的是同一个
（见 map_and_routing.md：R=12 的弯上右侧车道半径 13.75 m，因为 d=−1.75、κ=1/12，
σ = 1 + 1.75/12 = 1.1458，12 × 1.1458 = 13.75 ✓）。
**两处必须给出同一个数**，这是 S2 的一条对账用例。

### 3.3 偏移曲线的曲率

一般情形（`d` 随 s 变化）的曲率：

```
        ⎡ (d″ + (κ′·d + κ·d′)·tan Δψ) · cos²Δψ         ⎤   cos Δψ
κ_p  =  ⎢ ───────────────────────────────────  +  κ    ⎥ · ──────
        ⎣                  σ                            ⎦     σ
```

**先验一下退化情形**（`d` 为常数：`d′ = d″ = 0` ⟹ `Δψ = 0`、`cos Δψ = 1`）：

```
κ_p = (0 + κ) · 1/σ = κ / (1 − d·κ)
```

这就是熟知的等距偏移曲线曲率。再代数字自检：R=12 的圆（κ=1/12），
向左偏 d=+4 m ⟹ 新半径应是 8 m ⟹ κ_p 应为 1/8。
`κ/(1 − 4/12) = (1/12)/(2/3) = 1/8` ✓

> **实现策略（重要）**：S2 直接实现**一般形式**，把 `d′`、`d″` 的默认值设成 0。
> 这样常偏移只是它的退化路径，`κ/(1−dκ)` 的测试同时也在验一般代码路径 ——
> 而不是"简单版先上、S3 再换成复杂版"（那会让 S2 的测试保护不到 S3 真正跑的代码）。

### 3.4 奇异点：`d·κ ≥ 1` 必须抛异常，不能给个数

`σ = 1 − d·κ` 出现在 `κ_p` 的分母里。`σ → 0` 时曲率发散，`σ < 0` 时偏移曲线
**掠过曲率中心翻到另一侧**，几何上出现尖点 —— 此时「(s, d)」这套坐标不再一一对应，
再算下去得到的每一个数都是垃圾。

几何含义：`d = 1/κ = R` 正好是**曲率中心**。往左偏得比转弯半径还多，等于绕到圆心外面去了。

本项目地图最小 R = 8 m，而 `|d|` 受车道宽限制不超过 0.85 m，`d·κ ≤ 0.106`，
**永远不会触发**。那为什么还要判？

> 因为「不会发生」和「发生了会静默给出错误答案」是两回事。改地图（R 变小）、
> 改车道宽、或者 P7 允许借道之后，这个条件可能就近了。
> **抛异常的代价是一行；不判的代价是某天车按一条尖点轨迹打死方向盘。**

守卫：`test_frenet` 的 `ThrowsAtCuspSingularity`（S2 任务 2.3）。

### 3.5 初始条件怎么来 —— **符号最容易错的地方**

lattice 的起点必须是**自车当前状态**在 Frenet 下的表示 `(d₀, d₀′, d₀″)`。

```cpp
d0  = projection.lateral_error_m;                        // 左正，直接用
d0' = -(1.0 - d0 * kappa) * std::tan(projection.heading_error_rad);
d0" = 0.0;                                               // 见下
```

**那个负号是全模块最容易写错的一处**，推导如下：

`heading_error_rad` 的定义是 `angle_diff(车头朝向, 路径切向)`，即 **θ_路径 − θ_车**
（`ReferenceLine::project()` 的实现，`reference_line.cpp:214`）。而 `d′` 要的是
**车相对参考线**的夹角 `Δψ_车 = θ_车 − θ_路径 = −heading_error_rad`。

由 §3.2 的 `tan Δψ = d′/σ` 得 `d′ = σ·tan(Δψ_车) = −σ·tan(heading_error_rad)`。

**物理自检**（写完代码务必手算一遍这个）：车头偏向参考线**左侧**时，
车正在往左跑，`d` 应当**增大**，即 `d′ > 0`。
此时 `θ_车 > θ_路径` ⟹ `heading_error_rad < 0` ⟹ `−tan(负) > 0` ✓

> **写错符号的症状**：车遇到障碍物往**错误的一侧**打方向，然后代价函数发现那边
> 更糟又打回来 —— 表现为在障碍物前左右摇摆。而每一层单看都"正常工作"。
> 守卫：`test_frenet` 的 `InitialLateralDerivativeSignMatchesHeading`（S2 任务 2.5 故障注入）。

**`d₀″` 取 0 而不是从车辆状态估**：它对应横向加速度的二阶信息，
仿真里可以从转角算，真车上要么没有要么很脏。取 0 的后果是**重规划时轨迹的
曲率会有一个小台阶**（不是位置和朝向的台阶，那两个是连续的）。
本项目 10 Hz 重规划 + 低速，这个台阶被转向执行机构（τ=0.294 s）平滑掉了。
**要改成非零估计的前提是先量出估计的噪声**，否则是拿脏数据换连续性。

### 3.6 往返一致性在折线上**达不到浮点级**（S2 实测，2026-08-04）

SPEC §8 L1 点名要测「笛卡尔 ↔ Frenet 往返一致性」。直觉上它该是浮点级的，
**但在折线参考线上不是**，而且这不是 bug 是表示法的性质：

- `project()` 的垂足是相对**弦**求的（垂直于线段）；
- `lateral_error_m` 却是沿**插值朝向**的法向量取的分量。

两个方向差一个角 `ε = (ratio − 0.5)·Δφ`（`Δφ` = 每段扫过的圆心角），
于是 `(query − foot)` 有一份**纵向残量**在往返中被丢掉：

```
往返位置误差  =  |d| · Δφ/2  =  |d| · 采样步长 / (2R)
```

| 工况 | 上界 | 实测最大值 |
|---|---|---|
| R = 8 m（本项目最小转弯半径）、`d` = 0.85 m、步长 0.5 m | 26.56 mm | **23.85 mm** |

实测是上界的 **89.8%**，说明这个闭式上界是**紧的** —— 测试里专门断言了这一点
（`EXPECT_GE(max_error, bound*0.5)`）：如果实测远小于上界，说明上界算错了
或者采样没覆盖到最不利的 `ratio`，**那样这条用例其实什么都没验**。

**所以判据分两档**，而不是给一个能糊过去的松容差：
直线上判 `1e-12`（纯代数、无离散化），圆弧上判**那个闭式上界**。

> 这个量级（26 mm）相对 §6 的 0.5 m 安全间距是 5%。**知道它在那儿**，
> 就不会在 P3-S5 调试时把它误认成规划器的偏差。要压小它只能减小采样步长
> （误差与步长成正比）。

## 4. 横向：五次多项式 lattice

### 4.1 为什么是五次

要固定的边界条件有**六个**：起点的 `(d₀, d₀′, d₀″)` 和终点的 `(d_T, 0, 0)`。
六个条件 ⟹ 六个系数 ⟹ **五次多项式**。次数是被边界条件数定死的，不是调出来的。

**为什么终点的 `d′`、`d″` 都取 0**：终点要求「回到与车道中心线平行、且曲率与车道一致」。
`d′ = 0` 是平行，`d″ = 0` 是曲率一致。绕行的目的就是绕完回来。

**为什么起点必须约束到二阶**：
- 只约束 `d₀`（零阶）→ 位置连续、**朝向跳变** → 转角指令跳变
- 约束到 `d₀′`（一阶）→ 朝向连续、**曲率跳变** → 转角**速率**指令跳变
- 约束到 `d₀″`（二阶）→ 曲率连续 → 转角速率有界

P2 已经量到过转向执行机构比控制器慢会怎样（τ 1.198 s → 弯道误差 0.801 m）。
往它嘴里塞一个不连续的转角指令，症状是同一类的：**车能开完全程，只是抖**。

### 4.2 闭式解（不要数值求解 6×6）

设 `S` 为采样纵向长度，起点 `(d₀, d₀′, d₀″)`、终点 `(d₁, d₁′, d₁″)`，`Δ = d₁ − d₀`：

```
a₀ = d₀
a₁ = d₀′
a₂ = d₀″ / 2
a₃ = ( 20Δ − ( 8d₁′ + 12d₀′)·S − (3d₀″ −  d₁″)·S² ) / (2S³)
a₄ = (−30Δ + (14d₁′ + 16d₀′)·S + (3d₀″ − 2d₁″)·S² ) / (2S⁴)
a₅ = ( 12Δ −  6(d₁′ +   d₀′)·S − ( d₀″ −  d₁″)·S² ) / (2S⁵)
```

前三个系数直接由起点条件读出（把 `s=0` 代进多项式及其一二阶导即得），
后三个是把终点三个条件写成 3×3 线性方程组解出来的。**是闭式的，不要去数值求解。**

本模块**总是**取 `d₁′ = d₁″ = 0`（绕完要回到与车道中心线平行、曲率一致），
此时退化为：

```
a₃ = ( 20Δ − 12·d₀′·S − 3·d₀″·S² ) / (2S³)
a₄ = (−30Δ + 16·d₀′·S + 3·d₀″·S² ) / (2S⁴)
a₅ = ( 12Δ −  6·d₀′·S −   d₀″·S² ) / (2S⁵)
```

> **那为什么接口还留着终点导数？** 因为把「终点要平行」这个**策略**写死在
> 多项式类里，就没人再想起它是个选择了。P7 做借道/换道时终点不一定平行
> （比如变道后要接一段本身就在转弯的车道），那时它是参数才改得动。
> 一个参数的代价，换的是「这条约定在调用点可见」。

**自检**（用例直接用它）：`d₀=d₀′=d₀″=0`、`d₁=1`、`d₁′=d₁″=0`、`S=1` ⟹
`a₃=10, a₄=−15, a₅=6`，即 `d(s) = 10s³ − 15s⁴ + 6s⁵`。
`d(1)=1 ✓`、`d′(1)=30−60+30=0 ✓`、`d″(1)=60−180+120=0 ✓`

### 4.3 为什么对 `s` 求导而不是对 `t`

Werling 的原始论文里横向多项式是 `d(t)`，因为它要处理**动态**障碍物 ——
「什么时候到那儿」决定了「那儿有没有人」。

本阶段只有**静态**障碍物，障碍物不动，所以「什么时候到」不影响「能不能过」。
于是 `d(s)` 就够了，而且省掉一整个时间维度的采样。**这不只是简化，在静态前提下它是正确的。**

> ⚠️ **P6/P7 接动态障碍物时这条不成立**，而且不是"精度不够"而是"表达不了"：
> 对一个横穿的行人，正确解可能是**等它过去**（原地或减速，`d` 完全不变），
> 纯路径 lattice 里根本没有这个候选。
> **那时要加的是时间维度，不是在现有框架上多采几条 `d`。** 见 §9。

### 4.4 采样网格与参数后果

网格是**二维**的：终点横向偏移 `d_T` × 完成机动的纵向长度 `S`。

**为什么 `S` 也必须采样，而不是固定一个值** —— 五次式要走到 `s = S` 才达到 `d_T`，
中途只走了一部分。固定 `S = 30 m` 时，`s = 10 m` 处只到 `0.21·d_T` ≈ 0.17 m，
**近处的障碍物根本绕不开**，而所有候选看起来都"在往那边走"。
让 `S` 一起采样，规划器才能在「缓而晚」和「急而早」之间选。

| 参数 | 含义 | 调大 | 调小 |
|---|---|---|---|
| `lateral.max_offset_m` | `\|d_T\|` 上限 | 能绕更宽的障碍物，但会压车道线甚至越入对向（ODD 不允许） | 可绕的情形变少，更多退化成「停」 |
| `lateral.offset_step_m` | 横向候选间隔 | 候选变少、算得快，但**可能恰好跳过唯一可行的那条缝**（§6 的可行区间可能只有 0.4 m 宽） | 候选变多，耗时线性增长 |
| `longitudinal.min_horizon_m` | `S` 的下界 | 应付不了近处的障碍物 | 能应付更近的，但曲率变大 → 曲率限速压低速度，转角速率可能顶到限幅 |
| `longitudinal.max_horizon_m` | `S` 的上界，**同时也是评估长度** | 机动更缓更舒适，但整体更迟钝，且每周期检查更远 → 耗时线性涨 | 反之 |
| `longitudinal.horizon_step_m` | `S` 的间隔 | 候选变少，可能跳过唯一能及时绕开的那个 `S` | 耗时涨 |
| `trajectory.resample_step_m` | 输出轨迹点距 | 点少、下游插值误差大 | 点多、消息变大 |

`min_horizon_m` 的下界由**制动距离**给出：`S` 至少要大于「以当前速度发现障碍物后
停下来的距离」。园区限速 5.556 m/s、`max_decel` 1.5 m/s² ⟹ 10.3 m，所以取 10 m
是**贴着**这个下界的。**lib 层不检查这一条** —— 它要知道车速，而车速属于纵向（§7），
混进横向层会让这一层没法脱离纵向单独测试。

### ⚠️ 所有候选必须在**同样长度**上评估，与各自的 `S` 无关

`S` 小的候选如果轨迹也短，碰撞检查覆盖的距离就少 —— 于是**它会显得更安全**，
而一个只问「有没有撞」的判据完全发现不了。

所以实现上：`s ≤ S` 走五次式，`s > S` **保持 `d ≡ d_T`**（导数为 0），
一直画到完整的前视距离。既不能截断，也不能继续外推五次式
（它在 `3·S` 处已经发散到几百米）。这三种做法里只有一种对，而另外两种都不会
让碰撞检查变红 —— 守卫是 `CloseObstacleForcesAShortManeuverAndTheOffsetIsHeldAfterwards`，
它逐段量点距（跳变会让某一段从 0.5 m 变成 0.94 m）。

### 4.5 代价函数

```
J = w_offset · d_T²                       ← 尽量贴中心线
  + w_curvature · Σ κ_p²·Δs               ← 尽量平滑
  + w_clearance · Σ max(0, d_safe − 间距)² ← 离障碍物远一点
  + w_consistency · (d_T − d_T,上一周期)²  ← 别跟上一拍打架
```

| 权重 | 调大 | 调小 |
|---|---|---|
| `w_offset` | 更愿意贴中心线，绕行更晚更急 | 无事也偏着走，占用对向余量 |
| `w_curvature` | 轨迹更平滑，但可能选一条"平滑地擦过障碍物"的 | 轨迹急，横向加速度可能顶到限值 |
| `w_clearance` | 离障碍物更远，但更容易顶到车道边界 | 贴着安全距离走，传感器误差一来就变成碰撞 |
| `w_consistency` | 抗抖动；**过大则反应迟钝**，且见下面的硬上界 | 上下周期跳变，车在障碍物前摇摆 |

`w_curvature` **只有在 `S` 也被采样时才有意义**：若 `S` 固定，`∫κ²ds` 与 `d_T²`
都随 `|d_T|` 单调增，两者永远不会给出相反的排序，该项完全冗余。
有了 `S` 的采样，它才是「别为了早点绕开就猛打方向」这个偏好的载体。

#### `w_consistency < w_offset` 是硬约束，不是调参建议

连续最优在 `d* = ρ·p`，其中 `ρ = w_c/(w_o + w_c) < 1` —— 偏移每周期都在缩。
但采样是**离散**的：当 `|d* − p| < 步长/2` 时它会**停在 p 不动**。代入 `p = 步长` 得

```
停住  ⟺  w_consistency > w_offset
```

超界的症状极隐蔽：**车绕过障碍物之后永久停在某个偏移上**，
全程不报错、轨迹平滑、也不压线 —— 只是从此再也不走车道中心了。
守卫是 `ReturnsAllTheWayToTheCenterLineOnlyIfConsistencyWeightIsBelowOffsetWeight`，
它跑十个周期看收敛，**并且用一组越界配置证明判据真的在那个界上翻转**
（否则"收敛了"可能只是碰巧）。

> **`w_clearance` 不能替代硬约束。** 间距 0.5 m 是 SPEC §8 S04 的**判据**，
> 必须是候选的**准入条件**（不满足直接淘汰），不是代价里的一项。
> 放进代价里意味着"够便宜的话可以擦着过" —— 那是把安全逻辑放进可被权重绕过的分支，
> CLAUDE.md 明令禁止。

### 4.6 全部候选都不可行时：**返回"不可行"，不返回"最不糟的那条"**

这条单独列出来，因为它是最有诱惑力的一个错误：代价函数已经能给每条候选打分了，
"取分数最高的"看起来天经地义。但那意味着**全撞的时候也会输出一条撞的轨迹**，
而下游 `ads_control` 没有碰撞概念，会老老实实跟着开过去。

正确行为：显式返回不可行 → §7 的停车剖面接管 → diagnostics 报出来。

## 5. 碰撞检测

**在笛卡尔系做，不在 Frenet 系做。** 理由：障碍物是笛卡尔系里的矩形，
变到 Frenet 之后它**不再是矩形**（弯道上会被弯曲成扇形），
用 Frenet 下的轴对齐盒去近似它，误差在弯道上最大 —— 而弯道正是最需要精确的地方。

方法：车体 OBB vs 障碍物 OBB，**分离轴定理**（两个矩形共 4 个待测轴，
利用平行性可减到 4 个）。

车体轮廓不是一个点：沿候选轨迹按固定步长取若干"车位姿"，每个位姿放一个
`length_m × width_m` 的矩形（取自 `vehicle_params.yaml`，**不硬编码**）。

SPEC §8 L1 点名要覆盖的边界情况，各一条用例：

| 情况 | 为什么单独测 |
|---|---|
| **相切** | 分离轴上投影恰好接触，`>` 与 `≥` 写错就在这儿现形 |
| **包含** | 一个完全在另一个内部时**没有分离轴**，只看"轴上是否分离"的实现会漏判 |
| **退化** | 零宽/零长的障碍物（上游给了脏数据）不能让算法崩或给出随机结果 |

## 6. 可行性不等式 —— **本文最重要的一节**

绕行**不是无条件可解的**，而这件事必须在放障碍物**之前**算清楚，不是在仿真里撞了才发现。

设车道宽 `W`、车宽 `w`、要求的安全间距 `g`，障碍物在车道坐标下横向占据 `[o_r, o_l]`
（`d` 轴左正，所以 `o_l` 是**左**边缘）。**从左侧绕行**要求同时满足：

```
车右缘 ≥ 障碍物左缘 + 间距 :   d − w/2  ≥  o_l + g
车左缘 ≤ 车道左边线       :   d + w/2  ≤  W/2
```

两式对 `d` 有解 ⟺

```
o_l + g + w/2  ≤  W/2 − w/2      ⟺      o_l  ≤  W/2 − w − g
```

代入本项目（`W = 3.5`、`w = 1.8`、`g = 0.5`，来源见 §8）：

```
o_l  ≤  1.75 − 1.80 − 0.50  =  −0.55 m
```

**结论：障碍物必须整体位于车道中心线右侧 0.55 m 以外，才可能从左边绕过去。**
（右绕对称：`o_r ≥ +0.55`。）

留给绕行的可行区间是 `d ∈ [o_l + g + w/2, W/2 − w/2] = [o_l + 1.4, 0.85]`，
**最宽也只有 1.4 m 那一点点** —— 现实中人开车绕障常常要压线，是同一个不等式。

### 三种处理，只有一种是对的

| 做法 | 评价 |
|---|---|
| 把间距判据从 0.5 m 放宽到能过为止 | ❌ 「为了让测试通过而放宽判据」，CLAUDE.md 禁止项 |
| 允许压对向车道 | ❌ 需要判断对向来车，那是 **P7 行为决策**。P3 的 ODD 不含它 |
| **不可行 → 减速停车 + 报 diagnostics** | ✅ SPEC §2 第 3 条原文 |

### ⚠️ 连续不等式是**必要不充分**的：还要看采样网格（S5 实测）

上面那个不等式回答的是「连续意义上有没有解」。但规划器采样的是**离散**的
`d_T`（本项目 `k × 0.2`、上限 0.85 ⟹ 最大只到 0.80），所以真正该问的是：

> **可行区间里有没有落进采样网格的点？**

反例是实测出来的：把障碍物从 `d = −1.2` 挪到 `−0.8`，
`o_l = −0.55` 恰好**等于**阈值 −0.55，连续不等式判「可绕」——
但可行区间退化成 `[0.85, 0.85]` 这么一个**单点**，而采样网格里根本没有 0.85。
于是生成器说"可绕"、规划器报"绕不过去"，**而人会去查规划器**。

`scripts/gen_obstacles.py` 因此按**网格**判，并与 `config/obstacles.yaml` 里
声明的 `expect` 对账，对不上就拒绝生成（这道检查也进了 CI）。

### ✅ 决定了：`safety.margin_m` 维持 0.5（CP-P3-B 实测，2026-08-04）

之前担心「真 Gazebo 有轮胎侧偏，执行误差与假车不是一个量级，实测间距会掉到
0.5 以下」。**实测否掉了这个担心**：

| 环境 | 车辆模型 | 实测最小侧向间距 |
|---|---|---|
| L3-G | 运动学自行车，无轮胎 | 0.523 m |
| **CP-P3-B（Gazebo）** | AckermannSteering，有轮胎 | **0.532 m** |

两者相差 9 mm，**Gazebo 那边反而略好**。原因是这段绕行发生在直道上、机动很缓
（实测全程最大 `|yaw|` 只有 0.064 rad），轮胎侧偏在这个工况下几乎不起作用 ——
它起作用的是**弯道**，而绕障不在弯道上。

**所以余量不加。** 加到 0.65 会让 §6 的阈值紧 0.15 m，而 `avoid` 场景 `o_l`
的余量本来只有 0.4 m —— 拿掉 37% 的 ODD 去换一个实测证明不需要的安心，不划算。

> **这条结论的有效范围**：绕行发生在**直道**上。哪天要在弯道上绕障，
> 侧偏就会起作用，这个结论**必须重新量**，不能照搬。

### ⚠️ 原先的顾虑（保留，因为推理本身仍然成立）

这两件事之间隔着**执行误差**，而现在的配置里它们取了同一个数（0.5），
也就是说**执行后的间距没有任何设计余量**。

L3-G 带障碍物用例的实测（假车、运动学模型）：

| 量 | 值 |
|---|---|
| 规划器选中的横向偏移 `d_T` | 0.600 m |
| 按它规划的间距 | 0.650 m |
| **实测最小间距**（车体外廓 → 障碍物外廓） | **0.523 m** |
| 高出 SPEC §8 S04 判据（0.5 m）的余量 | **0.023 m** |

23 mm 不是设计出来的，是碰巧 —— **这个推理仍然成立**：只要
`safety.margin_m` 等于判据本身，执行后的间距就没有设计余量，
够不够全看那一天的执行误差。

上面那节说明的是：在**当前这个工况**（直道、缓机动）下实测证明够用，
所以不加。**推理没被推翻，只是这一次的数据落在安全侧。**
换个工况（弯道绕障、更高车速、更急的机动）要重新量。

代价也记在这里，免得下次有人只看到"不加"就以为加了没坏处：
`margin` 每加 0.1 m，§6 的阈值就紧 0.1 m，可绕行的情形随之减少
（本项目 `o_l` 的余量本来就只有 0.4 m）。

### 验收场景据此选，不是随手放箱子

| 场景 | 障碍物 | `o_l` | 判定 |
|---|---|---|---|
| **绕** | 0.5×0.5 m 锥桶，中心 `d = −1.2` | `−0.95` | ≤ −0.55 ⟹ 可行，`d ∈ [0.45, 0.85]`，**0.4 m 实打实的裕度** |
| **停** | 同样的锥桶，中心 `d = 0` | `+0.25` | > −0.55 ⟹ **几何上无解**，必须停 |

选「0.4 m 裕度」而不是"恰好擦过"是有意的：判据要能区分"算对了"和"碰巧过了"。

## 7. 纵向：速度剖面

**速度规划在本模块，不在 `ads_control`**（2026-08-04 决策，见 `tasks/plan.md` P3-1 决策一）。
分界线是：**算目标是规划，跟目标是控制。**

`speed_profile`（曲率限速 + 终点减速 + 前后向扫描）从 `ads_control` 整体搬来，
算法一个字不改 —— 它的推导见 [control.md §4](control.md)，19 个 L1 用例全部对着闭式解。
本模块只改**输入**和**加一种触发**：

| | P2（在 control 里） | P3（在 planning 里） |
|---|---|---|
| 输入曲率 | 车道中心线的 κ | **选中的候选轨迹**的 κ_p（§3.3） |
| 减速触发 | 终点 | 终点 **+ 不可行时的障碍物前停车点** |

**为什么换了输入就必须搬包**：绕行轨迹的曲率比中心线大，曲率限速因此更低 ——
这个"更低"是**算出来的**，而只有 planner 知道自己选了哪条候选。
留在 control 侧的话它拿到的仍是中心线，减速纯属巧合。

`speed_controller`（PI + 条件积分抗饱和）**留在 `ads_control`** —— 那是跟踪器。

### ⚠️ 滚动窗口的末点**不能**强制归零（S4 实测踩到）

`SpeedProfile` 从 P2 起就在末点强制 `v = 0` —— 那时它覆盖的是**整条路线**，
末点就是终点，归零是对的。

P3 的轨迹是一个 **30 m 的滚动窗口**，末点只是"看到这儿为止"。再强制归零就等于
宣称「30 m 后你会停住」，而后向扫描会把窗口后半段的速度全压低。

**它的隐蔽之处**：本项目 `max_decel = 3.0`、窗口 30 m 时
`√(2·3·30) = 13.4 m/s` 仍高于巡航 5.556 —— 所以**自车所在的窗口前端一点问题都没有**。
直路上一切正常，等到窗口因路径末端而变短时才突然开始"莫名其妙地减速"。

修法是把终点速度参数化（`SpeedProfileParams::terminal_speed_mps`，默认 0）：

| 窗口被什么截断 | 末点速度 |
|---|---|
| **前视距离**（路还长） | 巡航速度 |
| **路径末端** | 0 |
| **停车点**（绕不过去） | 0 |

默认值留 0 是有意的：**漏填时行为是保守的**（早停），而不是"车冲过终点"。

### 加速度前馈必须一起搬

`accel_mps2` 字段不是可选装饰。P2-S4 实测：纯 P 速度环跟踪**斜坡**目标的稳态误差
= 斜率 / `K_p` = 3.0 / 1.0 = **3.0 m/s**，症状是"入弯偏快、终点冲过头"，
而稳态巡航时速度跟得很准（因为那时目标是常值）。
`a_ff = ½·d(v²)/ds` 是闭式的（剖面存的是 `v²` 不是 `v`，正是为了这个）。

---

### ⚠️ 滚动窗口 + 前馈 ⟹ 速度超调（CP-P3-B 实测，**已修**）

CP-P3-B 的无障碍物回归跑出了两个明显变差的数（同一条路线、同一个脚本）：

| 判据 | CP-P2-B（P2 时） | CP-P3-B（发现时） | 判据上限 |
|---|---|---|---|
| 最大横向误差 | 0.080 m | **0.2724 m** | 0.30（余量 73% → **9%**） |
| 最大横向加速度 | 1.594 | **1.879** | 2.0 |

8 条判据仍然全过，但余量被吃掉了大半。根因**不在横向**：

| 量 | 实测 |
|---|---|
| 全程速度超目标 > 0.5 m/s 的拍数 | 139 / 1357（**10%**） |
| 最大超出 | **2.13 m/s** |
| 最高车速 | **6.53 m/s**（巡航 5.556） |

机制是算术，不是猜测 —— 日志逐拍对得上：

```
a_cmd = a_ff + K_p·(v_ref − v) = 1.50 + 1.0×(5.17 − 6.38) = +0.29
```

`a_ff` 的上限就是 `max_accel` = 1.5，而 `K_p` = 1.0 ⟹
**车速要超出目标 1.5 m/s 以上，指令才可能变负**。在此之前车一直在加速。

**为什么 P2 没有**：那时剖面覆盖整条路线、只算一次，车从静止起就贴着它跑；
现在剖面是 30 m 滚动窗口、每 100 ms 重算。

**真正的根因不是滚动窗口，是控制器读错了位置。** 一次性探针抓到超调时刻的
那条 `/planning/trajectory`：剖面在 `s=0` 处是 4.281 m/s，而控制器读的是
`s=2.81` → 5.130 m/s。2.81 m ≈ **轴距 2.7 m**。

`control_node` 用**前轴**投影去取速度目标和前馈 —— 那是 Stanley 的参考点，
横向必须用它；但纵向的一切（目标速度、前馈、剩余距离、到达判定）都该用**后轴**，
因为轨迹点本身就是"后轴该在哪"。于是控制器一直在读**一个轴距之后**的剖面值，
下坡（减速段）时读到的是更快的目标，车自然冲。

修法：`control_node` 里另开一个 `rear_projection`，纵向量全部改用它。
**横向仍用前轴投影** —— 两个投影并存不是冗余，是两个参考点各司其职。

### ⚠️ 判据本身量错了对象（同一次实测，**已修**）

修完上一条，「最大横向加速度」这个判据**一个数都没变**。原因是它压根没在量车：

| 定义 | 含义 | 实测峰值 |
|---|---|---|
| `v²·κ_path` | **参考路径**的横向加速度 | 2.687 |
| `v²·tanδ/L` | 自行车模型按**转角**推的 | 2.376 |
| `\|v·ω\|` | **车实际受的**（ω 来自 `/odom` 的横摆角速度） | **2.329** |

`record_control_run.py` 原来算的是第一种 —— 它描述的是**路**，不是车。
路的曲率与控制器好坏无关，所以横向误差改善 12.7 倍时它纹丝不动。
现在 `control_node` 直接发布 `lateral_accel_mps2 = |v·ω|`，脚本读它。

**这一条比上一条更值得记**：上一条是代码错了，测出来会红；
这一条是**判据错了**，红绿都不可信 —— 而它长得和一个正常的判据一模一样。

### ⚠️ `a_lat_max` 必须为跟踪超调留余量（**已定：1.15**）

换成真值判据之后，规划侧的 `a_lat_max` 与实测值之间露出一个**稳定的放大比**：

| 规划限值 | 实测 `\|v·ω\|` 峰值 | 超调比 |
|---|---|---|
| 1.5 | 2.329 | 1.553 |
| 1.3 | 2.080 | 1.600 |
| 1.2 | 1.991 | 1.659 |
| **1.15** | **1.910** | 1.661 |

判据上限是 2.0（SPEC 的舒适性要求，说的是**实测**横向加速度）。

**超调比不是常数，它随限值下降反而上升** —— 因为 Stanley 的横向修正量与车速
无关（只看横向/航向误差），而路径本身贡献的 `v²κ` 随限速平方下降，分母降得快。
所以"除以超调比"只能当一次迭代的起点，**不是解析解**。

1.2 实测 1.991，余量只有 0.5%，两次跑分别是 1.954 / 1.991 —— **这个判据会 flake**，
而 flake 的判据和坏掉的判据在现场分不开。取 **1.15**，余量 4.5%。
代价是过弯变慢：R=8 限速 3.464 → **3.033**（−12.4%），R=13.75 → **3.976**。
**这是用过弯速度换判据稳定性的取舍，经用户明确批准。**

⚠️ 这些数绑死在**这条路线、这套 `lateral.gain`** 上，换地图或改增益要重新量。

### ⚠️ 停车点早一个轴距（CP-P3-B 实测，**已修**）

场景二实测停车间距 **4.265 m**，而设计值是 1.5 m（`safety.margin_m` 0.5 +
`stop_margin_m` 1.0）。差值 2.77 m ≈ **轴距 2.7 m**，算术对得上：

```
实测 4.265  =  设计 1.5  +  轴距 2.7  +  量化 0.065
```

根因与上面那条速度超调**是同一个** —— 规划器按后轴排轨迹，控制器按前轴判到达。
`control_node` 的 `goal_distance_m` 量的是前轴到轨迹末点的距离，
于是轨迹只剩一个轴距时控制器就宣布到了，车比设计位置早停 2.7 m。

改用后轴投影之后实测 **1.918 / 1.752 m**（两次跑），设计 1.5 + 停车判定余量。
**一处根因、两个症状**：一个表现为"入弯偏快"，一个表现为"停得太早"，
中间隔着两个模块，看起来毫无关系。

### block 场景的正确结局：末态是 `NO_PATH`，不是"挂了"

停车轨迹被执行完之后，规划器发的是一条**零长度**轨迹（车已经在停车点上），
`control_node` 判它无效 → 落到 `NO_PATH` 降级分支刹停并保持。实测末段
**449 / 799 拍是 `NO_PATH`**，车正是在这段里从 0.95 m/s 刹到 0.000。

这个末态是**正确且安全**的，但 `NO_PATH` 这个名字同时也承载"还没收到路径"和
"规划器挂了"，三件事共用一个状态名。当前靠 `/planning/diagnostics` 的
`planner_message`（"前方绕不过去，按停车轨迹执行"）区分 —— 判据就是这么写的。
**这是已知的可诊断性粗糙处，不是功能缺陷**，留待后续引入独立的 `STOPPED` 态。

⚠️ 它咬过一次：`record_obstacle_run.py` 的「终速」原本在
`TRACKING`/`GOAL_REACHED` 过滤后的样本里取末拍，于是量到的是**刹车中途**的
0.950 m/s，判据报 FAIL 而车稳稳停着。见该脚本 `score()` 里的注释。

## 9. 边界：已实现与未实现

**未实现的一律显式抛异常或返回"不可行"，不静默降级。** 这是 `ads_map` 立下的规矩
（spiral 几何、多 laneSection、变宽车道都抛异常），本模块照办。

| 项 | 状态 | 说明 |
|---|---|---|
| 静态障碍物绕行 / 停车 | ✅ P3 | 本文 §4–§7 |
| **动态障碍物** | ❌ | 不是精度问题是**表达能力**问题：路径 lattice 里没有「等它过去」这个候选。P6/P7 加时间维度 |
| **借道 / 压对向车道** | ❌ | 需要判断对向来车 = 行为决策，P7 |
| **变道** | ❌ | 本项目地图是单向单车道；有多车道后才有意义 |
| **倒车** | ❌ | `s` 单调递增是全模块的前提假设 |
| 参考线精度 | 折线近似 | 0.5 m 步长、R≥8 m ⟹ 弦高 3.9 mm，比 CP-P2-B 的 0.080 m 横向误差低两个数量级。**步长翻倍弦高变 4 倍**（`step²/(8R)`），R < 3 m 时须重新评估 |
| `d·κ ≥ 1` | 抛异常 | §3.4。本项目 `d·κ ≤ 0.106`，永不触发，但仍然判 |

## 10. 八条「做错了不会报错」的结论（速查）

| # | 结论 | 错了的症状 | 守卫 |
|---|---|---|---|
| 1 | **`d₀′` 的符号是 `−σ·tan(heading_error)`** | 车往**错误的一侧**绕，然后被代价函数拉回来 → 在障碍物前摇摆。每一层单看都正常 | `InitialLateralDerivativeSignMatchesHeading`（故障注入验过） |
| 2 | **曲率要除 `σ = 1 − dκ`** | 绕行段的曲率偏小 → 曲率限速偏高 → 弯道横向加速度超标。直线段完全正确 | `OffsetCurvatureMatchesClosedForm`（故障注入：把 `κ/σ` 写成 `κ`） |
| 3 | **全撞时返回"不可行"，不返回最优的一条** | 遇到绕不过去的障碍物照样输出轨迹，control 跟着开过去撞上 | `AllCandidatesBlockedReportsInfeasible` |
| 4 | **间距 0.5 m 是准入条件，不是代价项** | 权重一调，"够便宜就擦着过" | 见 §4.5 |
| 5 | **所有候选在同样长度上评估**，`s > S` 保持 `d ≡ d_T` | 短 `S` 的候选轨迹也短 ⟹ 碰撞检查覆盖得少 ⟹ **它显得更安全**。截断和外推都不会让碰撞检查变红 | `CloseObstacleForcesAShortManeuverAndTheOffsetIsHeldAfterwards`（逐段量点距） |
| 6 | **碰撞检查用车体几何中心，不是后轴** | 整体沿车头方向偏 1.35 m，而轨迹、代价、日志全部正常 —— 车从障碍物侧面擦过去却报告安全 | `CollisionUsesTheBodyCenterNotTheRearAxle`（故障注入验过） |
| 8 | **滚动窗口的末点不能强制归零** | 直路上完全正常（后向扫描的起点仍高于巡航速度），只在窗口因路径末端变短时才突然"莫名其妙减速" | `NoObstaclesCruisesAlongTheCenterLine` + `AccelerationIsHalfTheSpatialDerivativeOfSpeedSquared`（一条验不归零、一条验该归零时归零） |
| 7 | **`w_consistency < w_offset`** | 车绕过障碍物后**永久停在某个偏移上**，不报错、不压线、轨迹平滑，只是再也不走中心线 | `ReturnsAllTheWayToTheCenterLineOnlyIfConsistencyWeightIsBelowOffsetWeight`（含越界配置的反例） |

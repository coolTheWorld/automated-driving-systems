## 0. 术语、坐标与符号约定

| 记号 | 含义 | 单位 |
|---|---|---|
| `L` | 轴距（wheelbase），`config/vehicle_params.yaml` 的 `geometry.wheelbase_m` = 2.700 | m |
| `θ` | 自车航向角，x 轴正方向为 0，**逆时针为正**（REP-103） | rad |
| `θ_p` | 路径在最近点处的切线方向 | rad |
| `ψ` | **航向误差** `ψ = normalize(θ_p − θ)` | rad |
| `e` | **横向误差**，前轴相对路径的有符号偏移，**车在路径左侧为正** | m |
| `δ` | 前轮转角，**左正右负**（与 `ads_msgs/VehicleCmd` 一致） | rad |
| `κ` | 路径曲率 `1/R`，**正 = 左转（逆时针）** | 1/m |
| `k_e` | Stanley 的**横向误差增益** | 1/s |
| `k_soft` | Stanley 的**软化速度** | m/s |
| `v` | 纵向车速（后轴），取自 `/odom` 的 `twist.twist.linear.x` | m/s |
| `s` | 沿**路径**的累计弧长 | m |

> ⚠️ **符号冲突警告**：`docs/modules/map_and_routing.md` 里 `k` 是**曲率**。
> 本文档用 `κ` 表示曲率、`k_e` 表示 Stanley 增益，就是为了避免在同一个
> 表达式 `atan(k_e·e / (k_soft + v))` 里出现两个含义不同的 `k`。
> **代码里也必须这么命名**：`curvature_inv_m` 与 `lateral_gain`，
> 不许出现一个光秃秃的 `k_`。

坐标系：位姿取 TF `map → base_link`，速度取 `/odom`。
`base_link` 在**后轴中心、地面高度**（SPEC §3.3）。这一条在 §3.2 是致命的。

**`e` 的符号约定必须和代码逐字一致。** 定义为：以最近路径点的切向 `θ_p` 为 x 轴、
其左手方向为 y 轴，前轴中心在这个局部系里的 y 坐标就是 `e`。等价的叉积写法：

```
e = (P_f − P*) × t̂ 的 z 分量的相反数 …… 容易写错，不用
e = −sin(θ_p)·(x_f − x*) + cos(θ_p)·(y_f − y*)      ← 用这个
```

第二式就是「把 `P_f − P*` 投影到 `θ_p` 的左法向 `(−sinθ_p, cosθ_p)` 上」，
一眼能验，没有叉积那种「z 分量要不要取负」的记忆负担。

**选左正而不是照抄教科书的右正**，是为了和本仓库其余部分一致：
`map_and_routing.md` §0 的横向偏移 `t` 是左正，ROS 的 y 轴是左，转角 `δ` 是左正。
代价是控制律里会出现一个**减号**（§3.1），必须显式写清楚。

## 1. 问题设定

输入 `/route/path`（`nav_msgs/Path`，`map` 系，来自 P1 的 `map_node`）是一串带朝向的
位姿点。输出 `/vehicle_cmd`（转角 rad + 加速度 m/s²）。**横纵解耦**：

- **横向**：算 `δ`，让车贴住路径中心线。用 Stanley。
- **纵向**：算 `a`，让车按一个合理的速度剖面跑，并在终点停住。用「速度规划 + 速度环 PID」。

解耦的前提是低速：横向动力学（侧偏、侧倾）与纵向的耦合可以忽略。
ODD 是 30 km/h 以内的园区（SPEC §2），成立。**这条前提写在这里，
是为了将来有人想把这套东西用到高速上时能看到它。**

## 2. 路径预处理

`nav_msgs/Path` 只有位姿。控制律要的是弧长、曲率、最近点 —— 都得自己算。

### 2.1 弧长必须按**实际点距**累加

`map_node` 的采样步长 `path_sample_step_m = 0.5` 走的是**道路参考线**的弧长 `s`，
不是车道中心线的弧长。两者差一个因子 `(1 − t·κ_ref)`（`map_and_routing.md` §3）。

本项目地图上最极端的情形是环线四角：参考线 R=12，外侧车道横向偏移 1.75 m，

```
弧长因子 = 1 + 1.75/12 = 1.14583
实际点距 = 0.5 × 1.14583 = 0.5729 m      比标称大 14.58%
```

**用 0.5 代替 0.5729 的后果**（这是一条会静默发生的错误）：

| 被算错的量 | 错误方向 | 具体后果 |
|---|---|---|
| 曲率 `κ = Δθ/Δs` | 偏大 14.58% | 曲率限速 `v = √(a_lat/κ)` 偏小 **6.58%**（√1.1458 = 1.0704）—— 弯道上车明显开得慢，而没有任何一层报错 |
| 累计弧长 `s` | 偏小 12.7% | 终点减速的起点算错，车要么提前停、要么冲过终点 |

所以：

```
s[0] = 0
s[i] = s[i−1] + hypot(x[i] − x[i−1], y[i] − y[i−1])
```

**永远不要用 `i × path_sample_step_m`。** 那个乘法看起来更快也更"干净"，
而它在直路上完全正确 —— 这正是它危险的地方。

### 2.2 曲率：中心差分

```
κ[i] = normalize(θ[i+1] − θ[i−1]) / (s[i+1] − s[i−1])          内点
κ[0] = normalize(θ[1] − θ[0]) / (s[1] − s[0])                  端点用单侧差分
```

**`normalize` 不是可选的。** `θ` 由 `map_node` 从四元数取出，值域是 `(−π, π]`。
路径穿过朝向 ±π 的地方（本地图上就是所有朝西行驶的路段）时，
相邻两点可能一个是 `+3.14`、一个是 `−3.14`，裸差得到 `−6.28`，
除以 0.57 m 得到曲率 **−11 1/m**（半径 9 cm）。速度剖面立刻把限速压到
`√(1.5/11) = 0.37 m/s`，**车在直路上爬行**，而所有测试都是绿的
（单元测试用的路径大概率不跨 ±π）。

用 `ads_common::normalize_angle`（P0a 已有，`test_angles` 覆盖）。

> **精度**：路径点是 `map_node` **解析求值**出来的（不是传感器数据），
> 所以朝向 `θ` 和位置都是精确值，没有噪声要滤。
>
> 于是**唯一的误差来源是 `Δs` 用弦长近似了弧长**：分子 `Δθ` 精确，
> 分母偏小，算出的 `κ` 偏大，相对量恰好是 `(Δφ/2)²/6`（`Δφ` = 相邻点的转角）。
>
> | 半径 | 点距 | `Δφ` | κ 相对误差 | κ 绝对误差 |
> |---|---|---|---|---|
> | 8.00 m（路口转弯） | 0.5729 m | 0.0716 rad | **0.021%** | 2.7e-5 1/m |
> | 13.75 m（四角外侧） | 0.5729 m | 0.0417 rad | 0.007% | 5.3e-6 1/m |
>
> 传导到限速上是 0.01% 量级，可以忽略。**注意误差是单向的（κ 恒偏大 →
> 限速恒偏保守）**，不是随机的，所以它不会互相抵消，但方向是安全的那一侧。

### 2.3 最近点：从上次索引出发的局部搜索

不做全局暴力搜索，**不是为了快，是为了对**。

1119 个点、50 Hz 全扫是 5.6 万次距离计算/秒 —— 算得动。真正的问题是**语义**：
环线上自车前后**必然**存在几何距离相近的两段路径。刚驶出路口时，
路径上「刚才走过的那一段」和「正前方那一段」可能只差几米，
全局最近点会在两者之间跳，症状是**转角瞬间打死**。

局部搜索：从上一拍的索引 `i_prev` 出发，向前后各扫一个窗口（取 ±`ceil(v·dt/Δs) + 余量`，
实现上直接给一个固定的 `search_window` 参数），取窗口内最近的。天然排除跨段跳变。

**首次调用（或路径刚更新）没有 `i_prev`**，此时才做一次全局扫描。这一次是安全的：
车还没开始跟这条路径，不存在"跳变"的概念。

### 2.4 横向误差与航向误差

最近点 `P*` 落在两个采样点之间，直接取采样点会有最多半个点距（0.29 m）的量化误差 ——
**那是横向误差判据（0.30 m）的量级**，不能忽略。做法是把 `P*` 投影到
`[P_i, P_{i+1}]` 这条线段上：

```
t = clamp( (P_f − P_i)·(P_{i+1} − P_i) / |P_{i+1} − P_i|² , 0, 1 )
P* = P_i + t·(P_{i+1} − P_i)
θ_p = normalize(θ_i + t·normalize(θ_{i+1} − θ_i))       ← 角度插值也要过 normalize
s* = s_i + t·(s_{i+1} − s_i)
```

然后

```
e = −sin(θ_p)·(x_f − x*) + cos(θ_p)·(y_f − y*)
ψ = normalize(θ_p − θ)
```

`P_f` 是**前轴**中心，见 §3.2。

## 3. 横向控制：Stanley

### 3.1 控制律

```
δ = ψ − arctan( k_e · e / (k_soft + v) )
```

⚠️ **教科书写的是加号**，因为教科书的 `e` 是右正（车在路径右侧为正）。
本项目的 `e` 是左正（§0），所以**这里是减号**。

自洽性检查（每次改这行代码都该在脑子里跑一遍）：

| 情形 | `e` | `ψ` | 期望动作 | 公式给出 |
|---|---|---|---|---|
| 车在路径左侧，车头与路径平行 | +1.0 | 0 | 向**右**打 → `δ < 0` | `−arctan(正) < 0` ✓ |
| 车在路径上，车头偏右 30° | 0 | +0.52 | 向**左**打 → `δ > 0` | `ψ = +0.52 > 0` ✓ |

**符号写反不是静默错误** —— 那是正反馈，车会立刻冲出路径。所以它反而是这一节里
最不用担心的一处。真正要担心的是下面三节。

### 3.2 为什么必须是**前轴**

Stanley 的推导对象是**前轮的横向运动**：前轮的速度方向就是 `θ + δ`，
于是「打多少方向盘」和「前轮往哪走」之间是一个纯几何关系，没有车辆动力学。
换成后轴就不成立了 —— 后轴的速度方向恒为 `θ`，与 `δ` 无关，
转角只能通过改变 `θ` 间接影响它，中间隔了一个积分。

而本项目的 `base_link` 在**后轴中心**（SPEC §3.3，Autoware 惯例）。所以必须：

```
P_f = P_base + L · (cos θ, sin θ)          L = 2.700 m
```

**漏掉这一步的症状**：低速下几乎看不出来，速度越高越明显地**持续外偏**，
且弯道比直道严重。而人的第一反应是"增益不够，调大 `k_e`" ——
调大确实能压住一部分稳态偏差，代价是低速下开始震荡，于是陷入
**「快了偏、慢了晃」的死循环**，而两头都调不好的原因是控制律的输入点就是错的。

这是 Stanley 最经典的一处实现错误，专门写一条 L1 用例盯它（S2 的 2.1）。

**S2 把这个症状量化了**（`UsingTheRearAxleDegradesTrackingBadly`）。用后轴投影时，
后轴走的是与路径同心的圆，车身朝向与该点的路径切向**恰好平行**，于是
`ψ ≡ 0` —— **航向项整个消失了**，转弯全靠横向项撑：

```
arctan(k_e·|e| / (k_soft + v)) = arctan(L / R_rear),   R_rear ≈ R + |e|
⟹  |e| ≈ (k_soft + v)·L / (k_e·(R + |e|)) = 3.9641 × 2.7 / 9.17 ≈ 1.17 m
```

实测 **1.182 m**，符号为负（= 路径右侧 = 弯道**外**侧），稳态 `ψ = −0.0038 rad`。
三件事都对上了：量级、方向、以及"航向项塌成 0"这个机理。

> ⚠️ **这条用例是故障注入时才补上的，补之前测试套件对这个错误没有鉴别力。**
> 当时把 `front_axle_pose()` 改成直接返回后轴，**只有那一条静态用例变红，
> 所有闭环用例全绿** —— 因为闭环用的是测试夹具自己的换算。
> 「函数写对了」和「调用方记得调它」是两件事，各需要一条用例。

### 3.3 直线上的收敛：`ė ≈ −k_e·e`

设路径为 x 轴（`θ_p = 0`），则 `ψ = −θ`。前轴速度方向是 `θ + δ`，
横向误差就是前轴的 y 坐标，于是

```
ė = v_f · sin(θ + δ)
```

代入控制律，`θ + δ = −arctan(u)`，其中 `u = k_e·e/(k_soft + v)`：

```
ė = −v_f · u / √(1 + u²)
```

**这就是 Stanley 的全部魅力所在**，两个极限都很干净：

- **小误差**（`u ≪ 1`）：`ė ≈ −v_f·k_e·e/(k_soft + v)`。
  当 `k_soft ≪ v` 且 `v_f ≈ v` 时退化成

  ```
  ė ≈ −k_e · e            时间常数 1/k_e，与车速无关
  ```

  **收敛速度与速度无关**是 Stanley 相对纯追踪（Pure Pursuit）最大的优点：
  纯追踪的前视距离必须随速度调，Stanley 不用。
  `k_e = 1.0` → 时间常数 1 s → 从 1.0 m 收到 0.05 m 理想情况下需要 `ln(20) = 3.0 s`。

  仿真实测 **3.42 s**，比理想值慢 14%，两项都能对上账：
  `k_soft` 打折 `v/(k_soft+v)` = 0.917（时间常数 1.09 s → 3.27 s），
  加上大误差段 `√(1+u²)` 的非线性（初始 `u`=0.165，慢 1.4%）。
  **超调 0.00%** —— 一阶系统本来就不该有超调，有的话先怀疑速率限幅或增益。

- **大误差**（`u ≫ 1`）：`ė → −v_f`。横向趋近速度被限制在车速本身，
  也就是车最多以 90° 冲向路径，不会发散。`arctan` 提供的是**全局**收敛性，
  不只是局部稳定。

> ⚠️ **「与速度无关」有前提**：`k_soft ≪ v`。低速时收敛按
> `v/(k_soft + v)` 打折 —— `v = 0.5`、`k_soft = 0.5` 时时间常数翻倍到 2 s。
> 这是软化项的**代价**，不是 bug，见 §3.6。

**Stanley 没有「前视距离」这个参数。** 那是纯追踪的。
`tasks/todo.md` 早前那条「Stanley 对前视距离敏感」的说法是错的，已在本次同步修正 ——
按弧长而非点数计算的告诫本身仍然成立（§2.1），只是它作用于曲率差分和速度剖面查表，
不作用于一个不存在的前视距离。

### 3.4 定曲率路径上的平衡点：`e = 0`，`ψ = δ`

这一节的结论和直觉相反，而且它**推翻了 tasks/plan.md 初稿里的一个判据**。

在半径 `R` 的圆弧上跟踪稳定后，车走的是一个与路径同心的圆。设前轴走半径 `R_f`。
运动学自行车模型给出：后轴半径 `R_r = √(R_f² − L²)`，转角 `sin δ = L/R_f`。

关键在于**航向误差 `ψ` 不是 0**：

- 车身航向 `θ` 垂直于**后轴**的半径矢量（后轴速度沿车身轴线）。
- 路径切向 `θ_p` 垂直于**前轴**的半径矢量（最近点沿径向）。
- 两个半径矢量之间的夹角 = `arctan(L/R_r) = δ`。

```
                    ／ 前轴（在路径上）
             ╱  ╱  ← 车身，与路径切线夹角 = δ
        ╱  后轴（在路径内侧 R − R_r）
   ●  转弯中心
```

所以 **`ψ = δ`，恒等式，与 `e` 无关**。代回控制律：

```
δ = ψ − arctan(k_e·e/(k_soft+v)) = δ − arctan(k_e·e/(k_soft+v))
⟹  arctan(k_e·e/(k_soft+v)) = 0  ⟹  e = 0
```

**Stanley 在定曲率路径上的稳态横向误差恰好是零，不需要任何前馈。**
航向项自己就把曲率补偿了 —— 因为 `ψ` 是在**前轴**处量的，它天然含有那个 `δ`。

本项目地图上的具体数字：

| 路径 | R | `δ_ss = arcsin(L/R)` | 后轴内偏 `R − R_r` | 占最大转角 |
|---|---|---|---|---|
| 路口转弯车道 | 8.00 m | **0.3443 rad = 19.72°** | 0.469 m | **57%** |
| 环线四角内侧 | 10.25 m | 0.2666 rad = 15.27° | 0.362 m | 44% |
| 环线四角外侧 | 13.75 m | 0.1976 rad = 11.32° | 0.268 m | 33% |
| 直路 | ∞ | 0 | 0 | 0% |

> **19.72° 是物理事实，不是 bug。** RViz 里过路口时会看到车身明显"斜着"过弯 ——
> 前轴贴着车道中心线，车尾往内切 0.47 m。真车（尤其是长车）都这样，
> 叫**内轮差 / off-tracking**。将来有人报"车过弯时歪着"，答案在这里。
>
> 顺带一个必须核的余量：`δ_ss = 0.3443` 占最大转角 `0.600` 的 **57%**，
> 剩下 43% 留给误差修正。如果哪天把 `turn_radius_m` 从 8 调小到 5，
> `arcsin(2.7/5) = 0.5686` 就吃掉 95% 的转角权限 —— **车将无法修正任何误差**。
> 这是一条改地图时会踩、且症状表现为"控制器不行"的约束。

**推导已用独立的数值仿真复核过**（前向欧拉积分自行车模型闭环，
与上面的几何闭式解是两套方法）。三个结果：

| 量 | 解析推导 | 仿真实测（`dt` = 0.02 s，`k_e` = 1.0，`k_soft` = 0.5） |
|---|---|---|
| `ψ_ss`（R=8） | 0.3443 rad | **0.3496 rad** |
| `e_ss`（R=8） | **0** | **0.0162 m** |
| `e_ss`（R=13.75） | **0** | 0.0163 m |

`e_ss` 不是恰好 0，是因为定步长积分。**它与 `dt` 严格成正比**，
这就是「离散化残差」而非「建模错误」的判据：

| `dt` | 0.0400 | 0.0200 | 0.0100 | 0.0050 | 0.0025 |
|---|---|---|---|---|---|
| `e_ss`（m） | 0.03246 | 0.01619 | 0.00809 | 0.00404 | 0.00202 |
| `e_ss / dt` | 0.811 | **0.810** | 0.809 | 0.808 | 0.808 |

比值在 16 倍的 `dt` 变化下只动了 0.4% —— `e_ss = 0.81·dt`，**外推到 `dt → 0`
就是 0**，与解析结论一致。控制周期 50 Hz 下残差 **1.6 cm**，
远小于横向误差判据 0.30 m。

那个系数跟的是**横向加速度**，不是 R 或 v 单独（扫了 R ∈ {8, 10.25, 13.75}
× `a_lat` ∈ {1.0, 1.5, 2.0} 共 9 组）：

| `a_lat` | 1.0 | 1.5 | 2.0 |
|---|---|---|---|
| `e_ss / dt`（三个 R 的范围） | 0.555 – 0.558 | 0.810 – 0.818 | 1.062 – 1.076 |

也就是说**按固定 `a_lat` 做曲率限速时，离散化残差在全程是个常数**，
不会在急弯处变大。**机理没细究，这是实测规律，不要当定论。**

> **顺带一个可用的结论**：想把这 1.6 cm 再压小，办法是**提高控制频率**
> （100 Hz → 0.8 cm），不是调增益。增益动不了它 —— 它根本不是增益造成的。

**入弯的暂态比想象中小得多。** 初稿在这里估过 0.19 m（按「ψ 要一个时间常数
才建立起来，这期间车走直线」算的），**那个估计是错的**：`ψ` 没有滞后 ——
路径切向以 `v/R` 的速率转走，`ψ` 立刻同步增长，不经过任何一阶环节。
仿真给出的真实数字（直路 → R=8 圆弧，车从直路上完美跟踪进入）：

| 过弯车速 | 入弯峰值 \|e\| | 备注 |
|---|---|---|
| 3.464 m/s（已按曲率限速） | **0.0166 m** | `k_e`=2.0 时降到 0.0102 m |
| 5.556 m/s（定速巡航，不限速） | **0.0716 m** | `k_e`=2.0 时 0.0633 m |

所以 CP-P2-A 第三个场景的两个判据都可以定得很紧：稳态 < 0.05 m、峰值 < 0.10 m。

### 3.5 ⚠️ 不要给 Stanley 加曲率前馈

「路径曲率已经算出来了（§2.2），顺手加个前馈 `δ_ff = arcsin(L·κ)` 让它入弯更快」——
这是一个看起来毫无争议的改进。**它会引入一个原本不存在的稳态误差。**

因为 §3.4 已经证明航向项就是那个前馈。再加一份就是**双倍补偿**：

```
δ = δ_ff + ψ − arctan(k_e·e/(k_soft+v)),  且 ψ = δ 恒成立
⟹  arctan(k_e·e/(k_soft+v)) = δ_ff
⟹  e_ss = (k_soft + v)·tan(δ_ff) / k_e
```

R = 8 m、`v = 3.464`、`k_soft = 0.5`、`k_e = 1.0`：

```
e_ss = 3.964 × tan(0.3443) / 1.0 = 3.964 × 0.3585 = 1.42 m
```

**1.42 m —— 车直接开到车道外面去了**（越界线 0.85 m）。而这个改动在直路上
毫无影响、在 L1 的直线用例里全绿、在弯道上表现为"稳态偏差怎么调都消不掉"。

> 这条之所以值得单列，是因为它属于**「合理的改进使事情变糟」**这一类。
> 单元测试挡不住它（除非专门有一条定曲率稳态用例），代码审查也挡不住
> （那行代码看起来完全正确）。挡住它的唯一办法是先把 §3.4 推出来。
>
> **前馈不是永远错的** —— 一旦换成考虑轮胎侧偏的动力学模型，
> 稳态存在不为零的侧偏角，那时需要的是**侧偏补偿**而不是几何前馈，
> 且量级完全不同。P2 是运动学模型，不需要。

### 3.6 软化项 `k_soft`

`v → 0` 时 `k_e·e/v → ∞`，`arctan → ±π/2`，**转角瞬间打死**。而低速正是
起步和停车的工况，也就是这个模块每次运行都必然经过的工况。

`k_soft` 就是把分母抬离零：`k_e·e/(k_soft + v)`。它的量纲是速度（m/s），
物理含义是「**低于这个速度就不要太激进地修正横向误差**」。

| `k_soft` | 后果 |
|---|---|
| 调小（→ 0） | 低速修正更积极，但接近停车时转角剧烈抖动；`v = 0` 时打死 |
| 调大（→ 2） | 低速平稳，但**高速时也在打折**：`v = 5.556`、`k_soft = 2` 时收敛慢 26% |

取 **0.5 m/s**：在巡航速度 5.556 下打折 8.3%（几乎无感），
在 0.5 m/s 的爬行速度下打折 50%（保守，正确）。

### 3.7 转角限幅与**转向速率**限幅

两条都来自 `config/vehicle_params.yaml`，控制器**必须自己实现**：

```
|δ|        ≤ limits.max_steer_angle_rad = 0.600 rad
|Δδ / Δt|  ≤ limits.max_steer_rate_rad_s = 0.500 rad/s
```

**为什么不能指望下游**：`gazebo_bridge` 确实会截断 `δ`，但那是**静默截断**
（只 throttle 告警，见 `vehicle_cmd_bridge_node.cpp:149`）—— 控制器不知道自己的
输出被改过，于是任何积分状态都会继续往外飘。而**转向速率在 Gazebo 侧根本没有生效**：
`max_steer_rate_rad_s` 只进了 URDF 的关节速度限位，SDF 里 `AckermannSteering`
插件自己控制转向速度（这是 `tasks/todo.md` 早就记下的一笔待办）。
**真正的转向速率约束只能由控制器实现。**

> ⚠️ **这一段原本写着「速率限幅是有代价的，而且代价不小：0.500 rad/s 意味着
> 从零打到满舵要 1.2 s，这是个显著的相位滞后，完全可能把一个稳定的 `k_e`
> 变成震荡的」。S2 实测推翻了它** —— 在本地图的几何上，那个代价约等于零。

**判断速率限幅会不会成为瓶颈，有一个现成的判据。** 入弯时 `e ≈ 0`，于是 `δ ≈ ψ`；
而 `ψ` 以**路径切向的转速** `v/R` 增长（§3.4：路径切向转走，`ψ` 立刻同步跟上，
没有一阶滞后）。所以入弯真正需要的转向速率就是 `v/R` —— **不是**"从零阶跃到满舵"。
于是限幅开始起作用的临界车速是

```
v* = R · max_steer_rate_rad_s
```

| 弯道 | R | `v*` | 曲率限速给的 v | 限幅是否起作用 |
|---|---|---|---|---|
| 路口转弯车道 | 8.00 m | **4.00 m/s** | 3.464 m/s（`a_lat` = 1.5） | 否，低 13% |
| 环线四角内侧 | 10.25 m | 5.13 m/s | 3.921 m/s | 否 |
| 环线四角外侧 | 13.75 m | 6.88 m/s | 4.541 m/s | 否 |

实测（`TheSteeringRateLimitOnlyBindsAboveRadiusTimesRateLimit`）：
按限速过 R=8 的弯，控制律需要的最大转向速率 **0.4285 rad/s**（低于 0.500），
入弯峰值 |e| 只有 **1.6 cm**；定速巡航 5.556 m/s 冲同一个弯需要 **0.6921 rad/s**
（超限 38%），限幅确实卡住了输出，峰值涨到 **4.3 cm** —— 仍在 0.10 m 判据内。

> ⚠️ **这里藏着一条跨模块的耦合，交给 S3**：`a_lat_max` 调到 2.0 时
> `√(2.0 × 8) = ` **恰好 4.0 m/s**，正好顶在临界值上。也就是说那个看起来
> 只关舒适性的参数，与本模块的转向速率限幅是**耦合**的。上面那条用例把它钉住了。

> **顺带纠正一个测量方法上的坑**：判断"限幅有没有起作用"要看**实际下发过的
> 最大转向角速度**，不能拿横向误差去反推。巡航速度下横向误差里混着更大的
> 离散化残差（`a_lat` = 3.86 → 残差约 4 cm），实测放开限幅反而是 0.0466 m、
> 带限幅是 0.0426 m —— **方向与直觉相反且差值只有 9%**，用它当判据必然误判。

实现上，速率限幅需要 `Δt`。用**节点时钟**（仿真时间），不是墙钟（SPEC §3.3）。

### 3.9 ⚠️ Gazebo 的转向执行机构有 **1.2 s** 滞后（S4 实测）

这是 CP-P2-B 第一次跑出来的头号发现，也是 L1 **结构上不可能**预测到的东西 ——
运动学模型里转角是瞬时生效的。

用 `scripts/probe_steering_response.py` 开环测（控制器不参与，直接给
`/vehicle_cmd` 一个转角阶跃）：

| 量 | 修复前 | **修复后** |
|---|---|---|
| 稳态达成率（ω vs `v·tanδ/L`） | 99.7% – 100.3%（准） | **100.7%** |
| 转向**关节** 63% 上升时间 | **1.198 s** | **0.294 s** |
| **横摆角速度** 63% 上升时间 | **1.238 s** | **0.314 s** |
| 90% 上升时间 | 约 2.5 s | 约 0.39 s |

**两个上升时间几乎相等，说明滞后全部来自转向执行机构，车身动力学几乎不贡献**
（差 0.04 s）。稳态是准的，只是慢。

**为什么它是个问题**：Stanley 自己的闭环时间常数是 `1/k_e` = **1.0 s**，
而被控对象的滞后是 **1.2 s** —— 比控制器还慢。这是典型的震荡配方，
CP-P2-B 里的表现就是弯道上横向误差在 ±0.8 m 之间来回摆
（而同一条弯在 L1 上是 1.6 cm）。

**这个 1.2 s 是模型的产物，不是我们选的物理量。** 真车的转向执行机构约
0.1–0.3 s。`AckermannSteering` 插件用一个 P 控制器驱动转向关节，
而 SDF 里**从没设过它的增益**，用的是插件默认值。
同时 `config/vehicle_params.yaml` 声明的 `max_steer_rate_rad_s = 0.500`
（零到满舵 1.2 s）在 Gazebo 侧**根本没生效** —— 这是 §3.7 早就记下的一笔账。
巧合的是这两个 1.2 s 数值接近，但它们没有因果关系：一个是声明的速率上限，
一个是插件默认 P 增益的自然响应。

> **这正是 SPEC §4.1「双环境行为漂移」的物理来源。** 两个仿真器的执行机构
> 响应不一致，不会有任何一层报错，只会表现为"本地调好的增益一上 CARLA 就震荡"。
> 所以 P0b 对齐时**必须拿同一个脚本量一遍 CARLA**，而不是只对齐质量和轴距。

**修法：把响应时间做成车辆参数，增益做成推导量**（2026-08-03）。
`config/vehicle_params.yaml` 新增 `actuator.steer_response_time_s = 0.050`，
`scripts/gen_vehicle_model.py` 推导出 `<steer_p_gain> = 1/τ = 20`。

**不让人直接填增益，是因为增益换个仿真器就没有对应物**，而"给一个转角阶跃，
多久转到 63%"是能拿去和 CARLA / 真车对齐的物理量。这与 `gen_map.py` 里
`cutback` 做成推导量是同一条原则。

> ⚠️ **但那个参数不等于实测的端到端响应时间 —— 插件的关节速度环还有约
> 0.24 s 的地板，调它动不了那一部分。** 实测：
>
> | `steer_response_time_s` | `steer_p_gain` | 实测 63% 上升时间 |
> |---|---|---|
> | （插件默认，没设过） | 1.0 | 1.198 s |
> | **0.050** | **20** | **0.294 s** ← 当前 |
> | 0.020 | 50 | 0.255 s（2.5 倍增益只换来 13%） |
>
> 取 0.050 是因为它拿到了可改进量的绝大部分而增益还只有 20。再往上是在跟
> 地板较劲，代价是大误差时向关节下发上百 rad/s 的速度指令。
> **要知道实际有多快，跑脚本量，不要读那个参数。**

**修完之后的效果**（CP-P2-B 同一场景，只改了这一个参数）：

| 项 | 修复前 | 修复后 | 判据 |
|---|---|---|---|
| 最大横向误差 | 0.801 m | **0.0633 m** | 0.30 ✅ |
| 横向误差 RMS | 0.252 m | **0.0159 m** | 0.10 ✅ |

被控对象从"比控制器慢 1.2 倍"变成"比控制器快 3.4 倍"，震荡随之消失。

## 4. 纵向控制

分两层：**速度规划**（每一点该跑多快）和**速度环**（怎么跑到那个速度）。

### 4.1 速度剖面第一步：曲率限速

匀速过弯的横向加速度 `a_lat = v²·|κ| = v²/R`。反解得逐点限速：

```
v_curv[i] = min( v_cruise , √( a_lat_max / |κ[i]| ) )        κ[i] = 0 时取 v_cruise
```

**这不是精细化，在这张地图上是必需的**。`cruise_speed_mps = 5.556`（20 km/h）：

| 位置 | R | 定速 20 km/h 的 `a_lat` | `a_lat ≤ 1.5` 时的限速 |
|---|---|---|---|
| 路口转弯车道 | 8.00 m | **3.859 m/s²** | 3.464 m/s（12.5 km/h） |
| 环线四角内侧 | 10.25 m | 3.012 m/s² | 3.921 m/s（14.1 km/h） |
| 环线四角外侧 | 13.75 m | 2.245 m/s² | 4.542 m/s（16.3 km/h） |
| 直路 | ∞ | 0 | 5.556 m/s（巡航值） |

舒适横向加速度 1.5–2.0 m/s²，**3.86 是紧急变道的量级**。

> ⚠️ **这里要诚实说清楚理由，因为初稿把它写夸张了。**
>
> 初稿写的是「定速跑过路口，车会被甩出去、Stanley 硬拽回来、于是震荡」。
> **仿真不支持这个说法**：运动学模型下定速 5.556 过 R=8 的弯，
> 入弯峰值横向误差只有 **0.0716 m**，稳态回到 1.6 cm，全程平稳，没有震荡。
> 原因很简单 —— **运动学自行车模型里没有轮胎，不存在"甩出去"这回事**。
>
> 曲率限速真正的三条理由是：
>
> 1. **舒适性**（主要理由）：3.86 m/s² 的侧向力，园区接驳车上站着的人会扶不住。
>    这是 ODD 层面的要求，与控制精度无关。
> 2. **真车/CARLA 的裕度**：运动学模型不含侧偏，真车在 3.86 m/s² 下前轮
>    会产生可观的侧偏角，实际轨迹外偏远大于 7 cm。**本项目的头号风险是
>    「两环境行为漂移」**（SPEC §12）—— 在一个不会侧偏的模型上把速度定到
>    需要靠轮胎抓地才能过的量级，正是制造漂移的做法。
> 3. **跟踪精度**：入弯峰值误差从 0.0166 m 涨到 0.0716 m，**4.3 倍**。
>    绝对值都很小，所以这是**最次要**的理由，不该拿它当主要论据。
>
> 决策本身（做曲率限速）不变，但**论据要对**。拿一个仿真里根本不会发生的
> 症状去论证一个正确的决定，下一个人照着它去 Gazebo 里找"震荡"，找不到，
> 于是开始怀疑别的地方 —— 而问题出在论据上，不在代码里。

### 4.2 前后向扫描（forward-backward pass）

曲率限速只保证「在这一点速度合适」，不保证「上一点减得下来 / 加得上去」。
终点还要归零。三步：

```
第 0 步   v[i] = v_curv[i]  ；  v[n−1] = 0                      终点必须停住
第 1 步   后向（i = n−2 … 0）:  v[i] = min(v[i], √(v[i+1]² + 2·a_dec·Δs_i))
第 2 步   前向（i = 1 … n−1）:  v[i] = min(v[i], √(v[i−1]² + 2·a_acc·Δs_{i−1}))
```

依据是匀加速公式 `v_2² = v_1² + 2·a·Δs`。

> ⚠️ **这里原本写着「顺序不能反：前向扫描调低某点后，后向扫描算出的减速起点
> 就失效了」。S3 实测推翻了它** —— 20000 组随机剖面（随机点距、随机曲率限速、
> 随机 a_acc/a_dec），两种顺序的结果**逐点完全相同**（最大差异 0.0），
> 且对调之后两条约束一个点都不违反。

**顺序其实无所谓，而理由正是"两个扫描都只下调"。** 前向把 `v[i]` 降到
`√(v[i−1]² + 2a_a·Δs)` 之后，后向要的 `v[i−1]² ≤ v[i]² + 2a_d·Δs` 变成

```
v[i−1]² ≤ v[i−1]² + 2(a_a + a_d)·Δs        恒成立
```

反方向同理。所以两个扫描各自恰好调到**对方约束的安全侧**，谁先谁后都到同一个不动点。

**真正必须成立的顺序是：曲率限速与终点归零要在两个扫描之前完成。**
终点归零若放在后向扫描之后，剖面看着完全正常，只是车不会在终点停下来。

> **但这个论证依赖"只下调"。** 将来若加入「这一点**至少**要跑多快」这类**下界**
> 约束（比如为了不挡住后车），两个扫描就不再单调，论证立刻失效 ——
> 那时才真的要讲顺序，甚至要迭代到收敛。
> `test_speed_profile` 的 `ScanOrderDoesNotMatter` 在测试里独立实现了对调的顺序
> 并逐点比对，**加了下界约束那条用例会先红**。

**本项目地图上的距离**（`a_acc = 1.500`、`a_dec = 3.000`，均来自 `vehicle_params.yaml`）：

| 过程 | 距离 |
|---|---|
| 5.556 → 3.464（进路口转弯车道） | **3.14 m** |
| 3.464 → 5.556（出路口） | **6.29 m** |
| 5.556 → 0（终点，按 −3.0） | **5.14 m** |
| 5.556 → 0（终点，若改按 −1.5） | 10.29 m |

3.14 m ≈ 5.5 个路径点，前后向扫描完全覆盖得到。

> **没有引入新的加减速参数。** `a_acc`/`a_dec` 直接取 `vehicle_params.yaml` 的
> `max_accel_mps2`/`max_decel_mps2`。若实测觉得 −3.0 刹得太急，
> **那时**再加一个 `profile_decel_mps2`，并说得出它和车辆能力的关系 ——
> 现在加就是凭空多一个没有依据的数字。

### 4.3 剖面只在**路径更新时**算一次

剖面是**纯几何量**：只依赖路径的曲率和长度，不依赖车当前在哪、跑多快。
路径不变，剖面就不变。1119 个点两遍扫描约 2200 次开方 —— 算一次毫无压力，
50 Hz 算就是纯烧 CPU，且违反 SPEC §7「不允许在回调中做重计算」。

控制回调里只做**按当前弧长 `s*` 查表 + 线性插值**，O(1)（索引已由 §2.3 的
局部搜索给出）。

> **代价要说清楚**：剖面不含当前车速，所以它不是"从此刻开始的可行速度曲线"。
> 若车当前速度远高于剖面值（比如刚被 teleop 开到 8 m/s 然后切自动驾驶），
> PID 会给出一个被限幅到 −3.0 的减速指令 —— 行为正确，但**减速过程会短暂
> 超出剖面**。这是可接受的：剖面是期望，PID 负责收敛。

### 4.4 速度环：为什么纯 P 就够，以及为什么 `Ki = 0`

被控对象是**积分器**：控制器输出加速度 `a`，而 `a = v̇`。所以闭环是

```
v̇ = K_p · (v_ref − v)          ⟹   一阶滞后，时间常数 1/K_p
```

**对常值 `v_ref`，纯 P 的稳态误差就是零** —— 因为误差趋于零时 `a` 趋于零，
而 `v` 保持住不掉。这一点和「P 控制器总有稳态误差」的直觉相反，
差别在于被控对象本身带了一个积分。

`K_p = 1.0` → 时间常数 1 s，63% 收敛用 1 s，95% 用 3 s。

于是 **`K_i` 在这里几乎无事可做**：积分项补偿的是**持续扰动**（长坡、恒定阻力、
执行器零偏），而本项目地图是平的、Gazebo 的 `AckermannSteering` 按速度设定值跟随、
没有坡度。给一个大 `K_i` 的后果是超调加震荡，而且是那种"看起来还需要更多调参"的震荡。

> **初值 `K_i = 0`。只有实测出稳态误差才往上加，并且要说得出那个误差来自哪个物理量。**
> 「加点积分试试」是本领域最常见的一种无依据调参。

`K_d = 0`：对象已是一阶，微分项只放大 `/odom` 的速度噪声。

> ⚠️ **「纯 P 没有稳态误差」只对**常值**目标成立，而速度剖面不是常值 —— 它是斜坡。**
>
> 这一节原文说的是"对常值 `v_ref`"，那句话本身没错，但它**没有覆盖真正的工况**：
> 剖面在入弯前和终点前都是按 `√(2a·Δs)` 下降的，换算成时间就是一条斜率
> 约 `−a_dec` 的斜坡。一阶系统跟踪斜坡的稳态误差是
>
> ```
> e_v = 斜率 / K_p = 3.0 / 1.0 = 3.0 m/s
> ```
>
> S4 实测：终点前剖面从 5.556 降到 0（5.14 m 内），车实际到达终点时还有
> **4.36 m/s**，最终**冲过终点 4.25 m**（判据 1.0 m）。
>
> **同一个原因还撑起了另一条不达标的判据（现已一并修好）。**
> 修好转向执行机构（§3.9）之后，
> 横向误差降到 0.063 m，但**最大横向加速度仍是 2.113 m/s²**（判据 2.0）——
> 一个数都没变。查下来：峰值处横向误差只有 **−0.027 m**（跟得很好），
> 而车速比剖面高 **+0.85 m/s**（5.402 vs 4.551）。
> 按剖面速度过那个弯，`a_lat` 恰好是 **1.5002** —— 正是限值。
> **所以那 2.113 完全是超速造成的，与横向跟踪无关。**
>
> 这条值得记下来：`a_lat = v²·κ` 里有**两个**因子，横向误差不影响 κ，
> 只有速度会。看到横向加速度超标就去调横向增益，方向从一开始就是错的。
>
> **标准解法是加速度前馈**：`a = a_ff + K_p·(v_ref − v)`。这不是调参，
> 是补上一个结构上缺失的环节 —— 靠调大 `K_p` 只能按比例减小误差，
> 而且会同时放大噪声和限幅冲突。
> **P2-S3 的设计漏了它，S4 的闭环把它暴露出来。**
>
> **已于 2026-08-03 补上**（`SpeedProfile::target_accel_at()` +
> `SpeedController::update()` 多收一个前馈参数）。代入闭环：
>
> ```
> ė = v̇_ref − a_ff − K_p·e − K_i·∫e  =  −K_p·e − K_i·∫e      （当 a_ff = v̇_ref）
> ```
>
> 斜坡那一项被整个消掉。L1 实测（斜率 −1.0，K_p = 1.0）：
> 无前馈稳态误差 **0.974 m/s**（理论 1.0），有前馈 **0.020 m/s**。
>
> **前馈取 `a_ff = ½·d(v²)/ds`，不收车速参数。** 严格的链式法则是
> `dv_ref/dt = (dv_ref/ds)·(ds/dt)`，而 `ds/dt` 是**实际**车速；
> 但前馈的定义就是"车跟在剖面上时需要多大加速度"，那时 `ds/dt = v_ref`，
> 于是化简成只依赖剖面的 `½·d(v²)/ds`。车偏离剖面的那一份差额是
> **反馈该管的**，塞进前馈只会混淆职责，而且 `v_ref → 0`（终点）时还要处理除零。
>
> **顺带把剖面的段内插值从 `v` 改成 `v²`。** 剖面从头到尾是用
> `v² = v₀² + 2a·Δs` 构造的，所以在每个被扫描卡住的段上 `v²` **严格线性**：
> 插 `v²` 再开方精确复现那条 √ 曲线，插 `v` 则是拿弦去近似曲线。
> 对速度本身只差 mm/s，**但对前馈（= 曲线斜率）在末端偏 0.515 m/s²** ——
> 正好落在最需要它准的地方。改完之后前馈是闭式解 `≡ −a_dec`，
> 实测偏差 **3.6e-15 m/s²**。
>
> **终点停车逻辑也随之自洽**：`goal_reached` 之后目标速度 0、前馈给 `−a_dec`。
> 这不是硬塞一个数 —— 剖面在距终点 d 处的速度是 `√(2·a_dec·d)`，
> 而从那个速度按 `a_dec` 刹停需要的距离恰好又是 d。
> `stop_distance_m = 0.5` → 进入时 1.73 m/s → 刹停 0.5 m，正好停在终点。
> 实测终点位置误差 **4.259 → 0.257 m**。

**抗饱和**：即便 `K_i = 0` 也要把抗饱和写进去（结构上留好），因为
`K_i` 一旦被调成非零，没有抗饱和的积分器在加速度限幅期间会一路累积，
症状是**松开限幅后车猛窜**。做法是输出饱和时停止积分（conditional integration）。

实测（`K_p`=0.2、`K_i`=0.5、目标 1 m/s、车顶着不动 10 s）：

| | 积分终值 | 松开后峰值速度（目标 1.0） |
|---|---|---|
| 带抗饱和 | **2.58 m**（冻结点 2.60） | **1.32 m/s** |
| 朴素无条件积分 | 10.0 m | **3.97 m/s** —— 冲到目标的 4 倍 |

> ⚠️ **一处不要过度声称的地方**：条件积分（只冻结"继续往饱和方向推"的那一半）
> 与"饱和就完全冻结积分"，**从干净初值出发是完全等价的** ——
> 故障注入实测两者一条用例都不差。证明：条件积分保证 `K_i·I ≤ a_max`
> （I 最后一次增长时输出未饱和，即 `K_p·e + K_i·I ≤ a_max` 且 `e > 0`），
> 于是"误差反向却仍处于饱和"（需要 `K_i·I > a_max + K_p·|e|`）根本到不了。
>
> 仍然写条件积分，是因为它在这个前提被打破时才对（将来若加"把积分重置成非零值"
> 的接口、或运行期改限幅）。**但不要以为现在有测试在保护这个区别。**

### 4.5 ⚠️ 被控对象**不是**纯积分器

`gazebo_bridge` 的抗饱和逻辑（`vehicle_cmd_bridge_node.cpp:220`）：

```cpp
const double lead_cap = measured_speed_mps_ + setpoint_lead_mps_;   // +1.0 m/s
speed_setpoint_mps_ = clamp(speed_setpoint_mps_, 0.0, std::min(max_speed_mps_, lead_cap));
```

速度设定值最多超前**实测**速度 1.0 m/s。这是 bridge 为了防止"顶着墙积分饱和"
而加的，逻辑本身是对的，但它让 `a → v` 这一段成了**非线性**环节。

什么时候会触发：以 `+1.5 m/s²` 加速时，积出 1.0 m/s 的超前量需要 **0.667 s**。

> ⚠️ **那 0.667 s 隐含一个前提：实测速度全程是 0，也就是车根本没动。**
> S3 实测把条件说清楚了（`TheSetpointLeadCapOnlyBindsWhenTheVehicleCannotFollow`）：
>
> | 工况 | 超前上限有没有卡住 |
> |---|---|
> | 车正常跟随设定值（0 → 巡航，10 s） | **一次都没碰到**。设定值与实测同步推进，超前量恒为一拍的 `a·dt` = 0.03 m/s |
> | 车完全动不了（顶着墙 / 打滑 / 陡坡） | 在 **0.68 s** 卡住（闭式解 0.667 s），设定值被摁在 1.0 m/s |
>
> 所以原来那句"起步瞬间会触发"要加限定：**只有车实际跟不上时才触发**。
> 真车/Gazebo 上起步是否触发，取决于 `AckermannSteering` 插件的跟随滞后有多大
> —— 那个时间常数**没有实测过，不要凭空给它编一个数**。
> CP-P2-B 在 Gazebo 上跑起来时才能量到。

**L1 的纵向闭环测试里必须带上这个饱和环节建模**，否则 Gazebo 上会看到一个
L1 完全没预测到的起步迟滞，而人会去怀疑 PID 的增益。

### 4.6 S3 实测汇总（2026-08-02）

`test_speed_profile`（16 用例）+ `test_speed_controller`（12 用例），合计 **8 ms**。

| 量 | 判据来源 | 实测 |
|---|---|---|
| R=8 曲率限速 | √(1.5×8) = 3.46410 | **3.46382**（偏小 2.82e-4） |
| R=13.75 曲率限速 | √(1.5×13.75) = 4.54148 | **4.54135**（偏小 1.25e-4） |
| 全程最大横向加速度 | ≤ 1.5 | **1.5**（恰好贴住） |
| 终点制动段 vs `√(2a_d·剩余)` | 逐点 | **8.9e-13 mm/s** |
| 入弯提前减速距离 | 3.1449 m | **3.0026 m**（差一个采样步，符合预期） |
| 出弯回到巡航的距离 | 6.2897 m | **6.5026 m**（同上） |
| 两种扫描顺序的差异 | 0 | **0** |
| 左转 vs 右转剖面差异 | 0 | **0** |
| 纯 P（`K_i`=0）稳态误差 | 0 | **3.9e-5 mm/s** |
| 一个时间常数后剩余误差 | e⁻¹ = 36.79% | **36.42%**（前向欧拉离散值 36.42%） |
| 抗饱和：顶着墙 10 s 的积分 | 冻结点 2.60 | **2.58**（无抗饱和会到 10.0） |
| bridge 超前上限卡住的时刻 | 0.667 s | **0.68 s** |

**曲率限速那两个偏差不是误差，是可以精确写出来的离散化量**：弧长按**弦长**累加，
弦比弧短 (1 − Δφ²/24)，于是中心差分的曲率偏大同一因子，限速 ∝ 1/√κ 于是偏小
(1 − Δφ²/48)。R=8、点距 0.5 m 时 Δφ = 0.0625 → 偏小 2.82e-4，与实测一致到三位有效数字。
**方向是保守的**（限速偏小 = 过弯更慢），测试单独断言了这个方向 ——
它一旦变成偏大，就是弧长或曲率的公式被改坏了。

还有两条 bridge 的既有行为，控制器要知道：

- **看门狗 0.5 仿真秒**（`:201`）：超时按 −3.0 刹停并回正。控制节点按 **50 Hz**
  发布，余量 25 倍。⚠️ 看门狗用**仿真钟**，RTF > 10 时会持续误触发（当前 RTF≈1.0）。
- **加速度下限按 `emergency_decel`（−5.0）截断，不是 `max_decel`（−3.0）**（`:166`）：
  bridge 模拟的是"这辆车能做到什么"，不是"谁被允许这么做"。
  常规控制器**自己**不得越过 −3.0。

## 5. 运动学自行车模型（测试夹具）

CP-P2-A 要在一个不需要 ROS、不需要 Gazebo 的闭环里证明控制律收敛。用的就是
`vehicle_cmd_bridge` 里那个自行车模型的正向形式：

```
ẋ = v·cos θ
ẏ = v·sin θ
θ̇ = v·tan(δ) / L
v̇ = a
```

积分用固定步长 `dt = 0.02 s`（与 50 Hz 控制周期一致），RK1（前向欧拉）即可 ——
步长 0.02 s、时间常数 1 s，比值 50，欧拉的相对误差在 1% 量级，
远小于本文所有判据的余量。

**自洽性检查**（S2 的 2.4 用例）：定转角 `δ` 输入下，车应当走半径 `L/tan δ` 的圆。
`δ = 0.3443` → `R_r = 7.531`，跑一整圈后回到起点，位置闭合误差 < 1 mm。

> 这个模型**不是产品代码**，放在 `test/` 下。但 S5 会把它包成一个 ROS 假车节点
> 用于不需要 GPU 的闭环回归（L3-G，进 CI）。届时它要发 `/odom` + TF + `/clock`。
>
> ⚠️ **它证不了车在 Gazebo 里能开**：Gazebo 是 dartsim 的真物理，有质量、
> 惯量、轮胎摩擦、悬架。两者的差异正是 CP-P2-B 要验的东西。
> 三层测试各验各的：L1 验**控制律**，假车闭环验**节点接线**，CP-P2-B 验**真物理**。

| 参数 | 初值 | 物理含义 | 调大 / 调小 |
|---|---|---|---|
| `lateral.gain` (`k_e`) | 1.0 | 横向误差收敛速率，量纲 **1/s**。闭环时间常数 `1/k_e` | 调大（→3.0）收敛快（`k_e=2` → 0.5 s）；调小（→0.5）收敛慢、入弯暂态大。经验范围 0.5–3.0。**它必须比被控对象快**：S4 实测执行机构响应 0.294 s，`1/k_e` = 1.0 s 是它的 3.4 倍，够；修 SDF 之前执行机构是 1.2 s，比控制器还慢，弯道上直接震荡（§3.9） |
| `lateral.soft_speed_mps` (`k_soft`) | 0.5 | 低速软化，单位 m/s（§3.6） | 调大（→2.0）低速平稳但高速收敛也被打折（5.556 下慢 26%）；调小（→0）接近停车时转角抖动，等于 0 时打死 |
| `lateral.search_window` | 30 | 最近点局部搜索的半窗口（**点数**） | 0.5729 m/点 × 30 ≈ 17 m。**它是正确性要求不是性能优化**（§2.3）：调小 → 车速高或某拍卡顿时"追不上"路径；调大 → 退化成全局搜索，重新引入跨段跳变 |
| `longitudinal.kp` | 1.0 | 速度环比例增益，量纲 **1/s**。闭环时间常数 `1/K_p` | 调大（→2.0）跟得紧；调小（→0.5）起步和终点减速拖沓。范围 0.5–2.0。⚠️ **它不再是终点冲过头的解药** —— 那件事由加速度前馈解决（§4.4），调 `K_p` 只能按比例减小斜坡误差 |
| `longitudinal.ki` | **0.0** | 积分增益，量纲 1/s² | **默认 0 而且那是对的**（§4.4，实测稳态残差 3.9e-5 mm/s）。只有实测出稳态误差、且说得出它来自哪个物理量时才加 |
| `profile.max_lateral_accel_mps2` (`a_lat_max`) | 1.5 | 过弯的横向加速度上限 | 调大 → 过弯快（2.0 时 R=8 处限速升到 4.0 m/s）；调小 → 全程慢。舒适 1.5–2.0。⚠️ 两条陷阱：① **2.0 恰好顶在转向速率限幅的临界车速上**（`v* = R·rate` = 4.0，§3.7）；② 运动学模型不体现轮胎打滑，**调到 5 以上仿真里"能过"而真车会失控** |
| `goal.stop_distance_m` | 0.5 | 距终点多近算"到了"：之后目标速度归零、前馈给 `−a_dec` | **它与 `a_dec` 是自洽的，不要单独调**：剖面在距终点 d 处的速度是 `√(2·a_dec·d)`，而从那个速度按 `a_dec` 刹停需要的距离恰好又是 d。0.5 → 进入时 1.73 m/s → 刹停 0.5 m，正好停在终点（实测终点误差 0.257 m）。调大 → 更早进入全力刹停，提前停；调小 → 进入时速度更高，反而容易冲过 |
| `safety.max_lateral_error_m` | 1.5 | 横向误差超过它就判定偏离路径、减速停车 | **这是兜底不是精度考核**。越界线 1.750 − 0.900 = 0.850 m；取 1.5 是"已经压到相邻车道/绿化带"的量级，比 CP-P2-B 的 0.30 m 判据宽 5 倍。调到判据附近会在正常暂态里误触发，而**一个动不动就刹停的兜底会被人关掉，那还不如没有** |
| `safety.odom_timeout_s` | 0.5 | `/odom` 停多久算断了（**仿真时间**） | 取 0.5 与 `gazebo_bridge` 看门狗的 `cmd_timeout_s` **相同是有意的**：两层同时判定失联，日志能互相印证，而不是一层说断了另一层说没断 |
| `control_rate_hz` | 50.0 | 控制周期 | 下限由 bridge 看门狗 0.5 s 定（≥2 Hz 即可，取 50 是 25 倍余量）；上限由单拍耗时定（实测 3–7 ms，SPEC §7 要求 < 10 ms）。它还直接决定 Stanley 的**离散化残差** `e_ss ≈ 0.81·dt`，50 Hz 下 1.6 cm —— 想压小它只能提高频率，调增益动不了（§3.4） |

> **没有 `longitudinal.kd`，而且是有意不提供。** 被控对象已经是一阶，
> 微分项唯一的作用是放大 `/odom` 的速度噪声。提供一个"建议填 0"的参数，
> 迟早有人去调它。`SpeedControllerParams` 里也没有这个字段。
>
> **加速度前馈没有增益。** 它不是可调项，是结构的一部分（§4.4）：
> `a_ff = ½·d(v²)/ds` 直接加在输出上，量纲已经对了。给它配一个"前馈系数"
> 等于给一个正确的东西留一个调坏的旋钮。

## 7. 已知边界（**未实现，不要假设能用**）

| 边界 | 现状 | 触发时的行为 |
|---|---|---|
| **倒车** | 不支持 | `VehicleCmd` 没有挡位字段，负加速度只能理解为"减速"（`vehicle_cmd_bridge` 的速度设定值下限固定为 0）。路径必须是前进方向的 |
| **原地转向** | 物理上不可能 | 阿克曼转向 `ω = v·tan δ/L`，`v = 0` 时 `ω = 0`。真车也一样 |
| **轮胎侧偏 / 动力学** | 不建模 | 运动学模型假设轮胎无滑移。ODD 是 30 km/h 园区（SPEC §2），成立。上高速或湿滑路面**不成立**，届时要换动力学模型 + 侧偏补偿（§3.5） |
| **避障 / 跟车 / 停车让行** | 不做 | P2 的速度规划是**纯几何**的：只看曲率和终点。P3 的 Frenet 规划器接管后，这一层退化成兜底 |
| **地图限速** | 不读 | `campus_map.yaml` 的 `speed_limit_mps: 8.333` 已写进 `.xodr`，但 `ads_map` 的解析器没读它。P2 用 `vehicle_params.yaml` 的 `cruise_speed_mps`。读地图限速留给 P3 |
| **路径重规划 / 变道** | 换路径**可以**，平滑过渡**不做** | 收到新路径时剖面重算、最近点索引清空、速度环积分清零（转角**不清** —— 车轮此刻物理上就在那个角度上）。S4 实测在一次会话里连换两条路径正常工作。但新旧路径之间没有任何混合，横向误差会跳一下 |
| **坡道** | 不建模 | 地图是平的。有坡时需要重力前馈 `a_ff = −g·sin(坡度)`，那时 `K_i` 才真正有事做 |
| **仿真钟停走** | **控制器会"冻住"而不是降级** | `use_sim_time=true` 下 `now()` 不再前进 → `dt = 0` → 控制回调直接 return，不再发指令；而 `gazebo_bridge` 的看门狗**同样用仿真钟**、也冻住 → **车保持最后一条指令**。真车上墙钟不会停，所以这是仿真特有的。要补得用**墙钟做健康检查**（那是健康检查不是算法时序，不违反 SPEC §5）。S4 发现，未修 |
| **三种降级路径未实测触发** | 已实现，**未验证** | `NO_TRANSFORM` / `ODOM_STALE` / `OFF_PATH` 三条各有独立日志，但在当前拓扑下触发不了：`/odom` 与 `/tf` 的唯一来源 `parameter_bridge` **同时也是 `/clock` 的来源**（见上一行），而 `OFF_PATH` 的阈值 1.5 m 比正常横向误差（0.06 m）高两个数量级。**只有 `NO_PATH` 实测触发过。** 要验它们得做故障注入，S4 没做 |

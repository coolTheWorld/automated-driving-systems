## 3. 为什么这样切片

### 垂直切，不横着切

一个常见的错误拆法是按组件横切：「先写完所有 Dockerfile」→「再写完所有 SDF」→
「再写完所有 ROS 节点」。这样做的问题是**直到最后一步才知道能不能跑通**，
中间积累的假设全部未经验证。

本计划按**能力**竖着切：每个切片结束时，系统都比上一个切片多具备一项
**可以亲眼验证**的能力。

| 切片 | 结束时新增的能力 |
|------|----------------|
| S1 | 「我能在容器里跑起带图形界面的程序，而且是硬件加速的」 |
| S2 | 「我有一个能跑的仿真世界，里面的车能动」 |
| S3 | 「仿真数据以我定义的话题格式进了 ROS，RViz 能看见」 |
| S4 | 「我能用键盘把车开起来」——闭环成立 |
| S5 | 「这套东西别人 clone 下来能复现，改坏了 CI 会拦住」 |

### S1 必须是第一个，而且是 go/no-go 点

整个环境 A 方案建立在一个假设上：**容器内能拿到 WSL2 的 OpenGL 硬件加速**。

宿主机上已实测可用（SPEC §4 有 `glxinfo` 输出），但**容器内是另一回事**——
需要 `/dev/dri` 正确映射、容器内 Mesa 版本带 d3d12 驱动、WSLg 的 X11 socket 挂进去。
任何一环断了，Gazebo 要么起不来，要么退化成软件渲染（llvmpipe，帧率个位数）。

**所以 S1 不是「搭环境」，是「验证一个决定整个方案成立与否的假设」。**
它失败的话，S2-S5 全部作废，需要回到 SPEC §4.1 重新讨论环境 A。

## 4. 任务详拆

### S1　容器 + GPU + GUI【go/no-go】

| # | 任务 | 验收标准 | 验证方法 |
|---|------|---------|---------|
| 1.1 | 宿主机装 Docker | `docker run hello-world` 成功 | 命令返回 0 |
| 1.2 | 写 `docker/Dockerfile`：Ubuntu 24.04 + ROS 2 Jazzy desktop + mesa 工具 | 镜像构建成功 | `docker compose build` |
| 1.3 | 写 `docker/docker-compose.local.yml`：映射 `/dev/dri`、挂载 WSLg socket、传 `DISPLAY` | 容器能启动 | `docker compose up -d` |
| 1.4 | **验证容器内硬件加速** | `glxinfo -B` 输出 `Accelerated: yes` 且 Renderer 含 `D3D12` / `Radeon` | 容器内执行 |
| 1.5 | **验证容器内 GUI** | `rviz2` 能在 Windows 桌面弹出窗口且可交互 | 肉眼确认 |

**关键实现要点**（以下为 2026-07-30 实测后的定稿，前四条缺一不可）：

- 映射 **`/dev/dxg`** —— WSL2 的 GPU 通路是 dxgkrnl 的这个字符设备
- 映射 `/dev/dri`（`card0` + `renderD128`），并以数字 GID `group_add` 注入权限
- 设 **`GALLIUM_DRIVER=d3d12`** —— Ubuntu 24.04 的 Mesa 25.2.8 不会自动选中 d3d12
- 设 `LD_LIBRARY_PATH=/usr/lib/wsl/lib` —— `d3d12_dri.so` 用 dlopen 找 `libdxcore.so`
- WSLg 图形通路：挂载 `/tmp/.X11-unix`、`/mnt/wslg`、`/usr/lib/wsl`，
  设置 `DISPLAY`、`WAYLAND_DISPLAY`、`XDG_RUNTIME_DIR`
- 容器内需装 `mesa-utils`、`libgl1-mesa-dri`（提供 `d3d12_dri.so`）

**实测结果（S1 已完成）**：`D3D12 (AMD Radeon 780M Graphics)`，`Accelerated: yes`，
OpenGL core 4.6，`rviz2` 在 Windows 桌面弹窗且交互流畅。**CP1 通过。**

> **这一步的教训值得记住。** 前两条是排查 1.4 时才发现的——初版 compose 两条都缺，
> 结果是 `glxinfo` 报 `llvmpipe` / `Accelerated: no`，**而且没有任何报错信息**。
> 如果当初图省事跳过 1.4 直接做 S2，症状会变成「Gazebo 能起但帧率个位数」，
> 那时你面对的是 SDF 世界、物理引擎、传感器插件一大堆变量，
> 根本想不到根因在两个环境变量上。
>
> **1.4 的价值不在于它「通过了」，而在于它把故障拦在了变量最少的时刻。**

### S2　Gazebo 世界 + 车能动

| # | 任务 | 验收标准 | 验证方法 |
|---|------|---------|---------|
| 2.1 | Dockerfile 加装 `ros-jazzy-ros-gz`（官方组合，自动拉 Harmonic） | 构建成功 | `gz sim --versions` 显示 Harmonic |
| 2.2 | 最小世界 `worlds/campus_minimal.sdf`：地面 + 一段直路 + 若干静态方块障碍 | `gz sim` 能加载 | GUI 里可见 |
| 2.3 | 车辆模型 `models/ego_vehicle/`：车体 + 四轮 + `AckermannSteering` 插件 | 车出现在世界里 | GUI 里可见 |
| 2.4 | 车辆物理参数写入 `config/vehicle_params.yaml`（**单一来源**，SPEC §4.1 强制要求） | 轴距/最大转角/质量/加减速限值齐全且带单位 | 人工检查 |
| 2.5 | 用 gz 原生话题让车动起来 | 发布指令后车前进/转向 | `gz topic -t /model/ego/cmd_vel -m ... -p ...` |
| 2.6 | **测量实时率 RTF** | **RTF ≥ 0.8** | GUI 状态栏读数 |

> **2.6 是本切片的隐藏关键**。RTF（Real Time Factor）低于 0.8 意味着仿真比真实时间慢，
> 虽然同步模式下不影响正确性，但会严重拖慢你的迭代速度。若不达标，先简化世界几何
> （减面数、关阴影），而不是急着往下做。

**实测结果（S2 已完成）**：headless 纯物理 RTF = 1.000，带 GUI 渲染 RTF = 0.999。
直行 6 s 前进 15.478 m，转向 6 s 侧移 10.988 m。全部由 `scripts/verify_sim.sh` 自动验证。

**两处对计划的偏离，都是往严格的方向走：**

1. **`model.sdf` 改为从 YAML 生成**（`scripts/gen_vehicle_model.py`），不手写。
   SPEC §4.1 要求车辆参数单一来源，而手写 SDF 做不到——轴距一个数字在 SDF 里
   要出现四次以上（前后轮位置、插件的 `wheel_base`、车体盒偏移），改一处漏三处
   迟早发生，后果是车在两个仿真里开出不同轨迹，而你会去怀疑控制器。
   生成器带 `--check`，S5 的 CI 可直接用它卡住「改了 YAML 忘了重新生成」。
2. **RTF 用脚本测，不读 GUI 状态栏**。S3 加完激光雷达要再测一次，那时需要的是
   同样方法测出的可比数字，否则判断不出传感器拖了多少帧率。

> **一个比「车动了」更有价值的观察**：指令 3 m/s、YAML 里 `max_accel_mps2: 1.5`，
> 理论位移 = 加速段 3 m + 匀速段 12 m = 15 m，实测 15.478 m。
> 这说明 YAML 里的限值**真的传导到了模型里**，而不只是模型能跑。
> 验收标准写成可以和理论值对账的形式，比写「车能动」强得多。

> **3.4 是整个双环境方案的技术枢纽**。这里做的事是把 Gazebo 的原生话题名
> 翻译成 SPEC 定义的规范名。P0b 里 `carla_bridge` 做完全相同的翻译。
> **翻译层做对了，上游算法就永远不需要知道数据来自哪个仿真器。**

#### S3 实测结果（2026-07-30，`verify_ros_bridge.sh` 6/6 通过）

| 指标 | 实测 | 判据 |
|---|---|---|
| 规范话题 | 7 条齐全 | SPEC §4.1 |
| `/lidar/points` 频率 | **10.00 Hz**（仿真时间） | ≥ 9 Hz |
| `/lidar/points` 坐标系 | `base_link`，**Δz = +1.600 m** | frame_id 正确**且数值真的变了** |
| TF 树 | 5 段全通，外参逐位可核对 | 无断裂 |
| RTF（带激光雷达） | **0.998** | ≥ 0.8（S2 纯物理 1.000） |

**三处偏离计划，都是有意的**：

1. **3.1 只建 3 个包，不建 SPEC §5 的 12 个空壳。** 空包各要两个纯样板文件、
   拖慢构建，还会让 `src/` 看起来已经有一套栈。模块划分由 SPEC §5 定义，
   不靠空目录存在。用到哪个建哪个。

2. **3.5 的 `frame_id == base_link` 用「真的变换点」实现，不靠改标签。**
   雷达装在车顶，Gazebo 出的点在 `lidar_link` 系。在 SDF 里把 `gz_frame_id`
   直接写成 `base_link` 能让判据变绿，但那是**谎报坐标系** —— 每个点带着
   1.35/1.60 m 的固定偏移进下游，且不报任何错。所以链路是
   `/gazebo/lidar/points_raw`(lidar_link) → 变换节点 → `/lidar/points`(base_link)，
   并新增了 **Δz 判据**来证明数值真的变了。`carla_bridge` 之后做同样的事。

3. **额外产出 URDF，并补了 IMU / NavSat。** 3.7 的 TF 树和 3.8 的车模型都需要
   ROS 侧的机器人描述；手写 URDF 等于车辆参数写第二份，直接违反 SPEC §4.1，
   所以由同一个生成器从同一份 YAML 产出。`/gnss` 是 SPEC §4.1 列了而本表漏了的，
   成本很低顺手补上；`/ego_pose_gt` 未做，理由见 `todo.md` 待办。

**另追加一项（本表原本没有，经用户确认后做）：自车反射点滤除。**
CP2 通过后查点云 z 分布，发现 **34% 的点打在自己车顶上** —— 雷达 z=1.6、
车顶 z=1.5，只高 10 cm。物理上正确（真车也这样），但不滤的话 P5 感知会把
自车车顶当成零距离障碍物。已在 `lidar_preprocessor` 实现（坐标变换 + 自车滤除
+ 无效点滤除三合一，避免多一次 0.6 MB 的跨进程传递）。
实测有效点 29239 → 19365，自车盒内 0 点，频率仍 10.00 Hz。详见 `todo.md`。

> **最有价值的一条经验**见 `todo.md` 的「排查记录 1」：点云频率只有标称的 35%，
> 直觉判断是 GPU 渲不动，砍掉一半分辨率后只快了 4% —— 真正的病根是
> **best-effort QoS 下 1.8 MB 的消息在每一跳被队列静默丢弃**。
> **先分层测量再动参数**，否则会花力气解决一个不存在的问题。

#### S4 实测结果（4.1-4.3，`verify_teleop.sh` 3/3 通过）

| 指标 | 实测 | 判据 |
|---|---|---|
| 键盘 → `/vehicle_cmd` | 六项按键行为全对（含左转为正的符号约定） | pty 自动化 |
| 直行 | Δx = **+25.5 m** / 6 s | ≥ 10.8 m |
| 转向 | Δy = **+7.8 m** | ≥ 1 m 且方向为正 |
| 转角限幅 | 下发 10 rad → 输出 **0.600 rad** | ≤ 0.600 |
| 速度限幅 | 下发 100 m/s² → 输出 **7.44 m/s** | ≤ 8.333 |
| NaN 指令 | **被拒绝**，未污染下游 | 不得下发 |
| 看门狗 | 停发指令 6.3 s 后 8.333 → **0.000 m/s** | 必须自动刹停 |

**新增一个包 `ads_teleop`**（已同步进 SPEC §5）。teleop 发布的是规范话题
`/vehicle_cmd`，与仿真器无关，P0b 接 CARLA 时原样复用 ——
塞进 `gazebo_bridge` 就绑死在 Gazebo 上了。

**两处超出计划但必要的补充**：

1. **看门狗**。计划只要求限幅，但限幅挡不住"teleop 进程崩了/ssh 断了，
   车带着最后一条加速指令一直开下去"。这是安全逻辑，没有开关只有阈值。
2. **NaN 拒绝**。NaN 参与任何比较都返回 false，所以 `clamp` 会原样放行，
   一路传到物理引擎解算出 NaN 位姿，车直接从世界里消失。限幅代码里
   不显式判 `isfinite` 就等于没挡住。

> **最有价值的一条经验**见 `todo.md` 的「4.1 排查记录 2」：
> `termios` 的 `VMIN/VTIME` 非阻塞**只对终端生效**，`ros2 launch` 下
> stdin 是管道，`read()` 会永久阻塞并卡死整个节点 —— 而现象是
> "进程活着、publisher 也在、就是不发数据"，没有任何报错。
> 非阻塞 I/O 要靠 `O_NONBLOCK`，它对所有 fd 类型都管用。

P0a 的产出不是代码，是**一个可信的基准**：从此以后车开歪了，
你可以确信问题出在你的算法里。这个确信非常值钱。

## P1-1. 地图设计（已定，数值可直接抄进 YAML）

**拓扑：环线 + 一条横穿路 = 2 个 T 型路口。** 用户于 2026-07-31 从三个选项中选定。

```
        ╭───────────────╦───────────────╮   ← 上边直线 y=+50，x∈[-78,+78]
        │               ║               │
        │               ║               │
   R=12 │               ║ 横穿路 x=0     │ R=12      左右直线 x=±90，y∈[-38,+38]
        │               ║ y∈[-50,+50]   │
        │               ║               │
        ╰───────────────╩───────────────╯   ← 下边直线 y=-50
         ↑ 路口 J_top (0,+50)  ↑ 路口 J_bot (0,-50)
```

| 量 | 值 | 依据 |
|---|---|---|
| 环线中心线包络 | 180 m (x) × 100 m (y) | 园区尺度；50 m 雷达量程下不会「一眼看到全场」 |
| 四角转弯半径 | **R = 12 m** | 低速园区常规值。调小 → P2 的 Stanley 更难跟；调大 → 弯道变缓，测不出问题 |
| 环线周长 | **539.398 m** | 2×156 + 2×76 + 4×18.850（弧长 = π/2 × 12） |
| 横穿路长 | 100 m | 连通上下两条直线边 |
| 车道 | 双向各 1 条，**宽 3.5 m** | 与既有 `campus_minimal.sdf` 的 7 m 路面、±1.75 车道中心一致 |
| 通行方向 | **右侧通行** | OpenDRIVE 里 lane −1 沿 s 增大方向行驶，lane +1 逆向 |
| 路口转弯半径 | **R_j = 8 m** | 定义在**车道中心线**上 —— 那才是车实际走的轨迹 |
| 路口切除距离 | **d = 11 m（推导量）** | `d = R_j + 半车道 + 余量 = 8 + 1.75 + 1.25` |

> **`d` 是推导量而不是配置项。** 它必须 ≥ `R_j + 半车道`，否则转弯圆弧的切点会落到
> 路口区域**外面**，连接道路接不上。做成可配参数等于给人一个填错就崩的机会；
> 做成推导量，这个约束永远成立。（同一思路见 `vehicle_params.yaml` 的
> `length = wheelbase + 前后悬`。）
>
> **为什么下界是 `R_j + 半车道` 而不是 `R_j`**：`R_j` 定义在车道中心线上，
> 而 OpenDRIVE 的圆弧画在**参考线**上，两者差半个车道。右转时参考线在车道中心
> 外侧，半径要加半车道 → `R_ref = 9.75`，切点最远，`d` 必须容得下它。

**道路划分**（OpenDRIVE 的 road 必须在路口处断开）：

| road | 组成 | 长度 |
|---|---|---|
| `loop_east` | 直 67 + 弧 18.850 + 直 76 + 弧 18.850 + 直 67 | 247.699 m |
| `loop_west` | 同上镜像 | 247.699 m |
| `cross` | 直线 | 78 m（100 − 2×11） |
| 连接道路 | 每个 T 路口 6 条（直行×2 + 转弯×4），共 **12 条** | 直行 22.000 m；左转 19.317 m、右转 17.815 m |

> **长度自洽校验**：247.699×2 + 22×2（两个路口的直行段） = **539.398 m** = 环线周长 ✓
> 这个校验已写进生成器的 pytest —— 它能抓住「圆弧接续算错了半径」这类错误，
> 因为算错了周长就对不上，而单看某一段几何是看不出来的。
>
> ⚠️ 上面这一整张表的数字都是 **2026-07-31 生成器的实测输出**，不是估算。
> 规划时按 `d = 10` 估过一版（环线道路 249.700 m），把 `d` 改成推导量后全部变了。

**为什么这个拓扑值得多花 150 行生成器代码**（对比「直路 + 一个 T」）：

- **路由才有东西可算**：A→B 有 4 条以上候选路径，Dijkstra 是在**比较代价**。
  只有一条路的话，「最短路」这个结果无法证明算法对 —— 它连错都错不了。
- **P2 才测得出控制器**：4 个 R=12 m 弯道是 Stanley 的真实考验。
  **直路上任何横向控制器看起来都是对的**，包括写错符号的那种。
- **P4 有可量化的定位指标**：绕环一圈回到起点，终点与起点的偏差就是累积漂移。

## P1-2. 数据来源与生成链（本阶段最重要的架构决定）

用户于 2026-07-31 选定：**YAML 是源头，`.xodr` 和 Gazebo 世界都是生成物。**

```
config/campus_map.yaml              ← 唯一手写的源头（路段 + 路口的紧凑描述）
        │
        │  scripts/gen_map.py
        ├────────▶ maps/campus.xodr             生成物① —— 两环境共用（SPEC §4.1 强制）
        │                 ├──▶ ads_map 解析 → 车道图 → 路由
        │                 └──▶ CARLA: generate_opendrive_world()（P0b，届时实测确认）
        │
        └────────▶ models/campus_road/model.sdf  生成物② —— Gazebo 侧道路可视
                          └──▶ worlds/campus_loop.sdf 用 <include> 引用
```

**这和 `config/vehicle_params.yaml → gen_vehicle_model.py → SDF + URDF` 是同一套结构**，
不是巧合：两者防的是同一类 bug。车辆参数那次防的是「Gazebo 的车和 RViz 的车不一样」，
这次防的是「`ads_map` 认为的车道」和「你在 Gazebo 里看到的路」不一样。

后者的症状特别隐蔽：**路由算得出来、RViz 画得出来、车也开得动，
但车沿着一条肉眼看不见的车道压着绿化带走**，而所有模块都不报错。

**为什么不手写 `.xodr`**：路口的连接道路要手工算圆弧的起点/终点/曲率并手填
`laneLink`。一个数填错的症状恰恰就是上面那条 —— 而且它只在**经过那个路口时**发作。
让程序算，是因为程序算错会**每次都错**，而每次都错的东西测得出来。

**为什么世界骨架仍然手写**：`worlds/campus_loop.sdf` 里的物理、插件、光照、自车
`<include>` 是人要改的东西（P3 还要往里加障碍物）。只把**道路几何**这一块
生成到 `models/campus_road/`，与 `models/ego_vehicle/` 完全对称。

**两个硬约束，写在这里免得后面忘**：

1. `campus_loop.sdf` 的 `<spherical_coordinates>` 必须与 `campus_minimal.sdf`
   **逐字相同**（31.230416, 121.473701, elev 10.0, ENU）。不同的话，两个世界里
   同一个 x/y 对应不同经纬度，P4 拿 GNSS 做定位时结果无法互比。
2. `maps/campus.xodr` 的 `<geoReference>` 必须编码**同一个**原点。
   OpenDRIVE 的 (0,0) = Gazebo 世界原点 = ROS `map` 系原点，三者重合。

**`campus_minimal.sdf` 保持不动。** 它是 `verify_sim.sh` / `verify_ros_bridge.sh` /
`verify_teleop.sh` 三个脚本的回归基线（RTF 0.970、点云 10.00 Hz 等实测值都基于它）。
改了它，那些数字全部作废，而它们是我们判断「环境有没有退化」的唯一依据。

| 切片 | 结束时新增的能力 |
|------|----------------|
| S1 | 「我有一份带 2 个路口的 OpenDRIVE 地图，和与之几何一致的 Gazebo 世界，且两者都是生成物」 |
| S2 | 「C++ 能把 `.xodr` 求值成世界坐标，而且有两套独立实现互相印证」 |
| S3 | 「给定起终点，我能算出一条**车道级**路径，且它不会让车逆行」 |
| S4 | 「RViz 里能看到车道图，点一个目标点就出全局路径」← **SPEC 的 P1 验收** |
| S5 | 「数学推导写下来了，地图改坏了 CI 会拦住」 |

### 为什么 S2 的检查点是「双实现互证」而不是「测试通过」

S1 的 Python 生成器和 S2 的 C++ 解析器，对同一段圆弧**各算一遍世界坐标**。
它们是两套独立实现，如果对 OpenDRIVE 的圆弧约定理解不一致（比如曲率符号、
起始朝向的定义），**两边各自的单元测试都会通过**，因为各自都自洽。

抓这种 bug 的唯一办法是让两边的输出直接对账：生成器导出一份车道中心线采样点，
C++ 测试读同一份 `.xodr` 求值，逐点比对，**偏差 > 1 mm 即失败**。

不做这个对账的话，症状要等到 P2 才出现 —— 车沿路径开偏了，
而你第一反应一定是去调 Stanley 的增益。**那时候你调的是一个正确的控制器。**

| # | 任务 | 验收标准 | 验证方法 |

#### S3 实测结果（2026-08-01，`colcon test-result --all` 241 / 0 failures）

| 项 | 实测值 | 判据 |
|---|---|---|
| 车道图规模 | **18 节点 / 24 边** | 手数一致：3 条常规路 × 双向 + 12 条连接路；6 × 2 + 12 × 1 |
| 每条边的几何断裂 | **4.0e-7 mm / 9.8e-12 rad** | < 1 µm / 1e-8 rad |
| 转弯车道中心线半径 | **8.000000 m**（8 条转弯连接道路全部） | = `campus_map.yaml` 的 `turn_radius_m` |
| 掉头边 | **0 条** | 必须为 0 |
| 对向车道最短路 | **674.732 m** | ≫ 3.5 m（无向图会给约 0 m） |
| 27 个新用例耗时 | **5 ms** | L1 要保持毫秒级 |

**3.4 的验收标准在执行时做了调整，理由要记下来**：计划写的是「逆行请求返回失败」，
但**本地图上不存在会失败的逆行请求** —— 两个 T 型路口把 6 条常规车道连成了强连通图，
任何一对起终点都可达，只是要绕。于是拆成两种形态验收：合成的断头路地图上
「目标在身后」确实返回 `nullopt`；真实地图上从一条车道到它对向车道的最短路是
674.73 m 而不是 ≈0 m。**后者比前者有分量** —— 无向图给出的那条 3.5 m「路径」
在 RViz 里是一条平滑的短线，长度也合理，肉眼永远看不出问题。

**一个计划里没预见到的坑：路由代价用参考线长度会让两条候选路线恰好并列。**
从东侧顺行车道到它的对向车道有两条候选（借横穿路兜回来 / 绕整圈）：
用车道中心线长度算是 674.73 vs 685.73，赢家唯一；用参考线长度算**两条都是 680.23 m**，
因为它们用到的参考线长度是同一个多重集，只是分配不同。并列的后果不是「算错」，
而是**返回哪条取决于堆的遍历顺序**，换个标准库实现就可能变。
所以 `Road::lane_arc_length()` 是必需的而不是精细化 —— R=12 的弯上，
右侧车道半径 13.75 m，与参考线差 14.6%。

#### S4 挖出一个 P0a 遗留的真 bug：`map → odom` 不该是单位变换

Gazebo 的 `AckermannSteering` 把 `odom` 原点放在**自车 spawn 的位置**，
所以这一段的正确取值是「自车 spawn 位姿在世界里的坐标」。P0a 一直发单位变换，
而 `campus_minimal.sdf` 里自车在 `(0, −1.75)` 几乎就是原点，从没露过马脚 ——
那个世界里没有任何东西依赖世界坐标。

换到 `campus_loop.sdf`（自车在 `(30, −51.75)`）症状立刻出来：**TF 报自车在
`map` 系的 `(0, 0)`，而它 physically 在 `(30, −51.75)`，差 60 m。**
于是全局路径从园区正中央的草地上出发，而它在 RViz 里是一条平滑正常的线。

修法是让 `gazebo_sim.launch.py` **从世界文件里读** spawn 位姿（不写死，否则
换个世界忘了改就又中招），节点名同步改成 `map_to_odom_static`。
改完 `verify_ros_bridge.sh` 6/6（RTF 1.002）、`verify_teleop.sh` 3/3，无回归。

> 这个 bug 的形状值得记住：**一个错误的默认值，被一个恰好让它成立的场景掩盖了整个 P0a。**
> 它不是被测试抓到的，是被「换了一个真实的地图」抓到的。

## 3. 为什么这样切片

### 垂直切，不横着切

一个常见的错误拆法是按组件横切：「先写完所有 Dockerfile」→「再写完所有 SDF」→
「再写完所有 ROS 节点」。这样做的问题是**直到最后一步才知道能不能跑通**，
中间积累的假设全部未经验证。

本计划按**能力**竖着切：每个切片结束时，系统都比上一个切片多具备一项
**可以亲眼验证**的能力。

| 切片 | 结束时新增的能力 |
|------|----------------|
| S1 | 「我能在容器里跑起带图形界面的程序，而且是硬件加速的」 |
| S2 | 「我有一个能跑的仿真世界，里面的车能动」 |
| S3 | 「仿真数据以我定义的话题格式进了 ROS，RViz 能看见」 |
| S4 | 「我能用键盘把车开起来」——闭环成立 |
| S5 | 「这套东西别人 clone 下来能复现，改坏了 CI 会拦住」 |

### S1 必须是第一个，而且是 go/no-go 点

整个环境 A 方案建立在一个假设上：**容器内能拿到 WSL2 的 OpenGL 硬件加速**。

宿主机上已实测可用（SPEC §4 有 `glxinfo` 输出），但**容器内是另一回事**——
需要 `/dev/dri` 正确映射、容器内 Mesa 版本带 d3d12 驱动、WSLg 的 X11 socket 挂进去。
任何一环断了，Gazebo 要么起不来，要么退化成软件渲染（llvmpipe，帧率个位数）。

**所以 S1 不是「搭环境」，是「验证一个决定整个方案成立与否的假设」。**
它失败的话，S2-S5 全部作废，需要回到 SPEC §4.1 重新讨论环境 A。

## 4. 任务详拆

### S1　容器 + GPU + GUI【go/no-go】

| # | 任务 | 验收标准 | 验证方法 |
|---|------|---------|---------|
| 1.1 | 宿主机装 Docker | `docker run hello-world` 成功 | 命令返回 0 |
| 1.2 | 写 `docker/Dockerfile`：Ubuntu 24.04 + ROS 2 Jazzy desktop + mesa 工具 | 镜像构建成功 | `docker compose build` |
| 1.3 | 写 `docker/docker-compose.local.yml`：映射 `/dev/dri`、挂载 WSLg socket、传 `DISPLAY` | 容器能启动 | `docker compose up -d` |
| 1.4 | **验证容器内硬件加速** | `glxinfo -B` 输出 `Accelerated: yes` 且 Renderer 含 `D3D12` / `Radeon` | 容器内执行 |
| 1.5 | **验证容器内 GUI** | `rviz2` 能在 Windows 桌面弹出窗口且可交互 | 肉眼确认 |

**关键实现要点**（以下为 2026-07-30 实测后的定稿，前四条缺一不可）：

- 映射 **`/dev/dxg`** —— WSL2 的 GPU 通路是 dxgkrnl 的这个字符设备
- 映射 `/dev/dri`（`card0` + `renderD128`），并以数字 GID `group_add` 注入权限
- 设 **`GALLIUM_DRIVER=d3d12`** —— Ubuntu 24.04 的 Mesa 25.2.8 不会自动选中 d3d12
- 设 `LD_LIBRARY_PATH=/usr/lib/wsl/lib` —— `d3d12_dri.so` 用 dlopen 找 `libdxcore.so`
- WSLg 图形通路：挂载 `/tmp/.X11-unix`、`/mnt/wslg`、`/usr/lib/wsl`，
  设置 `DISPLAY`、`WAYLAND_DISPLAY`、`XDG_RUNTIME_DIR`
- 容器内需装 `mesa-utils`、`libgl1-mesa-dri`（提供 `d3d12_dri.so`）

**实测结果（S1 已完成）**：`D3D12 (AMD Radeon 780M Graphics)`，`Accelerated: yes`，
OpenGL core 4.6，`rviz2` 在 Windows 桌面弹窗且交互流畅。**CP1 通过。**

> **这一步的教训值得记住。** 前两条是排查 1.4 时才发现的——初版 compose 两条都缺，
> 结果是 `glxinfo` 报 `llvmpipe` / `Accelerated: no`，**而且没有任何报错信息**。
> 如果当初图省事跳过 1.4 直接做 S2，症状会变成「Gazebo 能起但帧率个位数」，
> 那时你面对的是 SDF 世界、物理引擎、传感器插件一大堆变量，
> 根本想不到根因在两个环境变量上。
>
> **1.4 的价值不在于它「通过了」，而在于它把故障拦在了变量最少的时刻。**

### S2　Gazebo 世界 + 车能动

| # | 任务 | 验收标准 | 验证方法 |
|---|------|---------|---------|
| 2.1 | Dockerfile 加装 `ros-jazzy-ros-gz`（官方组合，自动拉 Harmonic） | 构建成功 | `gz sim --versions` 显示 Harmonic |
| 2.2 | 最小世界 `worlds/campus_minimal.sdf`：地面 + 一段直路 + 若干静态方块障碍 | `gz sim` 能加载 | GUI 里可见 |
| 2.3 | 车辆模型 `models/ego_vehicle/`：车体 + 四轮 + `AckermannSteering` 插件 | 车出现在世界里 | GUI 里可见 |
| 2.4 | 车辆物理参数写入 `config/vehicle_params.yaml`（**单一来源**，SPEC §4.1 强制要求） | 轴距/最大转角/质量/加减速限值齐全且带单位 | 人工检查 |
| 2.5 | 用 gz 原生话题让车动起来 | 发布指令后车前进/转向 | `gz topic -t /model/ego/cmd_vel -m ... -p ...` |
| 2.6 | **测量实时率 RTF** | **RTF ≥ 0.8** | GUI 状态栏读数 |

> **2.6 是本切片的隐藏关键**。RTF（Real Time Factor）低于 0.8 意味着仿真比真实时间慢，
> 虽然同步模式下不影响正确性，但会严重拖慢你的迭代速度。若不达标，先简化世界几何
> （减面数、关阴影），而不是急着往下做。

**实测结果（S2 已完成）**：headless 纯物理 RTF = 1.000，带 GUI 渲染 RTF = 0.999。
直行 6 s 前进 15.478 m，转向 6 s 侧移 10.988 m。全部由 `scripts/verify_sim.sh` 自动验证。

**两处对计划的偏离，都是往严格的方向走：**

1. **`model.sdf` 改为从 YAML 生成**（`scripts/gen_vehicle_model.py`），不手写。
   SPEC §4.1 要求车辆参数单一来源，而手写 SDF 做不到——轴距一个数字在 SDF 里
   要出现四次以上（前后轮位置、插件的 `wheel_base`、车体盒偏移），改一处漏三处
   迟早发生，后果是车在两个仿真里开出不同轨迹，而你会去怀疑控制器。
   生成器带 `--check`，S5 的 CI 可直接用它卡住「改了 YAML 忘了重新生成」。
2. **RTF 用脚本测，不读 GUI 状态栏**。S3 加完激光雷达要再测一次，那时需要的是
   同样方法测出的可比数字，否则判断不出传感器拖了多少帧率。

> **一个比「车动了」更有价值的观察**：指令 3 m/s、YAML 里 `max_accel_mps2: 1.5`，
> 理论位移 = 加速段 3 m + 匀速段 12 m = 15 m，实测 15.478 m。
> 这说明 YAML 里的限值**真的传导到了模型里**，而不只是模型能跑。
> 验收标准写成可以和理论值对账的形式，比写「车能动」强得多。

> **3.4 是整个双环境方案的技术枢纽**。这里做的事是把 Gazebo 的原生话题名

> **翻译层做对了，上游算法就永远不需要知道数据来自哪个仿真器。**

#### S3 实测结果（2026-07-30，`verify_ros_bridge.sh` 6/6 通过）

| 指标 | 实测 | 判据 |
|---|---|---|
| 规范话题 | 7 条齐全 | SPEC §4.1 |
| `/lidar/points` 频率 | **10.00 Hz**（仿真时间） | ≥ 9 Hz |
| `/lidar/points` 坐标系 | `base_link`，**Δz = +1.600 m** | frame_id 正确**且数值真的变了** |
| TF 树 | 5 段全通，外参逐位可核对 | 无断裂 |
| RTF（带激光雷达） | **0.998** | ≥ 0.8（S2 纯物理 1.000） |

**三处偏离计划，都是有意的**：

1. **3.1 只建 3 个包，不建 SPEC §5 的 12 个空壳。** 空包各要两个纯样板文件、
   拖慢构建，还会让 `src/` 看起来已经有一套栈。模块划分由 SPEC §5 定义，
   不靠空目录存在。用到哪个建哪个。

2. **3.5 的 `frame_id == base_link` 用「真的变换点」实现，不靠改标签。**
   雷达装在车顶，Gazebo 出的点在 `lidar_link` 系。在 SDF 里把 `gz_frame_id`
   直接写成 `base_link` 能让判据变绿，但那是**谎报坐标系** —— 每个点带着
   1.35/1.60 m 的固定偏移进下游，且不报任何错。所以链路是
   `/gazebo/lidar/points_raw`(lidar_link) → 变换节点 → `/lidar/points`(base_link)，
   并新增了 **Δz 判据**来证明数值真的变了。`carla_bridge` 之后做同样的事。

3. **额外产出 URDF，并补了 IMU / NavSat。** 3.7 的 TF 树和 3.8 的车模型都需要
   ROS 侧的机器人描述；手写 URDF 等于车辆参数写第二份，直接违反 SPEC §4.1，
   所以由同一个生成器从同一份 YAML 产出。`/gnss` 是 SPEC §4.1 列了而本表漏了的，
   成本很低顺手补上；`/ego_pose_gt` 未做，理由见 `todo.md` 待办。

**另追加一项（本表原本没有，经用户确认后做）：自车反射点滤除。**
CP2 通过后查点云 z 分布，发现 **34% 的点打在自己车顶上** —— 雷达 z=1.6、
车顶 z=1.5，只高 10 cm。物理上正确（真车也这样），但不滤的话 P5 感知会把
自车车顶当成零距离障碍物。已在 `lidar_preprocessor` 实现（坐标变换 + 自车滤除
+ 无效点滤除三合一，避免多一次 0.6 MB 的跨进程传递）。
实测有效点 29239 → 19365，自车盒内 0 点，频率仍 10.00 Hz。详见 `todo.md`。

> **最有价值的一条经验**见 `todo.md` 的「排查记录 1」：点云频率只有标称的 35%，
> 直觉判断是 GPU 渲不动，砍掉一半分辨率后只快了 4% —— 真正的病根是
> **best-effort QoS 下 1.8 MB 的消息在每一跳被队列静默丢弃**。
> **先分层测量再动参数**，否则会花力气解决一个不存在的问题。

#### S4 实测结果（4.1-4.3，`verify_teleop.sh` 3/3 通过）

| 指标 | 实测 | 判据 |
|---|---|---|
| 键盘 → `/vehicle_cmd` | 六项按键行为全对（含左转为正的符号约定） | pty 自动化 |
| 直行 | Δx = **+25.5 m** / 6 s | ≥ 10.8 m |
| 转向 | Δy = **+7.8 m** | ≥ 1 m 且方向为正 |
| 转角限幅 | 下发 10 rad → 输出 **0.600 rad** | ≤ 0.600 |
| 速度限幅 | 下发 100 m/s² → 输出 **7.44 m/s** | ≤ 8.333 |
| NaN 指令 | **被拒绝**，未污染下游 | 不得下发 |
| 看门狗 | 停发指令 6.3 s 后 8.333 → **0.000 m/s** | 必须自动刹停 |

**新增一个包 `ads_teleop`**（已同步进 SPEC §5）。teleop 发布的是规范话题
`/vehicle_cmd`，与仿真器无关，P0b 接 CARLA 时原样复用 ——
塞进 `gazebo_bridge` 就绑死在 Gazebo 上了。

**两处超出计划但必要的补充**：

1. **看门狗**。计划只要求限幅，但限幅挡不住"teleop 进程崩了/ssh 断了，
   车带着最后一条加速指令一直开下去"。这是安全逻辑，没有开关只有阈值。
2. **NaN 拒绝**。NaN 参与任何比较都返回 false，所以 `clamp` 会原样放行，
   一路传到物理引擎解算出 NaN 位姿，车直接从世界里消失。限幅代码里
   不显式判 `isfinite` 就等于没挡住。

> **最有价值的一条经验**见 `todo.md` 的「4.1 排查记录 2」：
> `termios` 的 `VMIN/VTIME` 非阻塞**只对终端生效**，`ros2 launch` 下
> stdin 是管道，`read()` 会永久阻塞并卡死整个节点 —— 而现象是
> "进程活着、publisher 也在、就是不发数据"，没有任何报错。
> 非阻塞 I/O 要靠 `O_NONBLOCK`，它对所有 fd 类型都管用。

## P1-1. 地图设计（已定，数值可直接抄进 YAML）

**拓扑：环线 + 一条横穿路 = 2 个 T 型路口。** 用户于 2026-07-31 从三个选项中选定。

```
        ╭───────────────╦───────────────╮   ← 上边直线 y=+50，x∈[-78,+78]
        │               ║               │
        │               ║               │
   R=12 │               ║ 横穿路 x=0     │ R=12      左右直线 x=±90，y∈[-38,+38]
        │               ║ y∈[-50,+50]   │
        │               ║               │
        ╰───────────────╩───────────────╯   ← 下边直线 y=-50
         ↑ 路口 J_top (0,+50)  ↑ 路口 J_bot (0,-50)
```

| 量 | 值 | 依据 |
|---|---|---|
| 环线中心线包络 | 180 m (x) × 100 m (y) | 园区尺度；50 m 雷达量程下不会「一眼看到全场」 |
| 四角转弯半径 | **R = 12 m** | 低速园区常规值。调小 → P2 的 Stanley 更难跟；调大 → 弯道变缓，测不出问题 |
| 环线周长 | **539.398 m** | 2×156 + 2×76 + 4×18.850（弧长 = π/2 × 12） |
| 横穿路长 | 100 m | 连通上下两条直线边 |
| 车道 | 双向各 1 条，**宽 3.5 m** | 与既有 `campus_minimal.sdf` 的 7 m 路面、±1.75 车道中心一致 |
| 通行方向 | **右侧通行** | OpenDRIVE 里 lane −1 沿 s 增大方向行驶，lane +1 逆向 |
| 路口转弯半径 | **R_j = 8 m** | 定义在**车道中心线**上 —— 那才是车实际走的轨迹 |
| 路口切除距离 | **d = 11 m（推导量）** | `d = R_j + 半车道 + 余量 = 8 + 1.75 + 1.25` |

> **`d` 是推导量而不是配置项。** 它必须 ≥ `R_j + 半车道`，否则转弯圆弧的切点会落到
> 路口区域**外面**，连接道路接不上。做成可配参数等于给人一个填错就崩的机会；
> 做成推导量，这个约束永远成立。（同一思路见 `vehicle_params.yaml` 的
> `length = wheelbase + 前后悬`。）
>
> **为什么下界是 `R_j + 半车道` 而不是 `R_j`**：`R_j` 定义在车道中心线上，
> 而 OpenDRIVE 的圆弧画在**参考线**上，两者差半个车道。右转时参考线在车道中心
> 外侧，半径要加半车道 → `R_ref = 9.75`，切点最远，`d` 必须容得下它。

**道路划分**（OpenDRIVE 的 road 必须在路口处断开）：

| road | 组成 | 长度 |
|---|---|---|
| `loop_east` | 直 67 + 弧 18.850 + 直 76 + 弧 18.850 + 直 67 | 247.699 m |
| `loop_west` | 同上镜像 | 247.699 m |
| `cross` | 直线 | 78 m（100 − 2×11） |
| 连接道路 | 每个 T 路口 6 条（直行×2 + 转弯×4），共 **12 条** | 直行 22.000 m；左转 19.317 m、右转 17.815 m |

> **长度自洽校验**：247.699×2 + 22×2（两个路口的直行段） = **539.398 m** = 环线周长 ✓
> 这个校验已写进生成器的 pytest —— 它能抓住「圆弧接续算错了半径」这类错误，
> 因为算错了周长就对不上，而单看某一段几何是看不出来的。
>
> ⚠️ 上面这一整张表的数字都是 **2026-07-31 生成器的实测输出**，不是估算。
> 规划时按 `d = 10` 估过一版（环线道路 249.700 m），把 `d` 改成推导量后全部变了。

**为什么这个拓扑值得多花 150 行生成器代码**（对比「直路 + 一个 T」）：

- **路由才有东西可算**：A→B 有 4 条以上候选路径，Dijkstra 是在**比较代价**。
  只有一条路的话，「最短路」这个结果无法证明算法对 —— 它连错都错不了。
- **P2 才测得出控制器**：4 个 R=12 m 弯道是 Stanley 的真实考验。
  **直路上任何横向控制器看起来都是对的**，包括写错符号的那种。
- **P4 有可量化的定位指标**：绕环一圈回到起点，终点与起点的偏差就是累积漂移。

## P1-2. 数据来源与生成链（本阶段最重要的架构决定）

用户于 2026-07-31 选定：**YAML 是源头，`.xodr` 和 Gazebo 世界都是生成物。**

```
config/campus_map.yaml              ← 唯一手写的源头（路段 + 路口的紧凑描述）
        │
        │  scripts/gen_map.py
        ├────────▶ maps/campus.xodr             生成物① —— 两环境共用（SPEC §4.1 强制）
        │                 ├──▶ ads_map 解析 → 车道图 → 路由
        │                 └──▶ CARLA: generate_opendrive_world()（P0b，届时实测确认）
        │
        └────────▶ models/campus_road/model.sdf  生成物② —— Gazebo 侧道路可视
                          └──▶ worlds/campus_loop.sdf 用 <include> 引用
```

**这和 `config/vehicle_params.yaml → gen_vehicle_model.py → SDF + URDF` 是同一套结构**，
不是巧合：两者防的是同一类 bug。车辆参数那次防的是「Gazebo 的车和 RViz 的车不一样」，
这次防的是「`ads_map` 认为的车道」和「你在 Gazebo 里看到的路」不一样。

后者的症状特别隐蔽：**路由算得出来、RViz 画得出来、车也开得动，
但车沿着一条肉眼看不见的车道压着绿化带走**，而所有模块都不报错。

**为什么不手写 `.xodr`**：路口的连接道路要手工算圆弧的起点/终点/曲率并手填
`laneLink`。一个数填错的症状恰恰就是上面那条 —— 而且它只在**经过那个路口时**发作。
让程序算，是因为程序算错会**每次都错**，而每次都错的东西测得出来。

**为什么世界骨架仍然手写**：`worlds/campus_loop.sdf` 里的物理、插件、光照、自车
`<include>` 是人要改的东西（P3 还要往里加障碍物）。只把**道路几何**这一块
生成到 `models/campus_road/`，与 `models/ego_vehicle/` 完全对称。

**两个硬约束，写在这里免得后面忘**：

1. `campus_loop.sdf` 的 `<spherical_coordinates>` 必须与 `campus_minimal.sdf`
   **逐字相同**（31.230416, 121.473701, elev 10.0, ENU）。不同的话，两个世界里
   同一个 x/y 对应不同经纬度，P4 拿 GNSS 做定位时结果无法互比。
2. `maps/campus.xodr` 的 `<geoReference>` 必须编码**同一个**原点。
   OpenDRIVE 的 (0,0) = Gazebo 世界原点 = ROS `map` 系原点，三者重合。

**`campus_minimal.sdf` 保持不动。** 它是 `verify_sim.sh` / `verify_ros_bridge.sh` /
`verify_teleop.sh` 三个脚本的回归基线（RTF 0.970、点云 10.00 Hz 等实测值都基于它）。
改了它，那些数字全部作废，而它们是我们判断「环境有没有退化」的唯一依据。

| S5 | 「数学推导写下来了，地图改坏了 CI 会拦住」 |

### 为什么 S2 的检查点是「双实现互证」而不是「测试通过」

S1 的 Python 生成器和 S2 的 C++ 解析器，对同一段圆弧**各算一遍世界坐标**。
它们是两套独立实现，如果对 OpenDRIVE 的圆弧约定理解不一致（比如曲率符号、
起始朝向的定义），**两边各自的单元测试都会通过**，因为各自都自洽。

抓这种 bug 的唯一办法是让两边的输出直接对账：生成器导出一份车道中心线采样点，
C++ 测试读同一份 `.xodr` 求值，逐点比对，**偏差 > 1 mm 即失败**。

不做这个对账的话，症状要等到 P2 才出现 —— 车沿路径开偏了，
而你第一反应一定是去调 Stanley 的增益。**那时候你调的是一个正确的控制器。**

#### S3 实测结果（2026-08-01，`colcon test-result --all` 241 / 0 failures）

| 项 | 实测值 | 判据 |
|---|---|---|
| 车道图规模 | **18 节点 / 24 边** | 手数一致：3 条常规路 × 双向 + 12 条连接路；6 × 2 + 12 × 1 |

| 掉头边 | **0 条** | 必须为 0 |
| 对向车道最短路 | **674.732 m** | ≫ 3.5 m（无向图会给约 0 m） |
| 27 个新用例耗时 | **5 ms** | L1 要保持毫秒级 |

**3.4 的验收标准在执行时做了调整，理由要记下来**：计划写的是「逆行请求返回失败」，
但**本地图上不存在会失败的逆行请求** —— 两个 T 型路口把 6 条常规车道连成了强连通图，
任何一对起终点都可达，只是要绕。于是拆成两种形态验收：合成的断头路地图上
「目标在身后」确实返回 `nullopt`；真实地图上从一条车道到它对向车道的最短路是
674.73 m 而不是 ≈0 m。**后者比前者有分量** —— 无向图给出的那条 3.5 m「路径」
在 RViz 里是一条平滑的短线，长度也合理，肉眼永远看不出问题。

**一个计划里没预见到的坑：路由代价用参考线长度会让两条候选路线恰好并列。**
从东侧顺行车道到它的对向车道有两条候选（借横穿路兜回来 / 绕整圈）：
用车道中心线长度算是 674.73 vs 685.73，赢家唯一；用参考线长度算**两条都是 680.23 m**，
因为它们用到的参考线长度是同一个多重集，只是分配不同。并列的后果不是「算错」，
而是**返回哪条取决于堆的遍历顺序**，换个标准库实现就可能变。
所以 `Road::lane_arc_length()` 是必需的而不是精细化 —— R=12 的弯上，
右侧车道半径 13.75 m，与参考线差 14.6%。

## P2-1. 两个已拍板的决策（2026-08-01，用户确认）

### 决策一：纵向只做速度环，不做加速度内环

SPEC §3.2 写的是「纵向双闭环 PID（速度环 + 加速度环）」。**P2 只实现外环**，
并在 SPEC §3.2 加一条脚注说明成立条件。

**为什么内环此刻没有可闭合的对象**：加速度环存在的意义是补偿执行器的非理想性 ——
真车上同一个油门开度在不同车速、坡度、载荷下产生不同的加速度，所以要拿实测加速度
反过来修正开度。而当前链路是

```
控制器 ──a_cmd──▶ bridge: v_setpoint += a_cmd·dt ──▶ Gazebo AckermannSteering
```

「指令加速度 → 实际加速度」这一段几乎是**理想积分器**：没有发动机延迟，没有制动
响应时间。对一个恒等环节再套一个 PI 去闭合它，只会引入震荡和一堆没有物理依据的增益。
更糟的是加速度反馈只能取 `/imu`（带噪声）或微分 `/odom`（噪声更大）——
**为了补偿一个不存在的误差，引入一个真实存在的噪声。**

**这个决定的有效期**：接实车或 CARLA 的执行器模型时内环就有对象了，届时补上。
脚注要把这个条件写死，否则将来有人看到 SPEC 说双闭环、代码只有一环，
第一反应会是「实现漏了」而不是「条件不成立」。

### 决策二：做曲率限速 + 终点减速的速度规划

不是精细化，在**这张地图上有具体后果**。`cruise_speed_mps = 5.556`（20 km/h），
横向加速度 a = v²/R：

| 位置 | 车道中心线半径 | 定速 20 km/h 时 | a ≤ 1.5 时的限速 |
|---|---|---|---|
| 路口转弯车道 | **8.00 m** | **3.86 m/s²** | 3.464 m/s（12.5 km/h） |
| 环线四角内侧 | 10.25 m | 3.01 m/s² | 3.921 m/s（14.1 km/h） |
| 环线四角外侧 | 13.75 m | 2.25 m/s² | 4.542 m/s（16.3 km/h） |
| 直路 | ∞ | 0 | 5.556 m/s（巡航值） |

舒适横向加速度一般 1.5–2.0 m/s²，**3.86 是紧急变道级别**。

> ⚠️ **2026-08-01 更正（S1.1 的数值仿真推翻了本条初稿的论据）**：
> 初稿写的是「定速跑过路口，车会飘出车道、Stanley 硬拽回来、于是震荡」。
> **仿真不支持这个说法** —— 运动学模型下定速 5.556 过 R=8 弯，入弯峰值横向
> 误差只有 **0.0716 m**，全程平稳。**运动学自行车模型里没有轮胎，
> 不存在"飘出去"这回事。**
>
> 决策不变（仍做曲率限速），但真正的理由是：**① 舒适性**（3.86 m/s² 的侧向力，
> 园区接驳车上站着的人扶不住，是 ODD 要求）；**② 真车/CARLA 的裕度**
> （运动学模型不含侧偏，真车在这个量级下前轮侧偏角可观 —— 在一个不会侧偏的
> 模型上把速度定到需要靠轮胎抓地才能过的量级，正是制造 SPEC §12 头号风险
> 「行为漂移」的做法）；**③ 跟踪精度**（峰值误差 4.3 倍，但绝对值都很小，
> 是最次要的理由）。
>
> 记下这条是因为：**拿一个仿真里根本不会发生的症状去论证一个正确的决定**，
> 下一个人会照着它去 Gazebo 里找"震荡"，找不到，然后开始怀疑别的地方。

另外**路径末端必须减速到 0**：从 5.556 按舒适减速度 −1.5 停下要 **10.29 m**，
按 −3.0 要 **5.14 m**。不做的话车开过终点，Stanley 找不到前方点，行为未定义。

**边界**：P2 的速度规划是**纯几何**的（只看曲率和终点），不含避障、不含跟车、
不含地图限速。P3 的 Frenet 规划器接管后，这一层退化成兜底。文档要写明这个边界，
否则 P3 会有人以为速度规划已经做完了。

## P2-2. 数据流与新增接口

```
              /route/path (nav_msgs/Path, map 系)        ← map_node（P1）
                         │  路径来一次，算一次
                         ▼
        ┌────────────────────────────────────┐
        │ lib/path_tracking                  │  纯 C++，无 ROS
        │  · 按**实际点距**累计弧长            │
        │  · 逐点曲率（中心差分）              │
        │  · 最近点查询（带上次索引的局部搜索） │
        └────────────────┬───────────────────┘
                         ▼
        ┌────────────────────────────────────┐
        │ lib/speed_profile                  │  纯 C++，无 ROS
        │  曲率限速 → 终点归零 → 后向扫描      │
        │  限减速 → 前向扫描限加速             │
        └────────────────┬───────────────────┘
                         │  v_ref(s) 查表，回调里只查不算
     TF map→base_link ───┤
     /odom（实测车速）  ───┤
                         ├──▶ lib/stanley  横向 → δ
                         └──▶ lib/pid      纵向 → a
                                    │
                                    ▼
                            /vehicle_cmd（50 Hz）
```

**新增的东西只有一个包和一个配置文件**，不动任何已有接口：

| 新增 | 位置 | 说明 |
|---|---|---|
| `ads_control` 包 | `src/ads_control/` | `lib/`（纯 C++17）+ `node/`，结构同 `ads_map` |
| `config/control_params.yaml` | 仓库根 `config/` | 控制增益与速度规划参数。**车辆限值不在这里**，那是 `vehicle_params.yaml` 的地盘 |

**曲率从哪来 —— 选了「控制器自己从路径点算」**，不改 `ads_msgs`、不加并行话题。
理由：路径点是**解析生成**的（`Road::lane_center_pose` 求值，不是传感器数据），
逐点朝向的自洽性已量化验证过（最大偏差 2.27°），中心差分 `k ≈ Δθ/Δs` 在 0.5 m
步长下完全干净 —— R=8 m 的弯上相邻点朝向差 0.5/8 = 0.0625 rad，信噪比极高。
改消息接口属于 CLAUDE.md 的「先问后做」，而这里没有非改不可的理由。

⚠️ **`Δs` 必须用实际点距，不能用 `path_step_m_`**（= 0.5）。弯道外侧实际点距是
0.5 × 1.1458 = 0.573 m，直接用 0.5 会把曲率算大 14.58%，
于是**弯道上限速偏严 7%** —— 车明显开得比该有的慢，而没有任何一层报错。

## P2-3. 顺手要修的一个 P1 隐患：`/route/path` 的 QoS

`map_node.cpp:157`：

```cpp
route_pub_ = create_publisher<nav_msgs::msg::Path>("/route/path", rclcpp::QoS(1).reliable());
```

`reliable` 但**没有 `transient_local`**。而 `/map/lane_graph` 那一行是有的。

**后果**：路径只在收到 `/goal_pose` 时发布**一次**。控制节点如果比 map_node 晚起、
或者中途重启，就**永远收不到那条已经发布的路径** —— 症状是车停着不动，
`/route/path` 用 `ros2 topic echo` 也是空的，而 map_node 的日志里明明白白写着
「路径已发布：1119 个点」。排查方向会全跑偏到「话题名对不对」「QoS 兼容性」上。

P1 阶段唯一的订阅者是 RViz，而人是先起 RViz 再点目标点的，所以从没露过马脚 ——
**和 `map → odom` 那个 bug 是同一个模式：错误一直在，只是没有东西依赖它。**

改法是一行：`rclcpp::QoS(1).reliable().transient_local()`。
放在 P2-S4（真正出现第二个订阅者的时候）而不是现在单独改，是为了让这次改动
**有一个能验证它的场景**：改完立刻用「先起控制节点、后点目标点」和
「点完目标点再重启控制节点」两种顺序各跑一次。

### 为什么 S2 的检查点是「纯 C++ 闭环」而不是「在 Gazebo 里看着还行」

Stanley 是个**闭环**控制律，单点测试证明不了任何东西 —— 给定一个横向误差算出
一个转角，这个转角"看着合理"和"能让车收敛"是两回事。判断稳定性必须让它**跑起来**。

而在 Gazebo 里跑，一次要几十秒、要 GPU、结果还带物理噪声。更要命的是
**失败时分不清是谁的锅**：控制律错了？增益没调好？TF 有延迟？bridge 的抗饱和
在捣乱？路径本身有问题？五个嫌疑人。

所以 S2 的判据是：在一个**纯 C++ 的运动学自行车模型**上闭环，从 1 m 初始横向偏差
出发跑 30 s，收敛到 < 0.05 m 且不震荡。这个测试毫秒级、完全确定、只有一个嫌疑人。
**它证不了车在 Gazebo 里能开，但它一旦红了，就绝对不用去查别的地方。**

这个自行车模型不是一次性代码 —— S5 会把它包成一个 ROS 假车节点，用来做
不需要 GPU 的闭环回归（见 5.2）。

### S2　横向 Stanley【纯 C++，无 ROS】【CP-P2-A】

| # | 任务 | 验收标准 | 验证方法 |

| 2.3 | 转角限幅到 `max_steer_angle_rad`；**转向速率**限幅到 `max_steer_rate_rad_s` | 任意输入下 \|δ\| ≤ 0.600、\|Δδ/Δt\| ≤ 0.500 | L1 |
| 2.4 | 运动学自行车模型（测试夹具，非产品代码） | 与解析解一致：定转角 → 半径 L/tan(δ) 的圆 | L1 |
| 2.5 | **闭环收敛测试**【CP-P2-A】 | 见下 | L1 |
| 2.6 | **定曲率稳态用例**：守住「不要加曲率前馈」这条结论 | R=8 圆弧稳态 \|e\| < 0.05 m。加了前馈这条必红（理论值 1.421 m） | L1 |

**2.1 是 Stanley 最经典的一处实现错误。** 标准推导里横向误差是**前轴中心**
到路径的距离，而本项目的 `base_link` 在后轴。用后轴误差去算的症状是：
低速下看着没问题，速度一高持续外偏 —— 而你会去调 `k`。调大 `k` 确实能压住
一部分，代价是低速下开始震荡，于是陷入「快了偏、慢了晃」的死循环。

**2.2 各项的物理含义**（详细推导见 `docs/modules/control.md` §3）：
- `ψ`（航向误差）项：车头方向对齐路径切线。**单独有它就能跟上直线，但会平行偏移**。
- `atan(k_e·e/(k_soft+v))` 项：横向误差项。`atan` 提供的是**全局**收敛性 ——
  大误差时横向趋近速度被限制在车速本身，不会发散。
- `k_e` 量纲是 1/s，时间常数 `1/k_e`。**收敛速度与车速无关**（前提 `k_soft ≪ v`），
  这是 Stanley 相对纯追踪最大的优点。初值 1.0 → 时间常数 1 s。
- `k_soft` 是**软化项**，防止 `v → 0` 时分母归零。没有它，车快停下时
  `k_e·e/v → ∞`，`atan` 饱和到 ±π/2 → 转角打死。初值 0.5 m/s。
- ⚠️ **Stanley 没有「前视距离」这个参数**（那是纯追踪的）。
  todo.md 早前那条「Stanley 对前视距离敏感」的说法是错的，已同步修正。

**2.6 是为了守住一条反直觉的结论**：**不要给 Stanley 加曲率前馈。**
`control.md` §3.5 证明航向项已经把曲率补偿了，再加 `δ_ff = arcsin(L·κ)`
就是双倍补偿，在 R=8 m 上引入 **1.421 m** 的稳态误差（越界线才 0.85 m）。
这个改动在直路上毫无影响、在所有直线用例里全绿，只在弯道上表现为
「稳态偏差怎么调都消不掉」。**属于「合理的改进使事情变糟」，
代码审查挡不住它** —— 所以要有一条定曲率用例专门盯着。

**2.3 的转向速率限幅要和控制律一起进闭环测试**，不能等到 Gazebo 里再加。
**先在 L1 里发现，比在 Gazebo 里发现便宜两个数量级。**

> ⚠️ **本条的理由在 S2 实测后改过。** 原来写的是「0.500 rad/s 意味着从零打到
> 满舵要 1.2 s，这是个不小的相位滞后，可能把稳定的增益变成震荡的」——
> **在本地图的几何上不成立**。入弯时 `e≈0` 于是 `δ≈ψ`，而 `ψ` 以 `v/R` 增长，
> 根本不是阶跃；限幅起作用的临界车速是 `v* = R·rate` = 8×0.5 = **4.0 m/s**，
> 曲率限速给的 3.464 比它低 13%，所以限幅**碰都碰不到**（实测入弯峰值 1.6 cm）。
>
> 但把它放进闭环仍然是对的，只是理由变了：一是 ψ=30° 那种**阶跃**工况下它确实
> 起作用（收敛 2.64 → 2.98 s）；二是它钉住了一条**交给 S3 的耦合约束** ——
> `a_lat_max` 调到 2.0 时 `√(2.0×8)` **恰好 4.0 m/s**，正好顶在临界值上。
> 详见 `docs/modules/control.md` §3.7。

**2.5 CP-P2-A 的判据**（全部在纯 C++ 自行车模型上，毫秒级，不需要 ROS）：

判据的期望值来自 S1.1 的**独立数值仿真**（前向欧拉自行车模型闭环，与 `control.md`
的几何闭式解是两套方法）。这与 P1 的做法一致：`test_routing` 的期望值也来自一个
穷举脚本，而不是再写一遍 Dijkstra。

| 场景 | 判据 | 解析值 | S1.1 Python | **S2 C++ 实测** |
|---|---|---|---|---|
| 直线，初始 \|e\| = 1.0 m，v = 5.556 | 5 s 内收到 \|e\| < 0.05 m，超调 < 5% | 3.00 s | 3.42 s / 0.00% | **3.36 s / 0.00%** ✅ |
| 直线，初始 ψ = 30°，e = 0，v = 5.556 | 5 s 内收到 \|e\| < 0.05 m | — | 2.64 s | **2.98 s** ✅（峰值 1.007 m） |
| R = 8 m 圆弧，v = 3.464 | **稳态** \|e\| < 0.05 m | **0** | 0.0162 m | **0.01618 m** ✅ |

**CP-P2-A 已于 2026-08-02 全部达成**，判据一条未放宽。场景②的 2.98 s 比 S1.1 的
2.64 s 慢，是因为 C++ 版**带转向速率限幅**而那次仿真没带 —— 这也是五条里唯一一处
限幅明显起作用的场景。最后一行的后轴反例是**故障注入时补上的**：注入前，
把 `front_axle_pose()` 改成直接返回后轴只有一条静态用例变红，**闭环全绿**。

> **圆弧稳态的 0.0162 m 不是误差，是离散化残差**：它与 `dt` 严格成正比
> （`e_ss = 0.81·dt`，在 16 倍的 `dt` 范围内比值只动 0.4%），
> 外推到 `dt → 0` 就是解析的 0。想压小它要**提高控制频率**，不是调增益 ——
> 增益动不了它。
>
> **入弯暂态 0.0166 m 也修正了初稿。** 初稿估的是 0.19 m，按「ψ 要一个时间常数
> 才建立，这期间车走直线」算的 —— 错在 **ψ 没有滞后**：路径切向以 `v/R` 转走，
> `ψ` 立刻同步增长，不经过任何一阶环节。

> ⚠️ **这三条判据是在 S1.1 写完推导之后改过的** —— 初稿写的是「R=8 圆弧稳态
> \|e\| < 0.10 m，因为 Stanley 在定曲率上有固有稳态误差」。**那句话是错的。**
>
> 推导（`docs/modules/control.md` §3.4）表明：在定曲率路径上
> `ψ ≡ δ` 是一个**几何恒等式**（航向误差在前轴处量，天然含有转角那一份），
> 代回控制律直接得到 `e_ss = 0`，**不需要任何前馈**。
> 车身与路径切线的 19.72° 夹角不是误差，是内轮差。
>
> 若不推导就写代码，这条会以「稳态差 10 cm 左右、判据刚好卡在边缘」的形态存在，
> 而人会把它当成 Stanley 的固有特性接受下来 —— **判据本身就是从推导来的，
> 推导错了，测试会忠实地验证一个错误的结论。**

### S3　速度规划 + 纵向 PID【纯 C++，无 ROS】

| # | 任务 | 验收标准 | 验证方法 |
|---|------|---------|---------|
| 3.1 | 曲率限速：`v_i = min(v_cruise, √(a_lat_max/\|k_i\|))` | R=8 处得 3.464 m/s | L1 |
| 3.2 | 终点归零 + **后向扫描**限减速 | 处处满足 `v_i² ≤ v_{i+1}² + 2·a_dec·Δs` | L1 |
| 3.3 | **前向扫描**限加速 | 处处满足 `v_i² ≤ v_{i-1}² + 2·a_acc·Δs` | L1 |
| 3.4 | 速度环 PID + 积分抗饱和 | 阶跃响应无稳态误差、无积分饱和 | L1 |
| 3.5 | 输出加速度限幅到 `[-max_decel, +max_accel]` | 任意输入下成立 | L1 |

**3.2/3.3 先后向（保证「减得下来」）再前向（保证「加得上去」）。**
这是标准的前后向扫描（forward-backward pass），`control.md` §4.2 给完整推导。

> ⚠️ **本条原本写着「顺序不能反」，S3 实测推翻了它**：20000 组随机剖面下，
> 两种顺序的结果**逐点完全相同**（最大差异 0.0）。理由恰恰是那句"只会调低" ——
> 两个扫描各自都调到对方约束的安全侧，谁先谁后都到同一个不动点。
> 真正必须成立的是**曲率限速与终点归零要在两个扫描之前**。
> 而这个论证依赖"只下调"：将来若加入**下界**约束（"这一点至少要多快"），
> 论证立刻失效，那时才真要讲顺序。`ScanOrderDoesNotMatter` 用例守着这条。

**为什么剖面在「路径来的时候」算一次而不是每拍算**：SPEC §7「不允许在回调中做
重计算」。剖面是**纯几何量**（只依赖路径的曲率和长度），路径不变则剖面不变。
1119 个点两遍扫描约 2200 次开方，算一次没问题，50 Hz 算就是白烧 CPU。
控制回调里只做**按弧长查表 + 线性插值**。

**3.4 的一个反直觉事实，值得单独记**：被控对象是**积分器**（a 是 v 的导数），
所以**纯 P 控制器对常值目标速度就没有稳态误差**。闭环是
`v̇ = Kp·(v_ref − v)`，一阶滞后，时间常数 `1/Kp`。`Kp = 1.0` → 63% 收敛用 1 s。

于是 `Ki` 在这里**几乎无事可做** —— 它补偿的是持续扰动（长坡、恒定阻力），
本项目地图是平的。给一个大 `Ki` 的后果是超调加震荡，而且是那种"看起来
需要更多调参"的震荡。**初值 `Ki = 0.0`，只有实测出稳态误差才往上加，
并且要说得出那个误差来自哪个物理量。** `Kd` 不用：对象已是一阶，微分只放大噪声。

> ⚠️ 但被控对象**不是纯积分器**：bridge 的抗饱和让速度设定值最多超前实测速度
> 1.0 m/s（`vehicle_cmd_bridge_node.cpp:220`）。正常加速时（+1.5 m/s²）
> 需要 0.67 s 才积出 1 m/s 的超前量，所以这个限制在常规工况下**不触发**。
> 但起步瞬间和急加速时会。L1 测试里要**带上这个饱和环节**建模，
> 否则 Gazebo 上会看到一个 L1 完全没预测到的起步迟滞。

## P3-1. 四个决策（一个要用户拍板，三个已定并说明理由）

### 决策一：速度规划从 `ads_control` **移到** `ads_planning`　✅ **已拍板（2026-08-04，用户确认「移」）**

**为什么必须移**：绕障和减速是**同一个决定的两半**。planner 决定往左绕 0.7 m，
这条轨迹的曲率比中心线大，"该慢多少"只有 planner 算得出来。如果速度仍留在
control 侧按纯几何曲率算，表面上"也会慢下来" —— 但那是**巧合**：
真正该减速的理由（离障碍物近、要给横向机动留余量、绕不过去要停）control 一无所知。

SPEC §3.2 的框图里「速度规划」本来就画在 `ads_planning` 内，`ads_control` 只有
「横向 Stanley / 纵向 PID」。所以这不是新设计，是**把 P2 临时借放在 control 里的东西还回去**
—— P2-S5 的收尾文档里已经写了这句话："速度规划…P3 接管后退化为兜底"。

**代价**（诚实列出）：
- `speed_profile.{hpp,cpp}` + `test_speed_profile.cpp`（19 个用例）整体搬到 `ads_planning`
- `control_node` 不再自己算剖面，改吃轨迹自带的 `speed_mps` / `accel_mps2`
- **CP-P2-B 必须重跑**（P2 的验收判据，8 条一条都不能掉）

**不移的后果**：`/planning/trajectory` 只能是几何，绕障时无法表达"这里要慢"，
而"绕不过去就停"这个能力**根本无处安放**。

> `speed_controller`（PI + 抗饱和）**留在 `ads_control`** —— 那是跟踪器不是规划器。
> 分界线是：**算目标是规划，跟目标是控制。**

### 决策二：参考线用 `/route/path` 折线，不用解析车道中心线　✅ 已定

两条路：

| | 折线（`/route/path`） | 解析（`ads_map` 车道中心线） |
|---|---|---|
| 精度 | 0.5 m 弦，R=8 上弦高 `R(1−cos(θ/2))` = **3.9 mm** | 精确 |
| planner 需要什么 | 只要话题 | 要拿到 route 的 **lane 序列** + 自己加载 `.xodr` |
| 复用 | P2 已验证的曲率/弧长代码 | 重写一套 |

3.9 mm 相对 CP-P2-B 实测的 0.080 m 横向误差是**两个数量级以下**，够用。
**选折线。** 什么时候这条不成立：采样步长调大（弦高按 `step²/(8R)` 涨，翻倍就是 4 倍），
或地图出现 R < 3 m 的急弯。两个条件都写进文档的边界节。

### 决策三：障碍物做成**生成物**，不手写进世界　✅ 已定

与 §3b「地图单一来源」完全同构。`config/obstacles.yaml` 一处手写，生成**两份**：

| 生成物 | 消费者 | 决定什么 |
|---|---|---|
| 世界里的静态模型（注入 `campus_loop.sdf`） | Gazebo 物理/渲染 | 车**会不会真的撞上** |
| 真值发布器的配置 | `/perception/obstacles` | planner **以为**障碍物在哪 |

**为什么不能各写各的**：两份一旦漂移，症状是**车绕过了一个不存在的东西、
然后撞上一个它看不见的东西** —— 而 planner 全程认为自己工作正常。
这与 §3b 里"车沿着一条肉眼看不见的车道走"是同一类故障。

真值发布器放在 `ads_simulation/gazebo_bridge`，话题 `/perception/obstacles`，
类型 `ads_msgs/ObstacleArray`（P0a 已定义）。P5 接上真感知后**换发布者、planner 一行不改**
—— 这正是 P0a 提前定接口的意义。

### 决策四：ODD 明确写「绕不过去就停」，且**先算可行性再放障碍物**　✅ 已定

这条是核实事实第 5 条逼出来的。设车道宽 `W`、车宽 `w`、安全间距 `g`，
障碍物在车道坐标下占 `[o_r, o_l]`（d 轴左正）。**从左侧绕行可行的充要条件**：

```
o_l + g + w/2  ≤  W/2 − w/2          ⟺   o_l ≤ W/2 − w − g
代入本项目：    o_l ≤ 1.75 − 1.80 − 0.50 = −0.55 m
```

**也就是说：障碍物必须整体位于车道中心线右侧 0.55 m 以外，否则在不压车道线的
前提下几何上无解。** 3.5 m 的车道装 1.8 m 的车再留 0.5 m 间距，只剩 1.2 m
给障碍物 —— 现实里人开车绕障常要压线，正是同一个不等式。

三种处理，只有一种是对的：

| 做法 | 评价 |
|---|---|
| 放宽间距判据到能过为止 | ❌ 违反「为了让测试通过而放宽判据」 |
| 允许压对向车道 | ❌ 那要判断对向来车，是 **P7 行为决策**的活。P3 不做 |
| **不可行时减速停车 + 报 diagnostics** | ✅ SPEC §2 第 3 条原文就是「安全减速**或**绕行」 |

所以 **P3 交付两个能力，不是一个**：可行则绕，不可行则停。
验收场景用**贴边的窄障碍物**（0.5 × 0.5 m 锥桶，中心距车道中心 1.2 m），
此时 `o_l = −0.95`，可行 d ∈ [0.45, 0.85] —— 有 0.4 m 实打实的裕度，
不是"恰好擦过"。**另配一个中心障碍物场景专门验「停」那条路径。**

### 决策五：横纵解耦（路径 lattice + 速度剖面），不做时空联合　✅ 已定

对**静态**障碍物，解耦不只是简化，是**正确的**：障碍物不动，
"什么时候到"不影响"能不能过"，所以 `d(s)` 和 `v(s)` 可以分别求再组合。

动态障碍物（P6/P7）才必须时空联合 —— 那时"绕过去"和"等它过去"是两个不同的解，
纯路径 lattice **表达不了后者**。这条边界写进 `docs/modules/planning.md`，
免得 P6 有人以为在现有框架上加个预测就够了。

### 新增消息 `ads_msgs/Trajectory` + `TrajectoryPoint`

这是**新增**而非修改已定义接口，但它将成为规划↔控制的长期契约，逐字段说明理由：

| 字段 | 单位/系 | 为什么在这儿 |
|---|---|---|
| `x_m` `y_m` `heading_rad` | m / rad，**map 系** | 几何本体 |
| `curvature_1pm` | 1/m | **由生产方给出，不让 control 重算**。control 已有参考线对象会算一遍，两边各算就有两个真值；绕障轨迹上（五次多项式曲率 vs 三点差分）差异比中心线上大得多 |
| `s_m` | m，从 0 起 | 沿**本条轨迹**的累计弧长，不是参考线的 s。控制侧的插值全按它走（P2 血泪：按点数在弯道外侧差 14.58%） |
| `speed_mps` | m/s | 已含曲率限速 + 障碍物减速 + 终点停车 |
| `accel_mps2` | m/s² | `= ½·d(v²)/ds`，给控制侧做前馈。**P2-S4 实测：不给它，斜坡段稳态差 3.0 m/s**（纯 P 跟踪斜坡的稳态误差 = 斜率/K_p） |

> **为什么不复用 `nav_msgs/Path` + 另一个速度话题**：两个话题就有两个时间戳，
> 控制侧要自己对齐。轨迹是一个整体，拆开就给了它们不一致的机会。

## P4-1. 三个决策

### 决策一：给世界加立体结构，做完整 ESKF + NDT　✅ **已拍板（2026-08-07，用户确认）**

**为什么当前世界里 NDT 做不了 —— 这不是调参问题**：

点云对位姿的约束来自表面法向，**一个平面只能约束沿它法向的那一个自由度**。
当前世界里所有点的法向都是 (0,0,1)，于是：

| 自由度 | 可观？ | 原因 |
|---|:---:|---|
| z / roll / pitch | ✅ | 地面法向正好是这三个的方向 |
| **x / y / yaw** | ❌ | 代价函数沿这三个方向**是平的** —— 点云在自己平面内滑动，残差一点不变 |

而且路面板厚 0.01 m、标线厚 0.01 m，**恰好等于雷达噪声 stddev（0.010 m）**，
信噪比 ≈ 1 —— 连这仅有的一点结构也被噪声吃掉。

这与 P3 决策四的可行性不等式**同构**：不是代码问题，是场景设定问题。
而症状会是「NDT 怎么调都飘」，然后所有人去查配准代码 —— 错却在世界文件里。

**一个把两件事绑死的推论**（这也是选 A 而不是「只做 ESKF」的实质理由）：

| GNSS 等级 | 水平 σ | ESKF 单靠它能到 | 对 P4 的含义 |
|---|---|---|---|
| 单点定位 | 2–5 m | **远不到 0.3 m** | 判据必须靠 NDT 才达得到 |
| RTK 固定解 | 0.02 m | 轻松达标 | NDT 沦为装饰 |

SPEC §1 的判据是 **0.3 m**。所以「GNSS 给单点级噪声」等价于「必须做 NDT」，
也等价于「必须先给世界加立体结构」。**这三件事是一个决策，不是三个。**
选 RTK 则等于假设园区全程固定解 —— 工程上偏乐观，且会让 P4 变成一个没有难点的阶段。

**代价**（诚实列出）：
- `campus_loop.sdf` 变了 → **CP-P2-B / CP-P3-B 必须复测一遍**（本仓库纪律）
- 结构增多 → 雷达 GPU 光线投射变量大 → **RTF 会降**，S1 出口要实测

**收益**：P5 感知**无论如何都需要一个有内容的世界**（现在点云全是地面，
聚类算法面对一个空场景），早加不亏；且不降 SPEC 规格。

### 决策二：立体结构与点云地图都做成**生成物**　✅ 已定

与 §3b「地图单一来源」、P3 决策三完全同构。`config/campus_map.yaml` 新增
`roadside_structures` 段，`gen_map.py` 多生成两份：

| 新生成物 | 消费者 | 决定什么 |
|---|---|---|
| `models/campus_structures/model.sdf` | Gazebo 渲染/物理 | 雷达**实际看到**什么 |
| `maps/campus_cloud.pcd` | `ads_localization` 的 NDT | 配准时**以为**世界长什么样 |

**为什么不能各写各的**：两份一旦漂移，症状是**NDT 稳定地收敛到一个错误的位姿**
—— 残差很小、协方差很紧、看起来一切正常，车却偏 1 m 开。
这比不收敛**危险得多**，因为不收敛会报警，而收敛到错处不会。

**点云地图用解析采样生成，不用真值建图跑一圈累积。** 两条路的对比：

| | 解析采样（选它） | 真值建图 |
|---|---|---|
| 确定性 | 完全确定，可 `--check` 逐字节比对 | 依赖那一次跑的路线与时序 |
| 能否进 CI | ✅ 不需要 GPU | ❌ 要 GPU、要跑仿真 |
| 与地图源的关系 | 直接来自地图源 | 来自**一次特定的仿真跑** |

地图是**先验**，它应该来自地图源。用一次仿真跑的产物当先验，等于让地图依赖
一条路线 —— 换条路线或换个世界，地图就悄悄变了。

> **已知的系统差异要写进文档**：解析采样是**全表面**均匀采样，而雷达只看得到
> 朝向自己的那一面、且有遮挡和距离衰减。NDT 用 voxel 内的高斯分布做匹配，
> 对这个差异容忍度尚可，但**voxel 尺寸取太小时会暴露**（voxel 内点太少，
> 高斯估不准）。这条进 S3 的边界节。

### 决策三：ESKF 保留完整 15 维，不退化成 2D　✅ 已定

状态量：位置误差 δp(3)、速度误差 δv(3)、姿态误差 δθ(3)、加速度计零偏 δb_a(3)、
陀螺零偏 δb_g(3)。

**为什么用误差状态而不是直接对状态做 KF**：姿态活在流形 SO(3) 上，
直接对四元数做线性化会破坏单位范数约束，且协方差没有良好定义。
误差状态把姿态误差表示成**小角度向量**（李代数），永远在原点附近线性化，
协方差始终定义在切空间里 —— 这才是 ESKF 的全部意义所在。

**为什么不退化成 2D**：IMU 本来就是三轴，退化要额外做投影；而 roll/pitch
恰好是地面点云**唯一可观**的那几个自由度（见决策一的表），扔掉它们等于
把 NDT 给出的信息丢一半。园区场景下 roll/pitch ≈ 0 是**结果**不是**假设**，
让滤波器自己估出来接近 0，比硬约束成 0 更能暴露问题。

## P4-2. 数据流与新增接口

```
                          ┌── /imu   (100 Hz, 带噪声与零偏)
gazebo_bridge ────────────┼── /gnss  (10 Hz, 单点级噪声)
                          ├── /odom  (轮速推算, 取车体纵向速度)
                          └── /lidar/points (10 Hz)
                                    │
                                    ▼
                          localization_node  ◀── maps/campus_cloud.pcd (先验点云地图)
                                    │
                  ┌─────────────────┼──────────────────┐
                  │                 │                  │
        TF map → odom      /localization/pose   /localization/diagnostics
         (动态, 替代               (PoseWithCovarianceStamped)
          map_to_odom_static)
                  │
                  ▼
            control_node（一行不改，见 P4-0 事实 5）
```

**关键点：发布的是 `map → odom`，不是 `map → base_link`。**
`odom → base_link` 由 Gazebo 的轮速里程计给（高频、平滑、但漂移）；
定位负责估计 `map → base_link`，两者相除得到 `map → odom`：

```
T(map→odom) = T(map→base_link)_估计 ∘ T(odom→base_link)⁻¹
```

这是 ROS 的标准分工，好处是**下游拿到的位姿始终连续**：定位跳变时跳的是
`map→odom`（低频修正量），而 `odom→base_link` 一直平滑。
直接发 `map→base_link` 会让 TF 树出现两个父节点，tf2 直接报错。

**新增话题**（`ads_msgs` 不改，用标准消息 —— 符合「先问后做」里
「修改 `ads_msgs` 已定义的消息接口」那条的规避）：

| 话题 | 类型 | 说明 |
|---|---|---|
| `/ego_pose_gt` | `geometry_msgs/PoseStamped` | 真值位姿，map 系。**仅评测用**，算法节点禁止订阅 |
| `/localization/pose` | `geometry_msgs/PoseWithCovarianceStamped` | 估计位姿 + 协方差 |
| `/localization/diagnostics` | `ads_msgs/...` 或 `diagnostic_msgs` | NDT 迭代数/残差/**退化指示**、ESKF 零偏估计值 |

## P4-3. 依赖图与切片

```
S1 世界结构 + 点云地图 + 传感器噪声 + /ego_pose_gt   ← 纯生成物与桥接，无算法
        │                    │
        │                    └──────────────┐
        ▼                                   ▼
S2 ESKF 核心【纯 C++】【CP-P4-A】      S3 NDT 配准【纯 C++】
        │                                   │
        └─────────────┬─────────────────────┘
                      ▼
        S4 localization_node + 接线【CP-P4-B = P4 验收】
                      │
                      ▼
              S5 文档 + CI + 收尾（可与 S4 并行）
```

### 为什么 S1 必须单独切一片，而且排在最前

S1 里**一行算法都没有**，全是生成物和噪声模型 —— 看起来像杂活，
但它决定了后面两片**有没有意义**：

- 不加噪声，S2 的 ESKF 在无噪声输入上「完美工作」，而这什么都没证明
- 不加结构，S3 的 NDT 在秩亏观测上「收敛」，给出的位姿是任意的
- 没有 `/ego_pose_gt`，S4 的判据**没有基准可对**

这三条都是「做完了看起来是绿的，其实什么都没验」——
和 P3-S2 那个「采样步长与段长可通约，用例全绿但什么都没测」是同一类。

**S1 出口必须先复测 CP-P2-B / CP-P3-B**，因为它动了 `campus_loop.sdf`。
把回归放在这里而不是最后，是为了让「世界改坏了」和「定位写错了」两类故障
**永远不会同时出现在现场** —— 否则排查要在两个模块之间来回跳。

### 为什么 S2 和 S3 都是纯 C++、且各自带 L1

沿用 P2-S2 / P3-S2 的做法。ESKF 的正确性判据（零偏估得出来、协方差收敛、
无观测时误差按预期增长）**在合成数据上比在 Gazebo 里好验一个数量级**：
合成数据里真值、噪声参数、零偏都是已知的，可以直接对账；
Gazebo 里只有真值位姿，零偏是看不见的。

## P4-4. 任务详拆

### S1　世界立体结构 + 点云地图 + 传感器噪声 + `/ego_pose_gt`【生成物与桥接，无算法】

1.1 `config/campus_map.yaml` 新增 `roadside_structures` 段：杆件间距、半径、高度、
　　建筑尺寸与位置、离路边距离。**每个参数都要写调大/调小的后果**。

1.2 `gen_map.py` 生成 `models/campus_structures/model.sdf`（`<static>true</static>`，
　　所有杆件与建筑作为多个 link 装进**一个模型**，减少实体数）。
　　**机械校验**（照 `gen_obstacles.py` 的做法）：结构不得侵入车道边界，
　　违反则拒绝生成 —— 否则症状是车正常行驶却撞上路灯，而所有人去查规划器。

1.3 `gen_map.py` 生成 `maps/campus_cloud.pcd`：对路面 + 结构表面解析采样。
　　`--check` 逐字节比对进 CI。

1.4 `vehicle_params.yaml` 给 IMU / GNSS 加噪声参数，`gen_vehicle_model.py`
　　推导进 SDF 的 `<noise>` 块。量级按**消费级 MEMS IMU + 单点 GNSS**：

| 参数 | 取值 | 依据与调整后果 |
|---|---|---|
| 陀螺白噪声 stddev | 8.7e-4 rad/s | ARW 0.005 °/s/√Hz × √100 Hz。调大 → 姿态随机游走快，ESKF 更依赖绝对观测 |
| 陀螺零偏（初始 / 动态 / 相关时间） | 1e-3 rad/s / 4.8e-5 / 100 s | 零偏不稳定性 10 °/h。**这是航向漂移的主因**，见下面的量级估算 |
| 加速度计白噪声 stddev | 1e-2 m/s² | 100 µg/√Hz × √100 Hz |
| 加速度计零偏（初始 / 动态 / 相关时间） | 2e-2 m/s² / 1e-4 / 100 s | 调大 → 速度积分漂得快 |
| GNSS 水平 σ | 2.0 m | 单点定位典型值。**改成 0.02（RTK）会让 NDT 失去意义**，见决策一 |
| GNSS 垂直 σ | 4.0 m | 卫星几何决定垂直精度约为水平的 2 倍 |

　　**为什么必须让 NDT 承担精度 —— 一个量级估算**：陀螺零偏 1e-3 rad/s，
　　绕环一圈约 640 m、按 5 m/s 计约 128 s，**纯惯性推算的航向漂移
　　≈ 0.128 rad ≈ 7.3°**，由此产生的位置误差是数十米量级。
　　单点 GNSS（σ=2 m）能把位置拉住但拉不到 0.3 m。**所以 0.3 m 只能靠 NDT。**
　　（这是估算，S2 出口用实测值替换。）

1.5 `/ego_pose_gt`：`gen_vehicle_model.py` 给模型加 `PosePublisher` 插件，
　　桥接到 `/ego_pose_gt`。**Gazebo 世界系就是 `map` 系**（`map→odom` 由 spawn
　　位姿推出，`odom→base_link` 由 Ackermann 给），所以模型位姿直接就是真值。
　　⚠️ 在 SPEC §4.1 和 CLAUDE.md 里标注**算法节点禁止订阅**，只给评测脚本用。

1.6 **出口**：
　　- `gen_map.py --check` / `gen_vehicle_model.py --check` 全过，进 CI
　　- RViz 里点云地图与 Gazebo 结构目视重合
　　- **实测 RTF**（结构增多的代价），与加结构前对比，掉太多则调稀杆件间距
　　- **CP-P2-B / CP-P3-B 三场景全量复测达标** ← 世界改了，这条不能省

### S2　ESKF 核心【纯 C++，无 ROS】【CP-P4-A】

2.1 名义状态 + 误差状态定义；IMU 中值积分推进名义状态。
2.2 误差状态协方差传播（`F` / `Q` 矩阵推导写进文档）。
2.3 观测更新：GNSS 位置（3 维）、**GNSS 测速（3 维）**、轮速纵向速度（1 维）。
　　⚠️ **测速这一路原本不在计划里，实施时补上的**：它与定位是**两种不同的观测量**
　　（载波多普勒 vs 伪距），精度高两个数量级。少接它不会报错，只会让精度停在
　　0.425 m 而不是 0.211 m。见 docs/modules/localization.md §4.2。
2.4 注入观测后的**名义状态修正与误差状态重置**（ESKF 的关键一步，容易漏）。
2.5 `RequireFinite` 三兄弟接上（`ads_common/numeric_checks`）—— 见 CLAUDE.md
　　那条「用比较去拦非有限值一条都拦不住」，本项目已咬过两次。
2.6 L1：**合成 IMU 数据**（已知真值轨迹 → 反算理想 IMU → 加已知噪声与零偏）。
　　用例要覆盖：零偏能被估出来且收敛到注入值、无观测时误差按 `√t` 增长、
　　协方差矩阵始终正定对称。
　　⚠️ **真值轨迹必须是「八字形 + 速度调制」，不能用匀速圆周。**
　　匀速圆周上 body 系的常值零偏在世界系里匀速旋转，一个周期内积分抵消 ——
　　零偏几乎不可观，实测跑 1000 s 相对误差反而涨到 **2.07**。
　　**用错轨迹会得到「滤波器写错了」这个假结论。** 对照用例保留在
　　`EskfDiagnostics.DISABLED_BiasObservabilityOnAConstantRateCircle`。
　　⚠️ 「位置误差按 √t 增长」是**错的**：位置是速度误差的积分，增长是 `t^1.5`。
　　有闭式解可对账的是**姿态**：`σ_θ(t) = σ_g·√(dt·t)`。

### S3　NDT 配准【纯 C++，无 ROS】

3.1 点云地图 voxel 化 → 每 voxel 拟合高斯（均值 + 协方差）。
　　⚠️ **必须按点数阈值丢弃稀疏 voxel**。S1 出口实测：2 m voxel 共 4354 个非空格，
　　每格点数中位 16，但 **8.3%（363 个）少于 5 个点** —— 那些格拟合出来的协方差
　　接近奇异，求逆会炸或给出荒谬的权重。
　　⚠️ 另有一类必须处理的退化：**路面点在 voxel 内共面**（法向全是 +z），
　　协方差矩阵秩亏（rank 2），必须对最小特征值做正则化。
3.2 目标函数与解析梯度/Hessian；牛顿法迭代。
3.3 从 Hessian 估计输出协方差（供 ESKF 用）。
3.4 **退化检测**：Hessian 最小特征值 / 条件数低于阈值时**报告退化并拒绝输出**，
　　不给一个看似合理的位姿。
3.5 L1 用例：
　　- 给定地图 + 已知位姿变换后的扫描 → 配准应恢复该变换（含旋转平移组合）
　　- **在纯地面点云上必须报退化** ← 把 P4-0 事实 2 那个坑固化成守卫用例
　　- 初值超出收敛域时应发散/报失败，而不是悄悄给个错位姿

### S4　`localization_node` + 接线【CP-P4-B = P4 验收】

4.2 NDT 用 ESKF 预测位姿作初值（闭环）；冷启动用 GNSS + 初始朝向。
　　⚠️ **初值差超过收敛域就发散** —— 这条要有明确的失败路径与日志，
　　不能静默给个错位姿。
4.3 发布动态 `map → odom` TF + `/localization/pose` + diagnostics。
4.4 **删掉 `map_to_odom_static`**（CLAUDE.md §5 早就写了「P4 接上定位后删掉」）。
4.5 降级策略：NDT 退化/失败时退回 GNSS+IMU；GNSS 也没有时纯推算并报警。
　　**分层要在 diagnostics 里说清楚现在靠什么在定位**。

| 1b | `\|误差\|` / 滤波器自报 σ | < 3 | **1.00** | 「估不准」可以接受（信息就那么多），「估不准却报告自己很准」才是 bug |

| 3 | 无观测时**姿态** σ 按 `√t` 增长 | 与闭式解差 < 2% | 通过（25→100 s 比值 2.00） | 验协方差传播。若不增长说明 `Q` 是 0，滤波器**过度自信** |
| 4 | 协方差始终正定对称 | 逐步断言最小特征值 > 0 | 通过（3000 步） | 数值退化的早期信号 |

#### ⚠️ S2 实施时对本检查点做的两处修订（2026-08-07，用户已知悉）

**修订一：评测时长 200 s → 400 s。阈值一个都没动。**
零偏从 0 收敛到真值的暂态本身约 300 s，在暂态里打分量到的是「初值猜得准不准」
而不是滤波器精度。5 个种子的实测散布：

| 时长 | 位置 RMS 范围 | 最差零偏分量均值 |
|---|---|---|
| 200 s | 0.18 – **0.37** m（判据 0.30，**会 flake**） | 0.119 |
| **400 s** | 0.19 – 0.245 m | **0.078** |
| 600 s | 0.19 – 0.266 m | 0.082 |

这与 CP-P2-B「跟踪质量类的量才该过滤，车没在跟轨迹时问它偏了多少没有定义」同理。

**修订二：判据取 5 个随机种子的均值 / 每种子分别断言，不用单次结果。**
单次结果是随机变量，拿它比固定阈值，判据的可靠性受限于那一次抽样的运气。

**⚠️ 原判据第 2 条与 P4-1 决策一曾经互相矛盾**：决策一论证「单点 GNSS 下 ESKF
远不到 0.3 m，所以必须做 NDT」，而本条却要求 ESKF 阶段就达到 0.3 m。
实测确认了矛盾：只用 GNSS 定位 + 轮速时 RMS **0.425 m**。
**解决方式不是放宽判据，而是补上一路本来就存在却没接的观测** ——
GNSS 测速（载波多普勒，σ=0.05 m/s，比定位精确两个数量级）。
接上之后 RMS 降到 **0.211 m**、末姿态误差从 0.0205 rad 降到 0.00049 rad。
决策一的结论方向仍然成立（NDT 仍是达到 SPEC §1 全程 0.3 m 的必要条件），
但「远不到」这个措辞过于悲观 —— ESKF+GNSS 实际能做到 0.21 m。

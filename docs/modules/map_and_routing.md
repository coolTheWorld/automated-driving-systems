> 这个模块里有四个地方**做错了不会报错，只会给出一个看起来完全正常的结果** ——

## 0. 术语与坐标约定

| 记号 | 含义 | 单位 |
|---|---|---|
| `s` | 沿**道路参考线**的弧长坐标 | m |
| `t` | 相对参考线的**横向偏移**，以参考线**左侧**为正 | m |
| `θ` | 航向角，x 轴正方向为 0，逆时针为正（REP-103） | rad |
| `k` | 曲率 `1/R`。**正 = 左转（逆时针）**，0 = 直线 | 1/m |
| `w` | 车道宽度 | m |

坐标系为 **ENU**（x 东、y 北、z 上），与 ROS 的 `map` 系一致（SPEC §4.1）。

### OpenDRIVE 的车道编号约定

这不是本项目的选择，是规范定的，但它是后面一切的地基：

```
        ┌──────────────────────────────┐
   +2   │  ← 逆 s 方向行驶              │   t > 0（参考线左侧）
   +1   │  ←                           │
    0   ├──────── 参考线 ──────────────┤   t = 0，宽度恒为 0，不可行驶
   -1   │  →                           │
   -2   │  → 沿 s 增大方向行驶           │   t < 0（参考线右侧）
        └──────────────────────────────┘
```

**右侧通行下，`−1` 是顺行道、`+1` 是对向道。** 注意这条约定说的是
「车道编号符号 ↔ 行驶方向」，与地图上哪条路朝哪个方向画无关 ——
参考线可以朝任意方向铺设，`−1` 永远沿 `s` 增大方向走。

由此立刻得到一条**在整个模块里反复用到**的推论：

> 沿 `s` 增大方向行驶 ⟺ 车道编号为负。

`LaneGraph::add_edge()` 就是拿它做自洽检查的（见 §5.3）。

## 1. 参考线求值：`s → (x, y, θ)`

参考线由若干**几何段**首尾相接。本项目只支持两种原语：直线和圆弧
（`spiral` / `poly3` / `paramPoly3` 遇到即**显式抛异常**，见 §10）。

### 1.1 圆弧的闭式解

一段圆弧由起点 `(x₀, y₀, θ₀)`、曲率 `k`、弧长 `L` 完全确定。
沿弧长参数化时航向线性增长：

```
θ(s) = θ₀ + k·s
```

于是

```
dx/ds = cos(θ₀ + k·s)
dy/ds = sin(θ₀ + k·s)
```

两边对 `s` 从 0 积到 `Δs`：

```
x(Δs) = x₀ + [ sin(θ₀ + k·Δs) − sin θ₀ ] / k
y(Δs) = y₀ − [ cos(θ₀ + k·Δs) − cos θ₀ ] / k
θ(Δs) = θ₀ + k·Δs
```

**对 `k` 的正负都成立**，不需要分左转右转两种写法 —— 想分开写的话，
两支之间的符号差异是最容易写反的地方之一。

验算 `y`：`d/ds { −[cos(θ₀+ks) − cos θ₀]/k } = −[−sin(θ₀+ks)·k]/k = sin(θ₀+ks)` ✓

### 1.2 为什么直线必须单独一支

上式在 `k → 0` 时是 `0/0` 型。极限确实存在（洛必达即得直线公式），
但**浮点上算不出来**：分子分母同时趋于 0，有效位一起丢光。

有人会想「用一个很小的 `k` 近似直线」。代入本项目最长的一段直线
（`loop_east` 的东侧 76 m）估一下：取 `k = 1e-9`，终点朝向偏 `7.6e-8` rad，
看着无害；但位置误差是 `L²·k/2 = 76²×1e-9/2 ≈ 2.9 µm`，而**误差随 `L²` 增长** ——
地图放大 10 倍就是 0.29 mm。更要命的是它会**吃掉 CP-P1-A 对账的全部余量**
（判据 1 mm，实测残差 0.00073 mm）。

所以：

```cpp
if (curvature_inv_m == 0.0) {  // 精确比较，因为它来自 .xodr 文本里的 "0"
  return { x + ds·cos θ, y + ds·sin θ, θ };
}
```

代码位置：`src/ads_map/src/geometry.cpp` 的 `Geometry::pose_at()`。

### 1.3 航向**不做**归一化

`Pose2D::heading_rad` 沿参考线累加时会连续增长，可能跑出 `[−π, π]`。
这是**有意的**：跨越 `±π` 时不跳变，做差、插值、判连续性都不必先处理绕回。
需要归一化时显式调 `ads_common::normalize_angle()`。

`test_geometry.cpp` 的 `ArcHeadingIsNotNormalised` 把这条钉住了 ——
哪天有人「顺手」加了归一化，它会红。

## 2. 车道中心线：横向偏移 `t`

车道 `i` 的中心线是参考线的**等距偏移曲线**：

```
p(s) = r(s) + t · N(s)
```

其中 `N` 是参考线的**左**法向：`N = (−sin θ, cos θ)`，即航向逆时针转 90°。

### 2.1 `t` 怎么算

从中心向外逐条累加：内侧车道算整宽，本车道算半宽。

```
t(lane i) = ± ( Σ_{j 在 i 与 0 之间} w_j  +  w_i / 2 )      右侧车道取负
```

**为什么不直接写 `sign·(|i| − 0.5)·w`** —— 那个公式只在**所有车道等宽**时成立。
本项目当前的地图确实等宽，但把这个巧合固化进代码，等到哪天加了一条展宽的
右转专用道，车道中心会静默偏掉半个车道宽，而没有任何一层会报错。

代码位置：`Road::lane_offset_at()`。

### 2.2 朝向

等距偏移曲线**处处平行于**原曲线，所以车道中心线在 `s` 处的朝向
就是参考线在 `s` 处的朝向 —— 不需要任何修正。

但**行驶朝向**要另算：

```
行驶朝向 = 参考线朝向 + (车道编号 > 0 ? π : 0)
```

这个 `π` 是「有向图」的全部物理含义所在。漏掉它的后果见 §5.1。

## 3. 车道中心线的弧长

这是整个模块里最容易被当成「精细化」而略过的一节，但它决定路由的对错。

### 3.1 推导

设参考线的 Frenet 标架为 `T`（切向）、`N`（左法向）。由

```
dθ/ds = k,    T = (cos θ, sin θ),    N = (−sin θ, cos θ)
```

直接微分得 Frenet 公式：

```
dT/ds = k·N
dN/ds = −k·T
```

对偏移曲线 `p(s) = r(s) + t·N(s)`，在 `t` 为常数的区间上：

```
dp/ds = T + t·(dN/ds) = T − t·k·T = (1 − t·k)·T
```

于是弧长微元

```
|dp| = |1 − t·k| · ds
```

**几何解释**：`R_lane = R_ref·(1 − t·k) = R_ref − t`（代入 `k = 1/R_ref`）。
左转（`k > 0`）时右侧车道（`t < 0`）在外圈，半径更大；右转反之。

### 3.2 为什么是精确解而不是数值积分

- **曲率 `k` 在一个几何段内是常数**（OpenDRIVE 的 `<geometry>` 就是这么定义的）
- **横向偏移 `t` 在一个车道段内是常数**（前提是等宽，见下）

所以只要在**几何段边界 ∪ 车道段边界**处切开，每一小块内 `k` 和 `t` 都是常数：

```
L_lane = Σ_块  Δs_块 · (1 − t_块 · k_块)
```

这是**精确值**，不是近似。代码位置：`Road::lane_arc_length()`。

### 3.3 三条守卫

| 情况 | 处理 | 理由 |
|---|---|---|
| 车道**非等宽**（`b/c/d ≠ 0` 或一段里多条 `<width>`） | **抛异常** | `t` 随 `s` 变，弧长成了椭圆积分。按常宽算完会返回一个**偏小**的值，症状是「路由莫名其妙偏爱某条路」，无任何报错 |
| `1 − t·k ≤ 0` | **抛异常** | 车道中心落到曲率中心之外，偏移曲线退化。这不是数值问题，是地图画错了：转弯半径 ≤ 车道到参考线的距离 |
| 两个端点任一越界 | **抛异常** | 只查一端的话，「起点合法、终点越界」会算出一个偏短但看不出问题的长度 |

### 3.4 这一节的实际后果（本项目地图上的具体数字）

`R = 12 m` 的角落弯，车道宽 3.5 m：

| 车道 | `t` | 长度比 `1 − t·k` | 该弯的车道弧长 |
|---|---|---|---|
| `−1`（外圈） | −1.75 | **1.145833**（+14.58%） | 13.75 × π/2 = 21.598 m |
| `+1`（内圈） | +1.75 | **0.854167**（−14.58%） | 10.25 × π/2 = 16.101 m |
| 参考线 | 0 | 1.000000 | 12 × π/2 = 18.850 m |

于是 `loop_east` 这条路：

```
参考线长      247.699112 m
lane −1 长    253.196899 m   （+5.50 m）
lane +1 长    242.201325 m   （−5.50 m）
```

**两个方向差 `2 × 2 × w/2 × π/2 = π·w = 10.996 m`**，且这个差
**与转弯半径无关** —— 半径在相减时抵消掉了。

## 4. 为什么路由代价必须用车道中心线长度

上一节的 14.58% 听起来像个可以忍受的误差。它不是。本项目的地图上有一个
**干净的反例**：

从 `(road 1, lane −1)` 的 `s=100` 走到它的**对向车道** `(road 1, lane +1)` 的 `s=100`
（两点相距 3.5 m），有且只有两条候选路线：

| 路线 | 车道中心线代价 | 参考线代价 |
|---|---|---|
| 经横穿路兜回来 | **674.732290 m** ← 赢家 | 680.230077 m |
| 绕整圈 | 685.727864 m | 680.230077 m |
| **差值** | **10.995574 m** | **0.000000 m** ← **并列** |

参考线代价**恰好并列**，不是巧合：两条路线用到的参考线长度是**同一个多重集**
（一条 22 m 直行、一条左转、一条右转、`loop_west` 全长、`cross` 全长），
只是分配到了不同的行驶方向上。而参考线长度**结构性地看不见方向**。

两条路线的真正差别只有一处：一条走 `loop_west` 的内圈车道，另一条走外圈。
差值 `10.995574 m = π·w = π × 3.5` —— 正是 §3.4 那个「与半径无关」的量。

**并列的后果不是「算错」，而是返回哪条取决于堆的遍历顺序** ——
换个标准库实现就可能变，而两条路径在 RViz 里都完全正常。这类不稳定性
极难在测试里复现，也极难在故障发生时想到。

`test_routing.cpp` 的 `OppositeDirectionOfTheSameRoadRequiresGoingAround`
就是这条的守卫：它断言路径**不含** `(2, −1)`，即没走那条更长的候选。

## 5. 车道图

### 5.1 为什么必须是有向图

一个节点 = **一条道路上的一条有向车道**，记作 `(road_id, lane_id)`。
同一条物理道路的两个方向是**两个节点，之间没有边**。

建成无向图的后果：Dijkstra 会发现「原地掉头」是通往对向车道的最短路。
上一节那个 674.73 m 的路径会变成约 **0 m** —— 而它在 RViz 里是一条平滑的短线，
长度也合理，肉眼永远看不出问题。要等到 P2 车真的开上去，才会发现它在逆行。

### 5.2 建边规则

对节点 `(r, l)`，行驶方向上的**出口端**由 `l` 的符号决定：

| `l` | 行驶方向 | 入口 `s` | 出口 `s` | 出口端的道路链接 |
|---|---|---|---|---|
| `< 0` | `s` 递增 | `0` | `length` | `<successor>` |
| `> 0` | `s` 递减 | `length` | `0` | `<predecessor>` |

出口端接的是什么，决定查哪张表：

- **接路口**（`elementType="junction"`）：遍历该路口的 `<connection>`，
  取 `incomingRoad == r` 且 `<laneLink from>` 等于 `l` 的那些，
  目标节点是 `(connectingRoad, laneLink.to)`。
- **接道路**（`elementType="road"`，本项目里是「连接道路 → 出口道路」）：
  车道级去向在 `<lane><link>` 里，目标节点是 `(elementId, lane.successor/predecessor)`。

**断头路（没有链接）是合法的**，只是没有后继 —— 不报错。
但「有道路级链接、没有车道级链接」要**抛异常**：静默跳过的后果是路网在这里
断成两半，而路由只会说「不可达」。

### 5.3 `contactPoint` 与车道符号的自洽检查

`contactPoint` 说明我们从目标道路的**哪一端**驶入。结合 §0 那条推论：

```
从 start 驶入  ⟹  此后沿 s 增大方向行驶  ⟹  目标车道编号必为负
从 end   驶入  ⟹  此后沿 s 减小方向行驶  ⟹  目标车道编号必为正
```

两者对不上就抛异常。这条检查不是形式主义 —— 放过去的后果是图里多一条
**方向相反**的边，而路径依然平滑。故障注入实测：把「出口端」的判据写反
（`lane_id > 0` 当成沿 s 走），这条检查在**第一条边**上就炸了，不用等到几何对不上。

### 5.4 建图结果与验收

本项目地图（3 条常规路 + 2 个 T 型路口 + 12 条连接道路）：

| 项 | 值 | 手数依据 |
|---|---|---|
| 节点 | **18** | 3 条常规路 × 双向 2 条 + 12 条单向连接道路 |
| 边 | **24** | 6 条常规车道 × 2 个去向 + 12 条连接道路 × 1 个去向 |
| 掉头边 | **0** | T 型路口 3 条腿，每个来向去另外 2 条，不含 U 形 |

> **T 型路口为什么是 6 条连接道路**：`n(n−1) = 3×2 = 6`，即每条腿去往另外两条腿。

**最强的一条测试判据是几何连续性**（`EveryEdgeIsGeometricallyContinuous`）：
对每条边，检查上一条车道**出口**处的行驶位姿 ≈ 下一条车道**入口**处的行驶位姿。

它的价值在于**不看上面任何一条约定** —— `contactPoint` 指哪一端、`laneLink from`
指谁、正编号车道的出口在 `s=0` 还是 `s=length`，这四处任意一处理解反了，
边数**都还是 24 条**，但连续性一定红。

实测：最大位置断裂 **4.0e-7 mm**，最大朝向断裂 **9.8e-12 rad**。

> ⚠️ 判据里的朝向必须用**行驶朝向**（正编号车道翻 180°），不是参考线朝向。
> 只比位置不比朝向的话，一条方向接反的边照样能过 —— 两条车道在路口处
> 位置本来就重合。

## 6. 路由：Dijkstra

### 6.1 代价与松弛

边权 = 走完一条车道的车道中心线长度（§3、§4）。`dist[v]` 定义为
「从起点位置出发、抵达节点 `v` **入口**的距离」，于是松弛就是

```
dist[w] = dist[v] + length(v)
```

—— 边权挂在**出发节点**上，不是到达节点上。

### 6.2 起点与终点的部分车道

起点不在车道入口处，终点也不在出口处，所以要拆出两段：

```
head = 从 start_s 到起点车道出口的弧长
tail = 从终点车道入口到 goal_s 的弧长
总长 = head + Σ(中间各条车道的完整长度) + tail
```

### 6.3 虚拟源点：一个只在特定输入下才发作的坑

直觉写法是 `dist[start] = 0` 然后把起点压进堆。**这在「起点终点同车道、
且目标在行驶方向后方」时会出错**：起点节点既是起点又是终点，前驱链会绕成一个环，
回溯时死循环或越界。

正确做法是引入一个**虚拟源点**（下标 = `node_count()`），它到起点车道各后继的
边权就是 `head`：

```
for v in successors(start):
    dist[v] = head;  prev[v] = SOURCE
```

这样起点节点就是一个**普普通通的节点**，可以被重新访问，
「目标在后方 → 绕一圈回来」自然成立，不需要任何特判。

`test_routing.cpp` 的 `SameLaneWithTheGoalBehindGoesAround` 覆盖这一支
（实测 189.831853 m，路径 `(1,−1) → (17,−1) → (3,+1) → (14,−1) → (1,−1)`）。

### 6.4 「不可达」与「已经在终点」必须能区分

```cpp
std::optional<Route> find_route(...);
```

- 返回 `std::nullopt` ⟹ **图上确实不可达**
- 返回的 `Route::steps` **保证非空**；「已经在终点」是一条**单段、长度 0** 的路径

把两者都表示成「空」的话，下游只会看到「路径里没有点」，然后照常发布一条空的
`nav_msgs/Path` —— RViz 上什么都不显示，而没有任何一层报错说路由失败了。

> ⚠️ `map_node` 在失败时**确实会**发一条空 `Path`，但那是**清屏**这个显式动作，
> 而且总是伴随一条 WARN 日志。库那一层绝不这么表示失败。两者别混起来看。

### 6.5 确定性

优先队列的元素是 `(距离, 节点下标)` 的 `pair`。距离相同时按下标比，
**结果就是确定的**。不这么做的话，代价并列的两条路线返回哪条取决于堆的内部顺序 ——
换个标准库实现就可能变（§4 已经说明这种不稳定有多难查）。

## 7. 最近车道查询：世界坐标 → `(road, lane, s)`

两步：

1. **粗采样**：沿每条车道中心线按固定步长求值，找最近的采样点。
   目的只是**框住**全局最小落在哪一段，不求精度。
2. **三分法细化**：在最近采样点两侧各一个步长内做三分搜索。
   距离平方在最小值附近是单峰的（这一小段上曲线近似直线），三分法适用。

最终精度由第 2 步保证，**与步长无关**。

### 7.1 朝向过滤不是可选项

双向道路的两条车道只差 3.5 m。不给朝向的话，自车停在偏左一点就会被判到
**对向**车道上，于是路由第一步就要求它掉头 —— 而那条路径在 RViz 里平滑正常。

所以 `nearest_lane()` 接受一个可选的 `heading_rad`：给了它就只在
**行驶方向夹角 < 90°** 的车道里找。`map_node` 对**起点永远传**
（自车朝向来自 TF），对终点默认不传（见 §9 的 `use_goal_heading`）。

## 8. 数值精度：同一个格式串套不同量纲是想当然

`gen_map.py` 生成 `.xodr` 时一度对所有浮点用同一个 `%.6f`。坐标用 6 位小数
（微米级）绰绰有余，但**角度和曲率不是坐标**：

| 量 | 机理 | 6 位小数下的后果 |
|---|---|---|
| **曲率** | 是**小数值** → 需要**相对**精度 | `1/12 = 0.083333…` 只剩 5 位有效数字，相对误差 **4.0e-6**；乘上 18.85 m 弧长 → 终点朝向偏 **6.3e-6 rad** |
| **朝向** | 是**力臂** → 需要**绝对**精度 | 舍入上限 5e-7 rad × 76 m 直线 = **38 µm** 位置偏差，且**随地图变大线性增长** |

后果不是「不准」，而是**判据变脆**：CP-P1-A 的对账余量一度只剩 1.5 倍，
随时可能因为改地图而误报。改用 `%.12g`（`gen_map.py` 的 `precise()`）后
余量回到两三位数倍，且不再随地图规模缩水。

> **这个洞是靠「打印实测最大值」而不是「只断言通过」暴露的。**
> 只看绿灯的话，它会一直躺到某次改地图时突然变红，而那时没人记得判据是怎么来的。

## 9. 参数表

SPEC §12 要求「每个参数在文档中给出物理含义和推荐范围」。

### 9.1 地图配置（`config/campus_map.yaml`，**唯一手写来源**）

| 参数 | 值 | 物理含义 | 调大 / 调小 |
|---|---|---|---|
| `lanes.width_m` | 3.500 | 车道宽 | 调小到 < 车宽 + 余量会让车压线；调大浪费园区空间。城市道路典型 3.0–3.75 |
| `lanes.speed_limit_mps` | 8.333 | 限速（**道路属性**，不是车辆能力） | P1 不读它，P2 速度规划才用 |
| `loop.corner_radius_m` | 12.0 | 环线四角的**参考线**半径 | 调小 → 外圈车道半径 `R+1.75` 仍需 ≥ 最小转弯半径；调大 → 直线段变短 |
| `junction.turn_radius_m` | 8.0 | 路口转弯的**车道中心线**半径 | 直接决定路口尺寸。调小到接近轴距会转不过来 |
| `junction.clearance_m` | 1.250 | 路口退让的额外余量 | 见下面的 `cutback` |

**`cutback` 是推导量，不是配置项**：

```
cutback = turn_radius_m + width_m/2 + clearance_m = 8.0 + 1.75 + 1.25 = 11.0 m
```

它必须 ≥ `turn_radius + 半车道`，否则转弯圆弧的切点会落到路口区域外面、
连接道路接不上。把这种约束交给人填等于给一个填错就崩的机会；做成推导量，
约束永远成立。

### 9.2 `lib/` 层的编译期常量

| 常量 | 值 | 含义 | 调大 / 调小 |
|---|---|---|---|
| `kEps`（`road_map.cpp`） | 1e-9 m | `s` 与道路长度比较的容差 | 放大到毫米级会掩盖真正的越界；缩到 0 会在 `s == length` 这个合法边界上误报 |
| `kNearestSampleStepM` | 0.5 m | 最近车道查询的粗采样步长 | **不决定精度**（三分法保证）。调大 → 线性变快，但急弯/S 弯上可能选到另一侧的局部极小；调小 → 线性变慢。判据是远小于曲率半径，本地图最小参考线半径 6.25 m，0.5 m 对应 4.6° 转角 |
| `kRefineIterations` | 60 | 三分法迭代次数 | 每次缩到 2/3，60 次把 1 m 区间缩到 ≈1e-11 m，远超浮点有效位 |
| `kHeadingToleranceRad` | π/2 | 朝向过滤阈值 | 调小（如 45°）→ 转弯中的自车可能一条车道都匹配不上，路由直接失败；调大（接近 180°）→ 等于没有过滤，对向车道会被选中 |

### 9.3 `map_node` 的 ROS 参数

| 参数 | 默认 | 含义 | 调大 / 调小 |
|---|---|---|---|
| `map_file` | `<share>/ads_map/maps/campus.xodr` | 地图路径 | 从本包 share 取，不假设工作区挂在 `/workspace` |
| `map_frame` / `base_frame` | `map` / `base_link` | TF 坐标系名 | — |
| `marker_sample_step_m` | 1.0 | 车道图显示的采样步长 | 调大 → RViz 更流畅但弯道显折线；调小 → 点数线性上升 |
| `path_sample_step_m` | 0.5 | 路径采样步长 | 同上。P3 若要等弧长采样，应在规划层做而不是改这里 |
| `max_start_distance_m` | 5.0 | 自车离最近车道多远还算「在路上」 | 依据：半车道 1.75 + 半车宽 ≈0.9 + 余量。调大 → 停在草地上也被静默吸附，路径看起来正常但起点是错的；调小 → 正常横向误差就让规划失败，用户只觉得「点了没反应」 |
| `max_goal_distance_m` | 10.0 | 点击目标点的容差 | 比起点松，因为点击是人手操作。但 10 m ≈ 三个车道宽，再大就该怀疑用户点的根本不是路 |
| `use_goal_heading` | `false` | 是否用 2D Goal Pose 的朝向约束终点车道 | 默认关：随手一点的朝向是噪声，当硬约束会让点击频繁失败。**起点的朝向永远参与匹配，那不是可选项** |

> ⚠️ 采样步长走的是**参考线弧长 `s`**，不是车道中心线弧长。所以弯道外侧的
> 实际点距会比设定值大最多 14.58%（§3.4）。显示用途下无所谓，但
> `check_map_node.py` 的「相邻点距」判据留了 1.5 倍余量正是为它。

## 10. 已知边界（**未实现，不要假设能用**）

| 项 | 现状 | 触发时会怎样 |
|---|---|---|
| `spiral` / `poly3` / `paramPoly3` 几何 | **不支持** | 解析时**显式抛异常**，不静默跳过。代价是读不了 CARLA 官方的 Town 地图 —— 这是清醒的取舍 |
| 多个 `<laneSection>` | 解析与几何求值**支持**，**建图不支持** | `LaneGraph` 构造时抛异常。跨段的车道对应关系需要读 `<lane><link>`，尚未实现 |
| 变宽车道（`width` 的 `b/c/d ≠ 0`） | **不支持** | `lane_arc_length()` 抛异常。弧长是椭圆积分，按常宽算会给一个偏小的值 |
| 车道级的横向换道边 | **没有** | 图里只有纵向的前后继与路口连接。P3 的 Frenet 规划在**车道内**做横向机动，不需要图上有换道边 |
| 转向惩罚 / 限速 / 信号灯代价 | **没有** | 代价只有长度。P3 若要「少拐弯优先」，是在代价函数里加项，不是对结果做后处理 |
| 定位 | **没有**（P4） | `map → odom` 目前由静态 TF 顶替，取值 = 自车 spawn 位姿（**不是单位变换**，见 CLAUDE.md） |

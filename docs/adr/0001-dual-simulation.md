## 背景

需要一个仿真环境来开发园区低速自动驾驶栈。硬约束有三条：

1. **开发机是 Windows 11 + WSL2，显卡是 AMD Radeon 780M 核显。**
   CARLA 官方要求 NVIDIA 独显（≥ 6 GB 显存），本机跑不了。
2. **路线图 P1–P7 有七个阶段**，每个阶段都要反复跑仿真调参。
3. **测试要分四层**（SPEC §8），其中 L3 场景测试是闭环的、分钟级的，
   必须能自动跑 —— 手动跑的测试三个月后一定没人跑。

---

## 考虑过的方案

### A. 只用云端 CARLA

租 GPU 实例（Vast.ai），所有开发都在云上。

**否决理由**：

- **L3 场景测试永远进不了 CI。** CARLA 要 GPU、镜像 20 GB、跑起来不确定
  （同样输入不保证同样输出）。这意味着整个 L3 层只能人工跑。
- 每次开发都要开实例、等启动、传代码；网络一断活就干不了。
- P1–P4 这些完全不需要高保真渲染的阶段（地图、路由、控制、定位）也要付 GPU 钱。

### B. 只用本地 Gazebo

**否决理由**：Gazebo 的传感器仿真保真度不足以支撑最终验收 ——
没有真实的相机成像、没有复杂交通流、没有行人模型。
项目目标是"工业级架构"，验收环节用玩具级仿真说不过去。

### C. 自研轻量仿真器

一度考虑过，理由是"只需要运动学，不需要渲染"。

**否决理由**：低估了工作量。传感器模型、物理引擎、时间同步、可视化，
每一样都是成熟仿真器已经解决的问题。自研等于把项目重心从"自动驾驶栈"
挪到"仿真器"上。**已在 SPEC §9 D1 标记作废。**

### D. AWSIM

**否决理由**：绑定 Autoware 生态。本项目要从零手写算法，
用一个假设你在跑 Autoware 的仿真器会处处别扭。

### E. ✅ 双环境：日常 Gazebo，验收 CARLA

**决定性的前提是一次实测**：WSL2 下容器内能拿到 OpenGL **4.6** 硬件加速
（`/dev/dxg` + `GALLIUM_DRIVER=d3d12` → D3D12 → Radeon 780M），
而 Gazebo 的 OGRE 渲染只要求 3.3+。**所以本地完全跑得动 Gazebo。**

这个实测把方案 A 的"只能上云"前提直接推翻了。

---

## 决定

**日常开发（P1–P7 全程）用本地 Gazebo Harmonic，最终验收用云端 CARLA。**

关键约束：**仿真数据源必须可插拔。**

```
                 ┌─ gazebo_bridge  （环境 A：本地日常）
ads_simulation ──┼─ carla_bridge   （环境 B：云端验收）
（统一接口）      └─ bag_replay     （离线回放）
                          │
                          ▼
              SPEC §4.1 规范话题（/lidar/points、/odom、/vehicle_cmd …）
                          │
                          ▼
                   上游算法节点
        **只认话题，不知道数据从哪来**
```

bridge 层的唯一职责是把仿真器原生话题翻译成规范话题名。
Gazebo 侧和 CARLA 侧做**完全相同**的翻译。

## 后果

### 正面

- **P1–P4 零云端成本、零网络延迟。** 这几个阶段（地图、路由、控制、定位）
  不需要高保真渲染，Gazebo 完全够用。
- **L3 场景测试能进 CI。** 这是最被低估的一条：Gazebo 可 headless、镜像小、
  行为确定。CARLA 永远做不到。没有它，L3 层就只能人工跑。
- **云实例断了也能继续干活。** 开发不再依赖网络和别人的机房。
- 版本约束链从 Gazebo 往外推（Harmonic → Jazzy → Ubuntu 24.04），
  官方支持落在天天用的那一侧。

### 负面 —— 头号风险是**行为漂移**

两套仿真的动力学一旦不一致，症状是**本地调好的控制参数一上 CARLA 就震荡，
而你无法判断是算法错了还是环境不同**。这种故障最消耗人。

缓解措施（都已落地，不是计划）：

| 措施 | 落地方式 |
|---|---|
| 车辆参数单一来源 | `config/vehicle_params.yaml` 是唯一允许定义轴距/转角/质量/限值**以及传感器外参**的地方；SDF 和 URDF 都是生成物，共用同一个 `derive()` 推导函数 |
| CARLA 侧对齐 | `carla_bridge` 用 `apply_physics_control()` 把 CARLA 车辆调到与 YAML 一致，传感器按同一份外参 spawn |
| 契约用同一套脚本验收 | `verify_ros_bridge.sh` 检查的全是 SPEC §4.1 的对外契约，不含任何 Gazebo 特有的东西 —— P0b 的 `carla_bridge` **原样复用它**，只换 `LAUNCH_PKG` / `LAUNCH_FILE` 两个变量 |
| 生成物同步进 CI | `gen_vehicle_model.py --check` 卡住"改了 YAML 忘了重新生成" |

### 其它代价

- **要维护两套 bridge。** 接受，因为翻译层本身很薄（一张话题映射表 + 少量单位换算）。
- **DDS 被锁死在 Fast DDS。** CARLA 原生 ROS 2 只支持它。症状是本地 Gazebo
  一切正常、一上 CARLA 完全收不到数据，所以在 Dockerfile 层面锁死
  `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`（SPEC §4 三条硬禁止之一）。
- 本地与云端**必须共用同一个 Dockerfile**，不允许分叉 —— 分叉了就等于有三套环境。

## 验证

P0a 结束时的实测（不是估计值）：

| 指标 | 实测 | 判据 |
|---|---|---|
| 容器内 OpenGL | 4.6 core，`Accelerated: yes`，D3D12 (Radeon 780M) | ≥ 3.3 |
| 实时率 RTF（带 32 线激光雷达） | **1.000** | ≥ 0.8 |
| `/lidar/points` 频率 | **10.00 Hz** | ≥ 9.0 |
| TF 树外参 | 五段连通，与 YAML 逐位一致 | 完全一致 |
| `verify_ros_bridge.sh` | 6/6 | 全过 |

**RTF 1.000 是这个决定成立的关键数字**：它说明本地 Gazebo 不是"勉强能跑"，
而是跑得和真实时间一样快，完全支撑得起日常开发和 CI。
